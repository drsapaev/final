# Public website slug format is part of the database contract

**Date:** 2026-10-08 13:34 UTC
**Files:** Alembic 0079, Service and Doctor models, PostgreSQL integration coverage
**Severity:** medium

## Problem

The public-site plan reserves URL slugs for lowercase ASCII letters and digits separated by single hyphens. Length and uniqueness were enforced, but direct database writes could store an empty or malformed slug.

## Root Cause

The migration and ORM metadata added a nullable string and unique partial index without a format check. The planned format existed only in documentation, leaving PostgreSQL as an incomplete source of truth.

## Solution

Add named PostgreSQL CHECK constraints for both services and doctors. Permit `NULL` for drafts and require non-null values to match `^[a-z0-9]+(-[a-z0-9]+)*$`. Mirror each check in the ORM metadata and test valid values, invalid values, uniqueness within each entity, and separate slug namespaces across entities using disposable local PostgreSQL.

## Prevention

- Treat slug format, null semantics, and uniqueness as database invariants, not only form validation.
- Keep migration DDL and ORM constraints aligned.
- Cover valid, invalid, null, duplicate, and cross-entity cases against PostgreSQL.
