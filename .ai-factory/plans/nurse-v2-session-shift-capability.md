## Цель и границы

Дать клинике факт дежурства: медсестра открывает смену на станции (QueueResource), работает в ней, завершает; система знает «кто сейчас на дежурстве», атрибутирует операции окном смены и не рвёт начатую работу при закрытии смены. Смена — это ФАКТ работы (кто/где/когда), а не новая роль и не пересмотр RBAC-модели (граница D2 FINAL).

- **В scope:** сущность смены (рабочее имя `nurse_duty_sessions`), жизненный цикл open/switch/close с учётом in-flight работы, server-state восстановление на планшете, координация revocation назначения с активной сменой (обязательная часть SS-2, см. отдельный раздел), PG-concurrency proof.
- **Не в scope (не-цели):** HR/табели/зарплаты; авто-планирование смен из `ScheduleTemplate` (`backend/app/models/schedule.py` — шаблоны приёма врачей для записи, НЕ ростер дежурств; переиспользование запрещено контекстом); публичные графики; новые RBAC-гранты или role enum (D2 FINAL: «не RBAC»); новый WS-протокол (polling-паттерн N2-5 §10); прод-deploy трека (N2-5 brief §15 — отдельное решение владельца, не этот трек); отчёт по сменам (S6 FINAL — отложен в отдельный read-only slice).

## Минимальная модель (финализировано S-FINAL владельца 2026-10-03)

`nurse_duty_sessions` (рабочее имя; одна новая таблица, additive-only, 0071/0072/0073 не трогаются):

- `id` PK; `user_id` FK `users.id` (NO ACTION — конвенция 0008/0054: удаление пользователя с живой историей смен запрещено); `queue_resource_id` FK `queue_resources.id` (NO ACTION; QueueResource остаётся справочником без человеческих полей; **QueueResource.id остаётся identity axis** — S7 FINAL).
- `effective_cabinet_snapshot` String(20) nullable — снапшот `assignment.cabinet_override ?? QueueResource.default_cabinet` НА МОМЕНТ открытия смены (прецедент routing-snapshot **0073**; исторический факт не переписывается живыми настройками назначения/справочника — S7 FINAL).
- `started_at` TZ; `close_requested_at` TZ nullable; `ended_at` TZ nullable; `status` CHECK (`active` | `closing` | `closed`) (S3 FINAL). `close_requested_at` разделяет момент ухода («попросили закрыться») от момента фактического завершения drain (`ended_at`) — не смешивать.
- Инвариант по S2 FINAL: **partial UNIQUE на `(user_id)` WHERE `status IN ('active','closing')`** — не более одной незакрытой смены на медсестру вообще. Assignments остаются МНОЖЕСТВЕННЫМИ (одна медсестра может иметь права на procedures + ecg и т.д.) — duty-session отвечает на вопрос «где она фактически работает сейчас». Несколько разных медсестёр могут ОДНОВРЕМЕННО иметь смены на одном QueueResource. PG-only DDL в миграции (прецедент 0065/0071/0072), RLS по образцу 0071/0072.
- **Binding-связь work→session (уточнение round-2, P1):** два additive nullable FK-столбца `duty_session_id` → `nurse_duty_sessions.id` (NO ACTION — строки смен иммутабельны и не удаляются) в существующих таблицах `queue_entries` (модель `OnlineQueueEntry`) и `service_executions`; прецедент 0073 — additive attribution-колонки в `service_executions`. Остальные существующие таблицы не трогаются; никакой связи с `ScheduleTemplate`; роль/гранты не меняются. Правила проставления — раздел «Canonical work→session link».
- **Терминальный штамп (уточнение round-4, P2):** ещё два additive nullable TZ-столбца `terminal_at` — в `queue_entries` и `service_executions` (та же миграция, что binding-колонки; прецедент 0073). `terminal_at` = фактический момент терминального перехода, выставляется АТОМАРНО (в транзакции перехода) каждым writer'ом терминального статуса; перезаписывается только следующим терминальным переходом (restore-воскрешение no_show/cancelled → waiting сбрасывает штамп тем же касанием restore-guard'а); читается ТОЛЬКО drain-финализацией (см. «Reconciliation»). Мотив: `updated_at` queue-entries — `default` без `onupdate` (`models/online_queue.py:363`), часть legacy terminal-путей его не выставляет (`api/v1/endpoints/qr_queue/_entries.py:125`/`:251` — `entry.status = "no_show"; db.commit()`), поэтому доказательства фактического момента терминального перехода он не даёт; `served_at`/`completed_at` покрывают только served/completed — no_show/incomplete/cancelled dedicated-колонок не имеют.

## S-FINAL владельца (2026-10-03, trace `1a101f752b14d4b9`) — все семь точек решены

Формулировки S-FINAL сохранены дословно как история design-gate.

- **S1 FINAL — фазировано, выбран вариант (c).** SS-2/SS-3 v1: duty-session = **operational/accounting fact** (учётный факт). N2-3 serving authorization НЕ ужесточается: ACTIVE `NurseWorkplaceAssignment` остаётся текущим data-level gate. Active duty-session НЕ требуется для call/start/execution/terminal в первой фазе. Будущий переход «assignment + active duty-session» — **отдельный owner GO и отдельный runtime slice после production наблюдения**; скрыто в SS-2/SS-3 не включать. Следствие, зафиксированное владельцем: **v1 session не заявляется security boundary.**
- **S2 FINAL — одна текущая станция на медсестру, вариант (a).** Не более одной session со `status active|closing` на `user_id` вообще (partial UNIQUE выше). Assignments множественные; несколько разных медсестёр могут одновременно иметь смены на одном QueueResource. **Implicit auto-switch НЕ вводится:** переход на другую станцию = close текущей → open новой; если старая session draining/closing — новая пока не открывается.
- **S3 FINAL — drain close.** Поля смены: `started_at`, `close_requested_at` nullable, `ended_at` nullable, `status active|closing|closed`. Close без живой работы: `active → closed`, `close_requested_at = now`, `ended_at = now`. Close с живой работой: `active → closing`, `close_requested_at = now`, `ended_at = NULL`. Когда последний live work разрешён: `closing → closed`, `ended_at = now`. Live work учитывается минимум: active queue entry этой медсестры на этой станции (`called` / `in_progress`); in_progress `ServiceExecution`, начатый этой медсестрой и привязанный к этой station/session window. `close_requested_at` нужен, чтобы не смешивать момент ухода со временем завершения drain. Tablet показывает количество незавершённой работы перед close.
- **S4 FINAL — сохранить существующий cross-Nurse completion.** Рекомендация v1 документа (S4a, starter-bound) **ОТКЛОНЕНА владельцем**. Execution НЕ делается starter-bound; существующий контракт N2-3 сохраняется: `execution.started_by_user_id` = медсестра A; медсестра B с ACTIVE assignment на ту же станцию может complete/incomplete этот in_progress execution; `performed_by_user_id` = фактическая медсестра B; стартер A без active assignment сохраняет bounded graceful-drain своего execution; terminal replay остаётся actor-safe/idempotent. **Новый attempt НЕ создаётся только потому, что исполнитель сменился** — это конфликтует с one-active execution invariant 0072; новый attempt создаётся по существующей семантике после terminal incomplete/cancelled retry, а не handover. Если session A находится `closing` и B завершает её execution — этот completion **участвует в разрешении drain session A**. На сценарий добавить regression pins.
- **S5 FINAL — explicit close only, без cron.** Никакого nightly auto-close. Забытая session: `GET current` восстанавливает её; UI показывает длительность/stale warning; перед новой session пользователь обязан явно закрыть старую. Порог warning — UI/config detail, **не DB invariant**; решение о количестве часов не блокирует SS-2.
- **S6 FINAL — отчёт по сменам отложен.** Отчёт НЕ входит в SS-2/SS-3: сначала накапливаются корректные session facts, позже — отдельный read-only reporting slice. Существующий UserAuditLog не дублируется. При этом open/close/revocation session mutations обязаны иметь обычный actor-attributed audit **в той же транзакции**.
- **S7 FINAL — cabinet snapshot.** `effective_cabinet_snapshot = assignment.cabinet_override ?? QueueResource.default_cabinet` на момент открытия session. Исторический факт не переписывается живыми настройками. QueueResource.id остаётся identity axis.

## Canonical work→session link (закрывает P1 round-2 вердикта; обязательная часть SS-2)

Проблема (вердикт round-2): `start_entry` фиксирует состояние СТАНЦИИ, а не personal claim (docstring `nurse_serving_api_service.py:1340`: «The start is the STATION's state, not a personal claim»); после takeover `called_by_user_id` остаётся у вызвавшей медсестры, отдельного `current_serving_user_id`/`session_id` у entry нет. Наивный запрос «live work = user_id + queue_resource_id + active-статус» невозможен: при S1 (сессия не authorization boundary) обслуживание бывает до открытия смены, после `close_requested_at` и вообще без смены — такой запрос ретроактивно смешивает работу вне смены с работой смены.

**Решение — вариант владельца «явный session snapshot/binding»:** принадлежность работы смене устанавливается ТОЛЬКО явным binding-столбцом `duty_session_id`, проставленным В МОМЕНТ действия из состояния «текущая смена исполнителя на этой станции»; никогда не выводится задним числом из user_id/ресурса/временного окна.

- **Столбцы:** `queue_entries.duty_session_id`, `service_executions.duty_session_id` — nullable FK на `nurse_duty_sessions.id` (additive, см. «Минимальную модель»). Для обеих таблиц станция уже известна (`queue_resource_id` — у entry через очередь станции, у execution — колонка 0072/0073), binding меняет только атрибуцию владельца.
- **Write-точки (все — в surface, который SS-2 и так трогает):**
  - `call_next` (`nurse_serving_api_service.py:1282`, `candidate.called_by_user_id = user_id`): entry получает `duty_session_id` = текущая смена вызывающего (active|closing на этой станции) или NULL.
  - `start_entry` (точка handover, `:1340`): entry ПЕРЕПРИВЯЗЫВАЕТСЯ к смене стартера (active|closing) или к NULL, если у стартера смены нет; `called_by_user_id` остаётся историческим фактом. D1 handover: вызвавшая A «отпускает» работу (entry покидает её live work), обслуживающая B «забирает» (entry становится live work смены B). **Обе ветки обязательны (P2 round-3):** rebind выполняется и в переходе called→in_progress, и в уже-in_progress takeover-ветке — ранний идемпотентный return при `entry.status == "in_progress"` (`nurse_serving_api_service.py:1379`) должен идти ПОСЛЕ rebind-логики, не вместо неё (иначе handover-binding никогда не сработает); повторный start владельцем той же смены (entry уже привязан к его текущей смене) — истинный no-op, идемпотентность сохраняется; если rebind снимает последнюю live work с closing-смены предыдущего владельца A — eager-финализация A отдельной транзакцией того же request'а (см. сериализацию выше).
  - старт ServiceExecution (`:1779`, `started_by_user_id=user_id`): execution получает `duty_session_id` смены стартера (active|closing) или NULL; ПОСЛЕ старта binding НЕ перепривязывается никогда — execution остаётся работой смены стартера (S4 FINAL: B завершает execution A → execution terminal → разрешает drain A; `performed_by` = B фиксируется существующей колонкой).
- **Live work смены S** (каноническое определение для S3/drain): ∃ `queue_entries`: `duty_session_id = S` ∧ `status ∈ ('called','in_progress')` (`_ENTRY_ACTIVE_STATES`, `nurse_serving_api_service.py:131`) ∨ ∃ `service_executions`: `duty_session_id = S` ∧ `status = 'in_progress'`.
- **Работа вне смены** (нет смены / смена на другой станции / смена closed): binding = NULL, в НИКАКУЮ смену не попадает — ретроатрибуция исключена by construction. Работа после `close_requested_at` привязывается к `closing`-смене и удерживает drain — drain никогда не недосчитывает работу (консервативная семантика).
- **Drain-разрешение:** терминальный переход привязанной работы (кем бы он ни выполнялся — B завершает за A) уменьшает live work смены-владельца; финализация — eager-проверка на nurse terminal path + reconciliation (раздел ниже). Внешние пути (например, `queue_svc/_helpers.py:staff_skip_queue_entry` — no_show из waiting/called, `:131`) binding не пишут, но терминальный переход привязанной работы совершают — reconciliation закрывает смену без их ведома.
- **Счётчик незавершённой работы перед close (S3 FINAL):** количество live bound work смены — вычислимо надёжно из bindings (то же определение, что у drain, без эвристик).

- **Сериализация binding × lifecycle (закрывает P1 round-3 вердикта; обязательная часть SS-2).** Проблема: canonical lock-order выше покрывает только session-мутации (open/close/deactivate) — serving-путь не обязан блокировать строку смены, поэтому возможен interleaving: смена S active и пока без live work → `call_next` прочитал S → параллельный `close` увидел 0 live work и закоммитил S=closed → `call_next` после этого коммитит `entry.duty_session_id = S`. Итог — closed-смена с live bound work: reconciliation её не исправит (работает только с closing), partial UNIQUE не мешает следующей смене того же пользователя. Тот же race применим к `start_entry` и execution-start. Правило (все три write-точки): транзакция, проставляющая/перепривязывающая `duty_session_id`, обязана в ТОЙ ЖЕ транзакции, в которой фиксируется work transition, взять `SELECT ... FOR UPDATE` строки смены исполнителя (предикат `user_id ∧ queue_resource_id ∧ status IN ('active','closing')`; partial UNIQUE — максимум одна строка) и **перечитать статус после ожидания блокировки**; binding коммитится только при `active|closing`; если за ожидание смена стала `closed`/исчезла — binding = NULL (работа вне смены; S1: сессия не обязательна, 409 не возникает). **Инвариант: ни в одном interleaving не существует закоммиченной live work с `duty_session_id`, указывающим на closed-смену** — закрепляется PG-пинами T6 (bind × close) и T7 (bind × revoke). Lock-order serving-пути: строка активного assignment (authorization-guard `FOR UPDATE`, первый шаг транзакции — P1 round-4, раздел revocation) → существующие блокировки пути (queue/entry/execution `with_for_update()` — `call_next` `:1216`/`:1273`, `start_entry` `:1369` до early-return, execution-start) → затем строка смены; session-мутации НЕ берут entry-класс блокировок после строки смены (live-work проверки — plain SELECT: решение принимается под FOR UPDATE строки смены, а все писатели binding/терминальных переходов держат её блокировку до коммита) — порядок ацикличен и закрепляется PG-пином. Rebind-путь трогает ровно ОДНУ строку смены (свою); eager-финализация предыдущей closing-смены A при снятии последней live work — ОТДЕЛЬНОЙ транзакцией в том же request'е сразу после коммита rebind (порядок reconciliation ниже; при краше между транзакциями — обычный self-healing) — это исключает cross-session lock-циклы двух одновременных handover'ов. **Restore-guard (тот же класс инварианта):** `restore_entry_to_next` (`qr_queue/_entries.py:17`, no_show/cancelled → waiting) может воскресить привязанную работу после закрытия смены; SS-2 добавляет guarded-шаг: если `duty_session_id` указывает на смену не в (active, closing) → binding = NULL (работа покидает смену; ретроатрибуция назад запрещена). Это единственное касание legacy-пути — он не становится session-aware (drain-семантика не меняется), только защищает инвариант.

## Reconciliation — authoritative self-healing (закрывает P2 round-2 вердикта)

Инвариант: **closing-смена обязана достичь `closed` без участия внешних queue-эндпоинтов** — ни один legacy путь (admin/doctor/registrar: `queue_svc/*`, doctor lifecycle и т.п.) не обязан знать о `nurse_duty_sessions`. Гарантия обеспечивается на session-surface:

- **Reconciliation-правило (только mutation-пути; P2 round-3):** `POST /sessions` (open) и `POST /sessions/close` начинают с идемпотентной сверки: если смена пользователя в `closing` и live bound work (каноническое определение выше) пуста → атомарно финализировать `closed` (`ended_at` — по контракту ниже: момент фактического исчезновения последней live bound work, не время сверки) в той же транзакции (FOR UPDATE строки смены + re-check; повторный вызов — no-op).
- **GET /sessions/current — строго read-only (P2 round-3; выбор владельца: «не превращать безопасный GET в скрытую мутацию»).** `get_db()` (`backend/app/db/session.py:213`) делает только `yield db; finally: db.close()` — автоматического commit НЕТ: ORM-изменение в GET молча откатилось бы при закрытии Session, и «восстановление» имело бы неопределённую transaction boundary. GET выполняет только SELECT (ни ORM-мутации, ни flush/commit); restore-семантика S5 FINAL = чтение server state, не запись. Durable reconciliation — только на mutation-путях: POST open (порядок выше), POST close, eager-финализация на serving mutation-путях (terminal path + rebind-handover).
- **Контракт `ended_at` (P2 round-3):** `ended_at` = момент фактического исчезновения последней live bound work, НЕ время финализации. S3 FINAL («ended_at = now») описывает синхронное разрешение drain — там now совпадает с фактом. При отложенном разрешении (внешние admin/doctor/registrar пути терминалят последнюю привязанную работу, о сменах не зная — пример владельца: работа кончилась в 18:05, медсестра обратилась к session-surface в 20:00 → «ended_at = 20:00 вместо 18:05» портит именно тот operational/accounting fact, ради которого вводится capability) финализация вычисляет факт: max(`terminal_at` привязанных записей) — доказуемый терминальный штамп (P2 round-4). `queue_entries.terminal_at` / `service_executions.terminal_at` — dedicated additive-колонки (см. «Минимальную модель»), выставляемые атомарно каждым writer'ом терминального статуса; полный перечисленный набор writer'ов — обязательный аудит SS-2 (repo-wide grep по writer'ам статусов на момент среза; перечисление по main `d397656`): nurse serving `nurse_serving_api_service.py` (served `:2089`, no_show `:2349`, incomplete `:2426`), legacy `api/v1/endpoints/qr_queue/_entries.py` (`:125` no_show, `:251` incomplete), `services/queue_svc/_helpers.py` (`:148` no_show, `:213` cancelled), doctor `api/v1/endpoints/doctor_integration/_queue_ops.py` (`:1136` served), `services/online_queue_new_service.py` (`:113`/`:131` cancelled), `services/batch_patient_service.py` (`:319` cancelled, `:409` action.status), `services/force_majeure_service.py` (`:201`/`:301` cancelled), generic `repositories/online_queue_new_repository.py:20`; `rescheduled` не терминальный (`_ENTRY_TERMINAL_STATES` `nurse_serving_api_service.py:132` — served|incomplete|no_show|cancelled). **Реконструкция из `updated_at`/`served_at` запрещена** (P2 round-4): `updated_at` — `default` без `onupdate` (`online_queue.py:363`), legacy-пути его не выставляют — пример вердикта: entry создан 17:30, терминальный переход 18:05 через `qr_queue/_entries.py` → `updated_at` остаётся 17:30, реконструкция дала бы ложный ended_at; `served_at`/`completed_at` покрывают только served/completed и остаются нетронутыми существующими семантиками. Явный `POST /sessions/close` без live work остаётся S3-семантикой (`ended_at = now` — авторитетное объявление конца смены владельцем смены, это не reconciliation). Fallback (у терминальной строки нет `terminal_at` — премиграционные строки/пропущенный writer, аномалия данных): `ended_at` = время финализации + audit-note о fallback — никакой реконструкции из `updated_at` (P2 round-4).
- **Порядок в open:** user-lock → reconciliation своих closing-смен → uniqueness-проверка → insert — «застрявшая» closing-смена не может блокировать новую смену (partial UNIQUE перестаёт действовать после финализации).
- **Eager-финализация:** nurse terminal path (complete/incomplete/no-show операции nurse-serving) после терминального перехода привязанной работы проверяет смену-ВЛАДЕЛЬЦА binding'а (не актора!) и финализирует её при пустом live work. То же — на rebind-пути handover (снятие последней live work с closing-смены предыдущего владельца; отдельная транзакция того же request'а — см. «Сериализация binding × lifecycle»).
- **Поверхности SS-2 сознательно НЕ расширяются** на legacy queue endpoints в части session-логики (решение владельца round-2: «не обязательно менять все старые queue endpoints» — legacy пути не становятся session-aware и о сменах не знают). Единственное исключение — one-line терминальный штамп `terminal_at = now()` в перечисленных terminal-writer'ах (опция 1 вердикта round-4: «SS-2 обновляет все terminal paths, способные завершить bound queue-entry»): без него отложенная финализация не может доказать фактический момент исчезновения live work при терминальном переходе на legacy-пути (пример вердикта: admin no_show в 18:05 → reconciliation в 20:00).

## Assignment revocation × session lifecycle (обязательная часть SS-2; закрывает Codex P2 #3569)

Вердикт владельца: координация revocation — **не отдельный поздний PR, а integrity contract самой session capability**; входит в срез SS-2.

- **Точный предикат (исправление round-2):** деактивация assignment затрагивает смену ТОЛЬКО при `session.user_id == assignment.user_id AND session.queue_resource_id == assignment.queue_resource_id` — никогда «любую active-смену медсестры». Сценарий D2/S2 (одна медсестра: assignment procedures + assignment ecg, текущая смена на procedures): деактивация ecg НЕ трогает procedures-смену — её assignment никто не отзывал.
- **Negative PG pin:** деактивация ДРУГОГО assignment той же медсестры не меняет текущую duty-session (обязательный тест среза).
- Open-session и deactivate-assignment сериализуются на одной строке `NurseWorkplaceAssignment` (FOR UPDATE этой строки ДО любого чтения/записи состояния смены в обоих путях; serving-путь берёт ту же строку первым шагом — authorization guard ниже, P1 round-4); полный canonical lock order — раздел Concurrency (session-мутации: user-row → assignment-row → session-row; serving: assignment-row → path-locks → session-row), определён один раз и закреплён PG-тестом.
- Деактивация assignment выполняется **в той же транзакции**: (1) assignment → inactive; (2) если существует duty-session с предикатом выше в статусе active|closing: нет live work → session `closed`; есть live work → session `closing` (drain-семантика S3 FINAL).
- **Нельзя оставлять ACTIVE session на revoked assignment ЕЁ станции** — ни в одном interleaving.
- Проверяются **ОБА interleaving**: «open wins first» (open закоммитился первым → деактивация в своей транзакции деактивирует assignment и закрывает/дренит смену) и «deactivate wins first» (деактивация первая → open получает отказ 403, ноль orphan-строк).
- Поверхность деактивации (`NurseWorkplaceApiService.deactivate_assignment`, `backend/app/services/nurse_workplace_api_service.py`) входит в SS-2 test surface; T3 PG-сьюта — канонический пин.
- **Authorization guard serving-мутаций (закрывает P1 round-4; assignment остаётся security boundary).** Текущий `_active_assignment_or_error()` (`nurse_serving_api_service.py:187`) — plain SELECT (`user_id ∧ queue_resource_id ∧ is_active`) без `FOR UPDATE` и без повторной проверки перед commit: guard прошёл → `deactivate_assignment` закоммичен → serving-мутация всё равно коммитится как «работа вне смены» (правило bind × close корректно даст binding = NULL, но queue/execution-мутация произойдёт). TOCTOU на единственной настоящей authorization boundary нарушает authorization contract (S1: session не security boundary, assignment — да). Правило: каждая serving-транзакция, меняющая work-state на основе assignment, берёт `SELECT ... FOR UPDATE` строки активного assignment как ПЕРВЫЙ шаг (до любых queue/entry/execution/session-блокировок и до любой мутации) и решает авторизацию по re-read под этой блокировкой; если после ожидания assignment уже отозван → 403 и НОЛЬ queue/execution-мутаций. PG-пин линеаризации (canonical): `serving прошёл initial check || admin revoke commits || serving reaches guarded mutation` → исход: либо serving линеаризован ДО revoke (guard держит строку assignment до коммита — revoke ждёт и коммитится после serving), либо serving = 403 ПОСЛЕ revoke. НИКОГДА: revocation committed first И serving mutation committed afterwards.
- **Классификация guarded путей (по основанию авторизации):** (a) жёсткий guard — assignment единственная основа авторизации: `call_next` (`:1207`), `start_entry` (`:1359`), `create_execution` (`:1610`), entry-level terminals `_terminal_entry` → `mark_entry_no_show`/`mark_entry_incomplete` (`:2282`, assignment требуется безусловно) — три примера вердикта («вызвать/начать/создать execution») покрыты здесь; (b) условный guard — execution-level terminals `complete_execution`/`incomplete_execution` (`_authorize_execution_terminal` `:1980`): линеаризованный re-read assignment под блокировкой ПЕРЕД мутацией; исход под блокировкой: `active` → полная авторизация (cross-Nurse completion S4 в силе); `inactive` → документированный graceful-drain (стартер завершает СВОЙ in_progress execution — основа авторизации starter-ownership, иммутабельный факт, а не отзывываемый грант; семантика N2-3/N2-5 drain-recovery сохранена) либо 403 не-стартеру — тем самым закрывается тот же TOCTOU (B завершает execution A после отзыва СВОЕГО assignment), не ломая graceful drain; (c) read-пути (`get_station_state` `:1081`, `list_workplaces`, `list_draining_executions`) — plain SELECT без блокировок. Реализация: `with_for_update()` в существующем guard-запросе (call-sites — первые операторы методов, до queue-lock `:1216`/entry-lock `:1369`) + тот же примитив в дублирующем plain-SELECT `_authorize_execution_terminal` (`:1997`) — единая точка линеаризации; 403-семантика ошибки сохраняется.
- **Ацикличность (round-4):** обе семьи путей берут строку assignment ДО любых queue/entry/execution/session-блокировок (session-мутации: user-row → assignment-row → session-row; serving: assignment-row → path-locks → session-row) и никто не берёт assignment-row при удержанных entry/session-блокировках — полный порядок ацикличен, закрепляется тем же PG-пином lock-order.

## API-surface sketch (по S-FINAL; все операции assignment-scoped, та же цепочка авторизации N2-3)

- `POST /api/v1/nurse/serving/sessions` — открыть смену на станции активного назначения; double-tap = идемпотентно 200 (та же строка); при уже открытой active-смене на другой станции → 409 (требуется явный close → open; **implicit auto-switch отсутствует** — S2 FINAL); если существующая смена в `closing`/draining — новая пока не открывается (409).
- `GET /api/v1/nurse/serving/sessions/current` — restore-путь планшета (reload = server state SSOT, §4/§8 N2-5); восстанавливает и забытую открытую смену (S5 FINAL). **Read-only (P2 round-3):** только SELECT — ни ORM-мутации, ни commit; durable-финализация застрявшей closing — на POST open/close (см. Reconciliation).
- `POST /api/v1/nurse/serving/sessions/close` — S3-семантика (200 closed / 202 closing-drain с количеством live bound work).
- Reconciliation (раздел выше) — неявная часть mutation-операций: open / close начинают с идемпотентной финализации своих `closing`-смен без live bound work.
- Board payload: + read-only саммари «кто на дежурстве сейчас» (additive поле; PHI-гигиена §11 — только имена пользователей-медсестёр, без контактов); перед close — количество незавершённой работы смены (live bound work, S3 FINAL).

## Concurrency-proof sketch (§6-стиль; обязательный PG-сьют среза SS-2)

- **Canonical lock order (определён один раз, закреплён PG-тестом; уточнение round-2):** (1) строка `users` владельца смены — сериализует ВСЕ мутации смен одного пользователя, включая open на разных станциях (round-1 вердикт «FOR UPDATE assignment FIRST» сохранён по смыслу: строка assignment берётся до любого чтения/записи состояния смены; user-row добавлен этапом 1 по прямому авторизованию round-2 «общий user-level lock либо корректное перехватывание unique-conflict»); (2) строка `NurseWorkplaceAssignment`; (3) строка `nurse_duty_sessions`. Все session-мутации (open/close/deactivate-координация) берут блокировки строго в этом порядке и держат до коммита. Defense-in-depth: перехват unique-conflict на insert — IntegrityError → rollback → re-read → контролируемый 409 (никогда не 500). **Serving/binding-транзакции (round-3 P1 + round-4 P1):** строка активного assignment `FOR UPDATE` (authorization guard, первый шаг — линеаризация с revoke, раздел revocation) → существующие блокировки пути (queue/entry/execution `with_for_update()`) → строка смены `FOR UPDATE` + re-read статуса после ожидания (допустимо только `active|closing`, иначе binding = NULL); session-мутации не берут entry-класс блокировок после строки смены — полный порядок ацикличен, закрепляется PG-пином; eager-финализация чужой смены — отдельной транзакцией того же request'а (никогда две строки смен в одной транзакции).
- T1: две медсестры открывают смены на одной станции — обе succeed (S2 FINAL: несколько медсестёр на одном QueueResource допустимо), partial UNIQUE на `user_id` держится.
- T2: double-tap «открыть смену» — идемпотентно, ровно одна строка.
- **T2b (новый, round-2):** та же медсестра, два разных QueueResource (procedures/ecg), конкурентный open → ровно одна смена; проигравший получает детерминированный 409 (никаких IntegrityError/500: user-row lock сериализует, unique-conflict перехват — страховка).
- T3: гонка open × deactivate-assignment — сериализация на строке assignment (этап 2 lock order); **оба interleaving**: open wins first → деактивация в той же транзакции деактивирует assignment и переводит смену в `closed` (нет live work) / `closing` (есть live work); deactivate wins first → open = 403, ноль orphan-строк. Предикат строго парный (`user_id ∧ queue_resource_id`); **negative pin:** деактивация ecg-assignment не трогает procedures-смену.
- T4: close-drain × параллельное разрешение последнего live work (включая внешние пути) — `closing→closed` ровно один раз; last-resolver ставит `ended_at` = моменту фактического исчезновения последней live bound work (контракт ended_at: при синхронном разрешении совпадает с now; отложенная финализация НЕ подменяет факт временем сверки и читает ТОЛЬКО `terminal_at` привязанных записей — P2 round-4, реконструкция из `updated_at` запрещена; обязательный кейс: внешний legacy no_show привязанной entry → `terminal_at` установлен в транзакции перехода → `ended_at` = штамп, не время финализации); reconciliation × параллельный терминальный переход привязанной работы — без двойной финализации (FOR UPDATE + re-check).
- T5: cross-Nurse completion в drain: смена A `closing`, медсестра B (ACTIVE assignment на той же станции) завершает execution стартера A (binding которого указывает на смену A) — completion участвует в разрешении drain A (S4 FINAL); плюс switch-гонка (close+open на B, пока коллега клеймит на A) — факты станции A стабильны, `FOR UPDATE` по образцу call-next.
- **T6 (round-3): bind × close** — каждая из трёх write-точек (call_next/start_entry/execution-start) конкурентно с close/reconciliation: ни в одном interleaving не существует закоммиченной live work с `duty_session_id`, указывающим на closed-смену; bind после ожидания блокировки видит `active|closing` (привязывает) либо `closed`/отсутствие (binding = NULL); close либо видит новую работу и дренит, либо не видит и закрывается.
- **T7 (round-3; расширен round-4): bind × revoke × serving-guard** — binding-путь конкурентно с `deactivate_assignment` (парный предикат): bind после revoke видит `closing` (привязывает, держит drain) или `closed`/отсутствие (NULL); revoke после bind видит новую live работу и дренит; деактивация ecg не трогает procedures-смену (negative pin T3). Плюс authorization-контракт (P1 round-4) на всех guarded путях: revoke закоммичен до захвата guard-строки → serving = 403 и НОЛЬ queue/execution-мутаций (execution-terminal не-стартера = 403; стартер уходит в задокументированный graceful-drain); serving захватил guard-строку первым → revoke ждёт и коммитится после serving; НИКОГДА «revoke закоммичен первым И serving-мутация закоммичена после» (обязательный асимметричный пин на каждой guarded операции).
- **T8 (round-3): restore × closed-binding** — `restore_entry_to_next` записи, чей `duty_session_id` указывает на смену не в (active, closing) → binding = NULL; смены в active|closing restore не трогает.

## Acceptance criteria (по S-FINAL; финальная формулировка за владельцем на SS-2 review)

- Медсестра со своего аккаунта открывает смену ТОЛЬКО на станции активного назначения; повтор = идемпотентно; все операции атрибутируются реальному User.
- Смена v1 НЕ выдаёт НИКАКИХ грантов и НЕ является security boundary (S1 FINAL): denial-матрица N2-3 не меняется вообще (регрессионный пин); active duty-session не требуется для call/start/execution/terminal.
- Вторая смена того же user при active/closing существующей — 409 (partial UNIQUE по S2 FINAL); implicit auto-switch отсутствует; переход = явный close → open; при draining новая смена не открывается.
- Принадлежность работы смене (P1 round-2) — ТОЛЬКО action-time binding (`duty_session_id` на `queue_entries`/`service_executions`, проставленный в момент call_next/start_entry/execution-start); никакой ретроатрибуции из user_id+ресурса+окна (регрессионный пин: работа без смены/до открытия не попадает ни в какую смену; работа после close_requested_at привязывается к closing-смене и удерживает drain).
- **Сериализация binding × lifecycle (P1 round-3):** binding коммитится только при `active|closing` после session `FOR UPDATE` + re-read в той же транзакции work transition; ни одна live work не остаётся привязанной к closed-смене ни в одном interleaving (пины T6 bind × close, T7 bind × revoke, T8 restore-guard).
- Close без живой работы → `closed` немедленно (`close_requested_at = ended_at = now`); с живой работой → `closing`, `ended_at` ставит last-resolver последнего live bound work; `close_requested_at` ≠ `ended_at` при drain (S3 FINAL); tablet показывает счётчик live bound work перед close. **ended_at-контракт (P2 round-3, уточнён round-4):** при отложенной финализации `ended_at` = момент фактического исчезновения последней live bound work — max(`terminal_at` привязанных записей); `terminal_at` выставляется атомарно каждым terminal-writer (включая legacy `qr_queue`/`queue_svc`/doctor/cancel-пути — опция 1 round-4), restore-воскрешение сбрасывает штамп; реконструкция из `updated_at`/`served_at` запрещена (`updated_at` — default без onupdate, legacy-пути не выставляют) — обязательный тест: внешний терминальный переход (legacy no_show) в T1, финализация в T2 > T1 → `terminal_at` = T1, `ended_at` = T1, не T2; явный close без работы — S3-семантика (`ended_at = now`).
- Handover-привязка: `start_entry` B перепривязывает entry к смене B (или NULL без смены); `called_by_user_id` A остаётся историческим фактом; execution binding не перепривязывается никогда. Rebind обязателен в ОБЕИХ ветках start_entry — включая уже-in_progress takeover-путь ДО раннего идемпотентного return (`nurse_serving_api_service.py:1379`, P2 round-3); повторный start владельцем той же смены — no-op; снятие последней live work с closing-смены A → eager-финализация A отдельной транзакцией того же request'а.
- Cross-Nurse completion сохранён (S4 FINAL): B с ACTIVE assignment на той же станции complete/incomplete in_progress execution стартера A; `performed_by` = B; новый attempt при handover НЕ создаётся (one-active 0072 не рвётся); terminal replay actor-safe/idempotent; completion B разрешает drain closing-смены A; regression pins на сценарий.
- Revocation-координация: нет ACTIVE-смены на деактивированном assignment ЕЁ пары (user_id ∧ queue_resource_id); деактивация другого assignment (ecg при procedures-смене) смену НЕ трогает (negative PG pin); сериализация user-row → assignment-row, canonical lock order закреплён PG-тестом, оба interleaving покрыты. **Authorization guard (P1 round-4):** каждая work-state serving-мутация берёт строку активного assignment `FOR UPDATE` первым шагом и решает авторизацию re-read'ом под блокировкой; после закоммиченного revoke — 403 и ноль queue/execution-мутаций (execution-terminal не-стартера); graceful-drain стартера сохранён (основа — starter-ownership, N2-3/N2-5 семантика); асимметричный пин: никогда «revoke закоммичен первым И serving-мутация закоммичена после».
- Open-гонки: конкурентный open одной медсестрой на разных станциях (T2b) — ровно одна смена, проигравший получает детерминированный 409, ноль 500.
- Self-healing: closing-смена финализируется reconciliation'ом на mutation-путях (POST open/close + eager на serving mutation-путях) при пустом live bound work; **GET current строго read-only** — обязательный тест: GET не меняет состояние и не коммитит (P2 round-3); reconciliation-запись переживает закрытие Session (тест fresh-session persistence — `get_db()` без auto-commit); внешний терминальный переход (staff no_show и т.п.) не оставляет смену застрявшей — обязательный тест: closing-смена + внешний no_show привязанной called-entry → следующая open успешна.
- Отчёт по сменам в SS-2/SS-3 отсутствует (S6 FINAL); open/close/revocation мутации смены имеют actor-attributed audit в той же транзакции; UserAuditLog не дублируется.
- Reload планшета восстанавливает смену из server state (`GET current`), включая забытую открытую (S5 FINAL); localStorage не несёт состояния смены (§4/§8 прецедент); stale warning — UI/config, без DB-инварианта.
- `effective_cabinet_snapshot` зафиксирован на open по формуле S7 FINAL и не переписывается живыми настройками.
- PG-сьют T1–T5 зелёный на CI; SQLite-пути (create_all conftest) не ломаются (PG-only DDL вне `__table_args__`).
