# Приемка исправлений регистратуры

[План](../codex-registrar-queue-remediation-plan.md) · [Прогресс](PROGRESS.md) · [Команды и среда](CLOUD-START.md)

Сценарии — критерии, а не утверждение о проведенной проверке. Результаты PASS/FAIL/NOT_RUN/BLOCKED записывать в E-NNN в PROGRESS с S-ID и tested HEAD. Не дублировать изменяемый статус в этом файле.

## Обязательные условия

- Только disposable dev/test/staging с подтвержденными адресами. Порты сами по себе не подтверждают безопасность среды.
- Данные — canonical synthetic_seed.py/dev_seed.py по AGENTS, с SYNTHETIC-/DEV-DEMO маркером; не переносить production. В unit fixtures использовать явно синтетические значения без реалистичных персональных связок.
- Для идентификации пациента в evidence достаточно внутреннего синтетического ID; не сохранять телефоны, ФИО, диагнозы, QR-токены и чувствительные URL.
- UI MOCK и REAL_API маркируются отдельно. SQLite unit/integration не заменяет PostgreSQL-проверки.
- В каждом evidence: роль, подготовка, действие, ожидаемый/фактический результат, инструмент, SHA, команды, artifact, пропущенная часть.
- Сценарий, требующий D-решения, не выполнять на самовольно выбранном поведении. Допустимо сначала зафиксировать нынешнее поведение как characterization, не как приемку будущей модели.
- Если сценарий обнаруживает новый дефект, зарегистрировать RQ-NN.x у владельца потока и пересмотреть зависимые критерии. Не чинить «заодно» в чужом срезе.

## Дополнительная обязательная проверка RQ-04

Она вынесена отдельно, чтобы atomicity не потерялась внутри пользовательского сценария создания направления S-14:

1. Успешный POST create department создает ровно по одной строке queue settings / registration settings.
2. Ошибка после подготовки зависимых записей откатывает Department и все новые связанные строки; недостаточно проверить HTTP-ответ.
3. Повтор после ошибки проходит предсказуемо, без «ключ уже занят» от частично закоммиченного Department.
4. Повтор существующего ключа возвращает согласованный конфликт и не создает новые зависимости.
5. Реальные UNIQUE/transaction ограничения проверены на одноразовом PostgreSQL с Alembic schema.
6. Создаваемая default consultation не имеет случайных requires_doctor/queue_tag/category/price; значения сверены с действующим контрактом, а не изменены по догадке.

## Сквозная приемка RQ-29

Минимальный путь проверяется в реальном disposable backend и браузере после выполнения узких задач:

1. Администратор подключает врача имеющейся специальности, затем новое поддерживаемое направление и ресурс без врача.
2. Добавляет услуги, состав и понятное представление. Возвращается к редактированию, исправляет обязательную связь.
3. Регистратор находит пациента, открывает мастер из «Все» и из конкретной вкладки.
4. Пациент получает QR выбранного поддерживаемого направления и записывается. Один дополнительный выбор отказывает — частичный результат виден.
5. Запись появляется у правильного исполнителя; другой врач/пациент не получает лишних данных или прав.
6. Номер/кабинет и состояние согласованы между регистратурой, пациентом и табло; lab/cashier получают свои виды работы.
7. Повтор команды, сетевой сбой и другая сессия не теряют пациента, ввод или успешный результат.
8. Архивирование/закрытие направления сообщает последствия и сохраняет историю/текущую очередь.
9. Выполнена поддерживаемая частичная отмена/оплата без потери остальных назначений.
10. Те же основные действия доступны клавиатурой и при 375/768/1280/1920 px; проверены длинные названия и локали интерфейса.

Это дополняет S-01…S-28, а не заменяет их одним happy-path screenshot. Существующие mock e2e specs полезны, но сами по себе этот раздел не закрывают.

## Что означает завершение

- RQ-02…RQ-28 закрыты результатом или доказанной эквивалентной реализацией. DEFERRED_BY_OWNER перечислены как оставшийся согласованный объем, не как исправленные дефекты.
- Все обязательные сценарии текущего согласованного объема прошли на записанном финальном содержимом.
- Для очередности/транзакций/миграций есть реальное PostgreSQL evidence; для пользователя — браузер; для межпанельного пути — REAL_API/WebSocket.
- RQ-30 содержит отдельную таблицу staging runbook. Ее NOT_RUN не превращается в PASS от зеленого CI.
- Production rollout — отдельное действие вне этого плана; формулировки «система проверена»/«деплой завершен» регулируются AGENTS и требуют всех 10 проверок.
