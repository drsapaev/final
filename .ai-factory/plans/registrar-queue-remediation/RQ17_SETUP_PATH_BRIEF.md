## 2. Проблема (F-15/F-24) и baseline переходов

Сегодня путь «подключить новое направление» физически разбросан по трём сайдбар-разделам из разных секций меню (`nav.system` → `nav.section_patients_booking` → `nav.section_clinic_queue`) плюс настройки и QR вне админ-контура, и ни один экран не показывает, что уже сделано, а что ещё обязательно. Минимальный корректный путь нового направления сегодня (последовательность открытий меню/страниц, без учёта возвратов и ошибок):

1. `/admin/users` — создать `User(role=Doctor)` + профиль (специальность берётся из каталога);
2. `/admin/doctors` — убедиться/создать запись Doctor (второй экран, второй модальный слой);
3. `/admin/services` (таб catalog) — создать услугу, выбрать `queue_tag`;
4. `/admin/services` (таб queue-profiles) — создать профиль, если тега ещё нет (порядок 3↔4 циклический: тег берётся из профилей, профиль описывает отображение);
5. «где QR?» — ответа в админ-контуре нет: provision-эндпоинт существует, но UI нулевой (`grep provision` по `frontend/src` вне generated — 0 вхождений), постоянный `/q/<public_code>` — RQ-18.

Baseline: **≥ 4 admin-раздела, 5+ экранов, 2 циклических зависимости (тег↔профиль), 0 индикаторов готовности**, технические ключи (`queue_tag`, `department_key`, `profile_key`) фигурируют в формах как обязательное знание пользователя. Это и есть F-15/F-24.

## 3. Собранный путь (target shape): «исполнитель → услуги → отображение → проверка → QR»

Путь собирается из существующих экранов поверх уже принятых решений:

- **Исполнитель** (D-01: doctor-owned `День + Doctor.id + канонический queue_tag` ИЛИ resource-owned `День + QueueResource.id`): User(role=Doctor)+профиль → Doctor-запись (существующий onboarding, второго мастера нет). Для resource-owned — QueueResource уже справочник (NURSE-V2 не нужен для RQ-17; не пересекаемся).
- **Услуги**: `ServiceCatalog` — услуга с `queue_tag` из существующих профилей; `requires_doctor`/`department_key` синхронизируются из контракта профиля (уже реализовано, RQ-06).
- **Отображение**: `QueueProfilesManager` — профиль (`queue_tags[]`, `show_on_qr_page`, департамент, кабинет/цвет/иконка). Профиль-обзор ≠ отдельная очередь (D-01: «QueueProfile — представление/направление, не ресурс-владелец»; «Обзор нескольких очередей не создаёт собственной нумерации»).
- **Проверка (готовность)**: проверяемые связи шага — (а) Doctor-запись активна и принадлежит specialty; (б) ≥1 активная услуга с этим `queue_tag`; (в) активный QueueProfile владеет тегом; (г) профиль visible (`show_on_qr_page`); (д) provision-статус постоянного адреса (D-03: provision идемпотентен, переименование не меняет адрес). Всё выводится из существующих API: `/services`, `/queues/profiles?active_only=false`, `/services/admin/doctors`, provision-GET/POST — ни одного нового бэкенд-контракта не требуется.
- **QR**: выдача/показ/скачивание постоянного `/q/<public_code>` — **RQ-18** (готовый бэкенд RQ-16.d: provision + анонимный start-session). RQ-17 останавливается на provision-статусе и явном указании «QR появится здесь после RQ-18» — не дублируем и не опережаем.

## 4. Экран-вход (shape, реализация — следующий срез)

Один новый admin-route (кандидат: `/admin/setup-directions`, id `admin-setup-directions`, секция `nav.section_clinic_queue`; точное место — по текущей навигации), который:

1. показывает **checklist готовности направлений** по профиль/тег-строкам: шаги §3 (а)–(д) со статусами «готово / не хватает X / где исправить» — каждая «не хватает» ведёт прямой ссылкой в СУЩЕСТВУЮЩИЙ экран и открывает соответствующую форму (без дублирования CRUD);
2. начинает **мастер нового направления** S-14 с пустой формы: последовательность §3, каждый шаг = переход в существующий экран с возвратом на checklist (никаких новых форм-дублей; сохранение/возврат/ошибка шага/повтор — обязательные состояния);
3. не требует технических ключей: `queue_tag`/`profile_key`/`department_key` в UI пути не вводятся руками — выбор из существующих значений, синхронизации уже реализованы (RQ-06);
4. после RQ-18 покажет колонку QR (provision → «Показать/скачать QR») — точка расширения зашита, но не реализуется в RQ-17.

Чего экран НЕ делает: не редактирует данные сам (только ссылки/статусы), не создаёт вторую систему справочников, не меняет существующие маршруты/сайдбар (одна новая запись в реестре), не трогает owner-модель D-01.

## 5. Проверка среза (из плана §RQ-17)

- **S-14** (`ACCEPTANCE.md:34`): новая specialty или существующая; новый врач/ресурс; синтетическая услуга → пройти предлагаемую настройку с пустой формы до статуса готовности; видны обязательные связи и ошибки; нет второго onboarding; профиль-обзор отличается от отдельной очереди; нет необходимости редактировать код. Admin browser + REAL_API. (Department-atomicity RQ-04 — отдельная обязательная проверка вне S-14, `ACCEPTANCE.md:52-59`.)
- **Число переходов до/после**: baseline §2 (≥4 раздела, 5+ экранов, 0 индикаторов) → после: 1 вход + переходы только на существующие экраны; каждый шаг показывает, что осталось.
- **Состояния шага**: сохранение / возврат / ошибка шага / повтор — каждое не теряет прогресс checklist (статус всегда пересчитывается из API, не хранится локально).
- **Ноль технических ключей** как обязательного знания пользователя — фиксируется тестом-пином на тексты форм пути.
