# Контракт направления записи (RQ-16) — согласованная редакция

**Статус:** СОГЛАСОВАН как производный документ — «первое касание» RQ-16 по плану (§RQ-16: «Первое касание: согласованное описание контракта в этом плане/PROGRESS»).
**Источники согласования (приоритет в порядке убывания):**
1. Решение владельца продукта от 2026-09-15 — D-01/D-02/D-03/D-04 APPROVED в уточнённой редакции ([DECISION_PROPOSALS.md](DECISION_PROPOSALS.md) §«Решение владельца», E-039, PR #3266 merged `b165aaf0f`);
2. ADR-001 — Queue Ownership & Specialty Architecture (Accepted; amended QD-2A dual-owner; уточнения stage C #3114, stage D #3191, stage E #3250);
3. Основной план ([codex-registrar-queue-remediation-plan.md](../codex-registrar-queue-remediation-plan.md)) §RQ-16 и сценарии S-14/S-15 ([ACCEPTANCE.md](ACCEPTANCE.md)).

**Назначение:** единый SSOT-контракт «адресуемого направления записи» для последующих дочерних срезов RQ-16.b (контракт/API), RQ-16.c (модель, при необходимости) и RQ-16.d (runtime). Контракт фиксирует текущее согласованное поведение и вытекающие из APPROVED-решений обязательства; он НЕ является runtime-реализацией и не отменяет gate/fail-first/PG-доказательства каждого среза.

**Что документ НЕ делает:** не добавляет новых продуктовых решений сверх APPROVED-редакции; не трогает код/схему; completion задач не повышает; пункты, помеченные «ОТКРЫТАЯ ТОЧКА», требуют либо решения в отдельном срезе по своим правилам, либо подтверждения владельцем.

## 1. Термины и пространства идентичности

| Термин | Значение | Пространство идентичности |
|---|---|---|
| **Владелец очереди** | Сущность, которой принадлежит дневная очередь: врач (`Doctor`) или ресурс (`QueueResource`) | `doctors.id` и `queue_resources.id` — РАЗНЫЕ пространства |
| **Направление (direction)** | Настраиваемая точка записи: набор услуг + владелец + представление + публичная доступность | Не имеет собственного числового пространства, пересекающегося с владельцами |
| **Представление (QueueProfile)** | Вкладка/представление регистратуры и публичного QR: `key`, `title*`, `queue_tags`, `department_key`, `is_active`, `show_on_qr_page` | `queue_profiles.id` — ОТДЕЛЬНОЕ пространство, НЕ ресурс-владелец |
| **Дневная очередь (DailyQueue)** | Строка очереди дня с XOR-владельцем и каноническим тегом | `daily_queues.id` |
| **Канонический тег** | Единый серверный источник тега очереди для desk и QR (RQ-14.b) | Лексическое пространство тегов (напр. `cardio`, `lab`) |

Непреложные правила идентичности (D-01 APPROVED, дословно):
- «Doctor.id, QueueResource.id и QueueProfile.id — разные пространства. Тип выбора передаётся явно.»
- «Не определять тип сущности по совпадению числового ID.»
- «QueueProfile — представление/направление, не ресурс-владелец. Профильный выбор разрешается в конкретного допустимого исполнителя по явно определённому серверному правилу.»
- «Не угадывать направление по названию услуги.»

## 2. Владелец: идентичность дневной очереди

Из D-01 APPROVED («Сохраняем») и ADR-001 stage D (миграция 0063: `ck_daily_queues_owner_xor`, partial uniques):

1. **doctor-owned**: день + `Doctor.id` + канонический `queue_tag`; уникальность активной строки — `uq_daily_queues_active_doctor_day_tag = (day, specialist_id, COALESCE(queue_tag,''))` (миграция 0065, RQ-14.a.1).
2. **resource-owned**: день + `QueueResource.id`; уникальность — `(day, queue_resource_id) WHERE active AND queue_resource_id IS NOT NULL` (0063).
3. **XOR**: ровно один из `specialist_id` / `queue_resource_id` на строку (CHECK на уровне БД и ORM-диалекта тестов).
4. **Запрещено**: схлопывать разные теги одного врача автоматически; объединять или перенумеровывать существующие очереди; создавать «универсальную очередь» без модели владельца (Stop-правило плана §RQ-16, L-DOMAIN).
5. Канонический тег QR-направления врача резолвится из реестра направлений (ключ QR-видимого профиля), а не из сырой `doctor.specialty` (RQ-14.b, #3281, E-047) — это ЕДИНСТВЕННЫЙ серверный способ разрешения для desk и QR.

Следствие для контракта: направление всегда адресуется парой «тип владельца + id владельца (+ канонический тег для doctor-owned)» и никогда — числовым id, совпадение которого с другой сущностью могло бы изменить маршрут.

## 3. Услуги и состав направления

1. Услуга принадлежит направлению через канонические метаданные каталога: `department_key` / `queue_tag` услуги (RQ-03/RQ-06; динамический фильтр мастера из `QueueProfile.queue_tags`, PR-25).
2. Флаг `requires_doctor` (RQ-05, E-023) — серверный контракт: услуга с врачом не может обслуживаться ресурсной поверхностью; выбор врача обязателен там, где требует сервер (дети RQ-05.a/RQ-05.b).
3. Владелец услуги без врача — ресурс реестра (QD-2C tag-first: активная строка `queue_resources` по точному тегу); неизвестная услуга НЕ уходит автоматически в `general` (S-13; Stage E fail-closed #3250 — каталог/руntime не делают общий фолбэк).
4. Группировка пакета (D-04 APPROVED с условием): «Группировка — один пациент, один визит, одна разрешённая очередь. Совпадения только врача недостаточно» — услуги должны разрешаться в ту же каноническую очередь; разные очереди/исполнители — отдельные записи со сводкой. Механика пакетов — срез RQ-25.b (не в RQ-16); контракт RQ-16 фиксирует только состав направления и правило принадлежности.
5. Мульти-специальность/замещение (D-05): одна каноническая специальность врача; автоматическое произвольное переназначение запрещено; недоопределённая механика переноса НЕ реализуется под видом замены `specialist_id` (граница с RQ-25.b).

## 4. Представление (QueueProfile) и «обзор направления»

1. `QueueProfile` — представление/направление: определяет вкладку регистратуры, фильтр записей по `queue_tags`, отображение на публичном QR (`show_on_qr_page`, `title_ru`, icon/color), и НЕ владеет очередью и нумерацией.
2. «Обзор нескольких очередей не создаёт собственной нумерации. Операции из обзора адресуют конкретную очередь/запись» (D-01 APPROVED). Профиль без собственного владельца = read-only обзор; профиль с разрешаемым исполнителем = точка записи, разрешаемая серверным правилом (RQ-09.b: явный `specialist_type`/`specialist_entity_types`, нетипизированный payload = выбор врача).
3. Архивирование профиля — существующий переход `is_active=False` (D-02 APPROVED): скрытие из вкладок и публичного QR, сохранение истории/связей/ожидающих, без каскадного отключения общих услуг/тегов других профилей; hard delete — только при доказанном нуле значимых связей с server-side re-verified preview и stale-защитой (RQ-12.b, E-040).
4. Переименование/косметика представления не меняет идентичность владельца и (после D-03-реализации) не меняет постоянный адрес автоматически.

## 5. Публичная доступность

Из D-03 APPROVED (дословно, приоритетная редакция):
1. «Постоянный публичный адрес направления выдаёт короткую сессию через защищённый путь записи. Он не является бессрочным токеном доступа.»
2. «Сохранить общий QR клиники. Постоянные адреса направлений — дополнительная возможность.»
3. «Переименование не меняет адрес автоматически.» (и не требует перепечатки таблички)
4. «Архивирование блокирует новую запись по старому адресу.» (отказ без утечки существования скрытых сущностей — S-15)
5. «TTL, eligibility, лимиты и защита от повторной отправки сохраняются.» — постоянный адрес наследует: eligibility-контракт RQ-09 (selection/join/token-path: #3225, #3241, #3284, #3245), честный TTL RQ-11 (#3192), частичный результат RQ-10 (#3227), rate-limit анонимного пути.

Ограничения публичности представления: скрытый/архивный профиль не участвует в публичной подборке (`show_on_qr_page=False` / `is_active=False` — фильтрация selection и join зеркальна, E-028/E-032/E-048); «мёртвых» поверхностей не появляется — все новые точки входа проходят тот же eligibility-контракт.

**Форма адреса — РЕШЕНО владельцем 2026-09-17** (дословная запись — [DECISION_PROPOSALS.md](DECISION_PROPOSALS.md) §«Решение владельца по открытой точке RQ-16.c», E-055; источник — сообщение владельца, trace `1a0ae53e51ec7769`): URL-вид `/q/<public_code>` — публичный frontend route, НЕ токен записи; `public_code` — opaque random code (12 символов, lowercase Crockford/Base32-подобный алфавит, crypto-random; название направления и `QueueProfile.key` в URL не используются); генерация сервером ОДИН РАЗ при первом provision/enable (создание QueueProfile ≠ создание адреса; backfill существующим профилям не выполняется); владелец адреса — QueueProfile как направление/представление (не владелец DailyQueue, D-01 сохранён); реестр — ОТДЕЛЬНАЯ таблица (не колонка `queue_profiles.slug`), `public_code` глобально UNIQUE навсегда с tombstone-FK (после разрешённого hard-delete код остаётся зарезервированным, переиспользование исключено), максимум один действующий адрес на профиль; ручная смена адреса в RQ-16.c/.d запрещена (rotation — отдельный будущий workstream, без redirect по умолчанию); rename не меняет адрес, archive сохраняет запись и блокирует join, реактивация того же профиля реактивирует тот же адрес; refusal для unknown/archived/hidden/deleted — единая анонимная semantics (S-15/RQ-16.b); `permanent_address=true` — только в RQ-16.d (динамический per-direction), до RQ-16.d постоянный адрес в UI не появляется (правило досье D-03 п.4 сохраняется). Runtime shape RQ-16.d зафиксирован решением, но НЕ реализуется в RQ-16.c.

## 6. QR target: единый серверный резолвер

1. «Desk и QR для одного выбранного набора услуг и исполнителя должны использовать один серверный способ разрешения очереди. Не вводить отдельные fallback-правила в каждой поверхности» (D-01 APPROVED). Реализация контракта: канонический резолвер RQ-14.b (`queue_svc/_operations.py`) + SSOT-выбор владельца формы (RQ-09.b) — новые поверхности RQ-16 обязаны потреблять резолвер, а не дублировать правила.
2. «Сервер возвращает поддерживаемые способы QR-входа» (план §RQ-16, Результат) — контракт/API-срез RQ-16.b: сервер явно перечисляет поддерживаемые способы входа для направления (сессионный QR / постоянный адрес после RQ-16.c/.d; обзор без записи), без угадывания на клиенте.
3. Печатный QR до RQ-16.c/.d остаётся текущим короткоживущим (честность срока RQ-11); никакие UI-поверхности не показывают постоянный адрес до принятия модели slug-реестра.

## 7. Ограничения и явные запреты контракта

1. Без миграций prod/staging/Supabase вне отдельных операторских авторизаций; переписывание смерженных миграций (включая #3250/0066, 0065, 0067) запрещено — только новые ревизии.
2. Без объединения/перенумерации существующих очередей; без схлопывания тегов одного врача; без fallback-правил на поверхностях.
3. Без определения типа сущности по числовому совпадению id; без угадывания направления по названию услуги.
4. Без «универсальной очереди» без модели владельца; без открытого продуктового выбора внутри среза (Stop §RQ-16, L-DOMAIN); без обхода токен-защиты.
5. Каждый runtime-срез: pre-work блок, gate по якорю, fail-first на disposable PG, точный allowlist; «Нельзя открыть PR на весь этап» (план §RQ-16).
6. Реализация D-решений не опережает редакцию владельца: ОТКРЫТЫЕ ТОЧКИ не закрываются молча.
