## D-01 — Идентичность очереди вкладки: исполнитель против обзора

> **APPROVED 2026-09-15 в уточнённой редакции (см. «Решение владельца»).** Пункт 1 «Предлагаемого поведения» «ровно одна активная строка очереди на ключ (день, владелец)» ЗАМЕНЕН: раздельные идентичности сохраняются — doctor-owned `(день, Doctor.id, канонический queue_tag)`, resource-owned `(день, QueueResource.id)`; схлопывание разных тегов одного врача и перенумерация существующих очередей запрещены; вилка E-033 закрывается единым серверным резолвером desk/QR без per-surface fallback и без угадывания по названию услуги. Форма выбора: Doctor.id, QueueResource.id и QueueProfile.id — разные пространства, тип выбора передаётся явно; QueueProfile — представление/направление, не ресурс-владелец; профильный выбор разрешается сервером в конкретного допустимого исполнителя; тип сущности не определяется по совпадению числового ID. Обзор нескольких очередей — без собственной нумерации (как предложено). Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Нужна ли каждой вкладке строго одна очередь или также обзор нескольких? Как задаются врач, ресурс и набор услуг?

**Текущее поведение (наблюдаемое, merged-контракт).**
- Desk-маршрут (мастер регистратуры): `registrar_wizard_queue_assignment_service.py` раскладывает visit по `service.queue_tag` каждой услуги — `get_or_create` строки `(day, doctor, tag)`.
- Живой QR: clinic-wide токен + Doctor.id override — маршрут по `doctor.specialty`; профильная ветка — по `profile_key` (трассировка E-033; Path A/B в `queue_svc/_operations.py`).
- Вилка владельца запинена characterization-тестом (E-033): при `service.queue_tag ≠ doctor.specialty` одна пара (день, врач) получает ДВЕ строки с независимой нумерацией — один и тот же пациент может встать в две очереди на разных поверхностях.
- Целостность внутри одной строки закрыта независимо от этого решения: RQ-14.a (FOR UPDATE + advisory lock, `#3248`, E-035) и RQ-14.a.1 (UNIQUE 0065 DEFERRABLE, `#3252`, E-036) — конкурентные записи больше не дублируют номера и не форкнут строки. Отсутствует именно согласование ИСТОЧНИКА тега между поверхностями.
- Коллизия формы идентификатора (наблюдение E-032/E-034): `QueueJoin` отправляет Doctor.id из `selectable_specialists[].id`, но Path A сначала матчит QueueProfile.id — малые id сид-профилей молча переключают маршрут.

**Предлагаемое поведение.**
1. Ровно одна активная строка очереди на ключ `(день, владелец)`; владелец — врач (doctor-owned) или ресурс (resource-owned, QD-2C dual-owner). Единственный источник тега для ОБЕИХ поверхностей — `service.queue_tag`; `doctor.specialty` остается фолбэком только для услуг с пустым тегом. Вилка владельца из E-033 после утверждения переворачивается фикс-срезом RQ-14.b.
2. «Обзор направления» (вкладка, показывающая несколько исполнителей/очередей) — отдельная read-only поверхность: не создает строк очереди, не участвует в нумерации, показывает владельца и правило нумерации каждой строки. Создание записи возможно только в конкретную строку исполнителя.
3. Форма выбора владельца — явная пара `(owner_type, owner_id)` на публичных поверхностях (QueueJoin): выбор врача всегда Doctor.id, выбор профильной/ресурсной поверхности всегда QueueProfile.id; числовое совпадение id больше не переключает маршрут (снимает RQ-09.b).
4. Табло/работлист показывают источник номера (владелец + правило) — продолжение линий RQ-24.a.2/RQ-20.a.

**Альтернатива и цена.** Оставить два источника (тег для desk, specialty для QR) с «примирением» на отображении: дешевле разово, но навсегда сохраняет вилку из E-033 — два талона одному пациенту на разных поверхностях, что прямо противоречит цели плана («куда попадает пациент из мастера или QR»).

**Разблокирует.** RQ-14.b (согласование источника тега), RQ-16/RQ-17/RQ-18 (модель направления), RQ-09.b (форма id). Сценарии S-12, S-14, S-15.

**Риск и откат.** Изменение маршрутизации живого QR — единственный поведенческий сдвиг предложения; исполняется отдельным срезом RQ-14.b с fail-first PG-проверками (паттерн E-033/E-035) после APPROVED. Существующие короткоживущие токены живут часы — миграция ссылок не требуется. Откат — revert PR среза; констрейнты 0065 не затрагиваются.

## D-02 — Смысл удаления и отключения используемой вкладки

> **APPROVED 2026-09-15 в уточнённой редакции (см. «Решение владельца»).** Архивирование = существующий переход `QueueProfile.is_active=False` (модель уже использует его для скрытия из активных и публичных выборок); отдельный archive-флаг НЕ добавляется без отдельной необходимой семантики — пункт о «миграции (флаг)» в «Риске и откате» ниже более не применим. Дополнительно закреплено владельцем: отключённый профиль не принимает новые записи через свои публичные точки входа, но существующая очередь остаётся доступной персоналу для завершения обслуживания; общие услуги и теги других действующих профилей не отключаются каскадно; hard delete — только при доказанном отсутствии значимых связей, включая исторические/будущие записи и публичные адреса; preview перепроверяется сервером при выполнении, устаревший preview не разрешает разрушительное действие. Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Что означает удаление и отключение используемой вкладки (профиля)?

**Текущее поведение.**
- RQ-12.a (`#3221`, E-026): удаление профиля больше не обнуляет теги, используемые оставшимися профилями — data-loss закрыт.
- Полного lifecycle нет: `_queue_profiles.py` выполняет жесткое удаление строки профиля; archived-состояния и preview последствий не существует; услуги, ссылающиеся на удаленный профиль/тег, теряют связь без предупреждения; история очередей не затрагивается, но и не связывается с «закрытой» вкладкой.

**Предлагаемое поведение.**
1. Для используемой вкладки единственное штатное действие — **архивирование**: профиль скрыт из вкладок регистратуры и публичных QR-выборок (join-контракт уже исключает неактивные — RQ-09/RQ-09.a/RQ-09.c), при этом услуги, история записей и CSV-реестр сохраняют ссылки; повторное включение возвращает вкладку без восстановления данных.
2. Жесткое удаление доступно только при нуле ссылок (ни одной услуги с тегом профиля, ни одной активной дневной очереди) и выполняется с preview-отчетом: список затрагиваемых связей до подтверждения; отказ, если отчет неактуален (stale-preview защита, S-10).
3. Bulk-операции проверяют каждую вкладку отдельно; частичная ошибка показывается построчно, успешные строки не откатываются молча (S-10).
4. CSV-экспорт/импорт (RQ-26) переносит archived-статус и отказывается импортировать удаление используемых профилей без явного подтверждения (стык с RQ-26.b).

**Альтернатива и цена.** Оставить жесткое удаление с обязательным preview, но без archived-статуса: проще модель, но теряется различие «временно не показываем» и «уничтожаем» — администратор не сможет временно скрыть вкладку, не рискуя связями, а ошибки preview становятся необратимыми.

**Разблокирует.** RQ-12.b (lifecycle), опора для RQ-13 (закрытие отделения переиспользует archived-семантику) и RQ-26.b. Сценарий S-10.

**Риск и откат.** Архивирование добавляет состояние — миграция (флаг) выполняется отдельным Alembic-срезом по правилу 7 плана; публичный контракт QR не меняется (неактивные уже исключены). Откат — revert среза; флаг аддитивен.

## D-03 — Долговечный QR для направления

> **APPROVED 2026-09-15 (см. «Решение владельца»).** Утверждено как предложено с уточнениями: постоянный адрес — точка входа, выдающая короткую сессию через защищённый путь записи (не бессрочный токен); общий QR клиники сохраняется — адреса направлений его дополняют; переименование направления не меняет адрес автоматически и не требует перепечатки QR; архивирование блокирует новую запись по старому адресу; TTL, eligibility, лимиты и защита от повторной отправки сохраняются. Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Нужен ли постоянный (печатный) QR у направления?

**Текущее поведение.**
- QR существует только как короткоживущая сессия: токен с TTL и одноразовым потреблением; RQ-11 (`#3192`, E-015) сделал срок честным на UI и в скачанном PNG. Постоянного адреса нет — распечатанная табличка устаревает с истечением токена.

**Предлагаемое поведение.**
1. Постоянный публичный адрес направления вида `/q/<direction-slug>` (стабильный slug профиля/направления, без PII и без секретов): открытие адреса выдает короткую сессию через существующий start-механизм и дальше работает текущий защищенный путь (RQ-09 selection-контракт, RQ-10 частичный результат, RQ-11 TTL).
2. Печать/табличка в кабинете используют постоянный адрес; UI показывает срок только у сессионного этапа, постоянный адрес не обещает бессрочного доступа (продолжение честности RQ-11).
3. Архивное/скрытое направление отдает понятный отказ на постоянном адресе (статус и причина без утечки существования скрытых сущностей); после archive по D-02 записаться по старой табличке нельзя (S-15).
4. Slug-реестр — часть модели направления из RQ-16; до RQ-16 постоянный адрес не появляется в UI.

**Альтернатива и цена.** Не делать постоянный адрес, печатать короткоживущий QR: администратор вынужден перепечатывать таблички на каждый день/сессию — прямое нарушение цели RQ-18 («получать QR для поддерживаемой новой очереди из настройки»).

**Разблокирует.** RQ-16, RQ-18. Сценарий S-15.

**Риск и откат.** Постоянный публичный адрес расширяет публичную поверхность — обязан проходить eligibility-контракт RQ-09 (selection + join + token-path, `#3225`/`#3241`/`#3245`) и rate-limit на анонимный путь. Откат — revert среза; slug-таблица аддитивна.

## D-04 — Пакеты услуг: один исполнитель против маршрута по кабинетам

> **APPROVED 2026-09-15 с условием (см. «Решение владельца»).** Группировка = один пациент + один визит + одна разрешённая очередь; совпадения только врача недостаточно — услуги должны разрешаться в ту же каноническую очередь; разные очереди/исполнители — отдельные записи с понятной сводкой. Дополнительно: отмена/выполнение одной услуги не меняет остальные молча; повтор команды не создаёт второй комплект записей; номер и queue_time существующей записи не переписываются при простом дополнении её совместимыми услугами. Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Как собирается пакет услуг у одного исполнителя и маршрут по нескольким кабинетам?

**Текущее поведение.**
- Корзина группирует услуги по каноническим метаданным (RQ-07, `#3219`, E-025); сохранение создает visit + assignment на каждую услугу; `registrar_wizard_queue_assignment_service.py` раскладывает записи по `queue_tag` каждой услуги — у одного врача за день возникает несколько параллельных строк, пациент получает несколько талонов без сводного вида.
- Требование врача передается DTO-флагом (RQ-05, E-023); серверная валидация — RQ-05.a (заблокирована #3085/#3250).

**Предлагаемое поведение.**
1. Услуги одного исполнителя с совместимым тегом в одном визите — одна строка очереди и один номер; «пакет» — представление над assignments (список услуг с общим номером), а не отдельный механизм очередей.
2. Услуги разных исполнителей — явно несколько записей: регистратор и пациент видят список (кто/кабинет/номер); никакого скрытого объединения или пересчета (S-23).
3. Частичное выполнение пакета видно: неоказанные услуги остаются в списке с владельцем (опора на честный частичный результат RQ-10); отмена одной услуги не трогает остальные (регрессия S-25).
4. Дубли одного и того же набора от повторной команды не создают вторую пачку (идемпотентность на уровне визита — стык с RQ-25.a.1 и S-22).

**Альтернатива и цена.** Единый номер на весь пакет независимо от исполнителей: удобнее пациенту, но ломает владение (ресурс-владелец должен видеть СВОЮ строку и СВОЮ нумерацию — противоречит QD-2C dual-owner и S-13) и требует кросс-очередной координации вызова, которой в системе нет.

**Разблокирует.** RQ-16 (состав направления), RQ-25.b (пакеты, остатки, замены). Сценарии S-23, S-25, S-22 (стык).

**Риск и откат.** Группировка в одну строку меняет нумерацию для пакетов — реализуется после 0065-инфраструктуры (DEFERRABLE reorder уже поддержан), отдельным срезом RQ-25.b. Откат — revert.

## D-05 — Мульти-специальность врача и замещение

> **APPROVED 2026-09-15 в ограниченном объёме (см. «Решение владельца»).** Утверждённый принцип: одна основная специальность врача в текущей версии (расширение — отдельная задача); автоматическое произвольное переназначение запрещено; явное замещение — только уполномоченному пользователю с проверкой допустимости заместителя и аудитом; история оказанных услуг и фактического исполнителя не переписывается. НЕ утверждено и не считается готовым: безусловное обещание «строка очереди не пересоздаётся» (пункт 2 ниже) убрано; до реализации переноса отдельно фиксируются целевая очередь, номер, порядок обслуживания, сохранение исходного времени и поведение при уже существующей очереди заместителя; недоопределённая часть не реализуется под видом простой замены specialist_id. Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Врач нескольких специальностей и замена отсутствующего врача.

**Текущее поведение.**
- Doctor.specialty — одно каноническое значение; eligibility-контракт #13 (active + не-incomplete + владелец существует/активен/роль doctor) закреплен RQ-09 (`#3225`, E-028), RQ-09.a (`#3241`, E-032), RQ-09.c (`#3245`, E-034). Автоматического переназначения ожидающих нет ни на одной поверхности.

**Предлагаемое поведение.**
1. Поддерживаемое ограничение: одна каноническая специальность на врача; интерфейс не предлагает запись вне ее (уже выполняется selection-стороной; фиксируется как контракт, а не случайность).
2. Замещение отсутствующего — только явная операция уполномоченной роли (админ/старший регистратор): выбор заместителя из допустимых той же специальности, сохранение пациента и `queue_time`, запись в аудите; строка очереди не пересоздается (S-24).

4. Расширение модели (мульти-специальность) — отдельная задача ВНЕ RQ-плана; до нее UI показывает поддерживаемое ограничение, а не прячет его.

**Альтернатива и цена.** Авто-переназначение на «любого свободного врача» при неявке: экономит время стойки, но нарушает владение очереди (D-01), правила пациента (queue_time/fairness) и права — прямое противоречие S-24 «нет автоматического произвольного переназначения».

**Разблокирует.** RQ-25.b (замена/изменения дня). Сценарий S-24.

**Риск и откат.** Минимальный: контракт фиксирует текущее поведение, добавляется только явная операция замещения с аудитом. Откат — revert.

## D-06 — Эффективные настройки и влияние отключения отделения

> **APPROVED 2026-09-15 в уточнённой редакции (см. «Решение владельца»).** Цепочка вычисления: клиника → отделение → владелец (врач ЛИБО ресурс — ресурсные очереди имеют собственные лимиты и стартовые номера, не только врач). Для действующей дневной очереди — снимок применённых параметров, включая стартовый номер, время и лимит (review 4017767792: колонки `start_number` в `DailyQueue` нет — при нехватке полей потребуется отдельный Alembic-срез по правилам плана; формулировка «миграции схемы не требует» в «Риске и откате» ниже убрана). Новые настройки не меняют выданные номера и историю текущего дня; ручное изменение параметров дня — отдельная явная операция с аудитом. Отключение отделения блокирует новые записи, но не удаляет ожидающих и не запрещает завершение существующего обслуживания/оплаты. Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Приоритет времени, лимита, стартового номера; влияние отключения отделения на сегодняшних пациентов.

**Текущее поведение.**
- Time SSOT (`#3142`) закрепил часовой пояс и границы дня; настройки очереди создаются атомарно с отделением (RQ-04, `#3202`, E-020); параметры активной DailyQueue фиксируются при создании строки дня (RQ-23 пин-поверхность: UI не показывает источник и время применения настроек).
- Отключение отделения сегодня не имеет согласованного контракта для ожидающих пациентов дня.

**Предлагаемое поведение.**
1. Один серверный SSOT эффективных настроек: разрешение clinic → department → doctor, специфичный уровень переопределяет общий; функция эффективных настроек — серверная (фронтенд только отображает результат и источник уровня), S-20.
2. Активная дневная очередь не меняется задним числом: новая конфигурация применяется со следующего дня/новой строки дня; уже открытая очередь продолжает работать на зафиксированных параметрах; UI показывает «источник и время применения» (S-20/S-26) — это и есть рабочее определение RQ-23.
3. Отключение отделения: ожидающие сегодняшнего дня остаются в своих строках; вызов/закрытие/оплата существующих записей работают до конца дня; новые записи в отделение блокируются с понятным отказом; переименование не пересоздает сегодняшнюю очередь и не теряет историю (S-11).
4. Стартовый номер и лимит — атрибуты строки дня, наследуемые от SSOT в момент создания; ручная правка дня возможна уполномоченной ролью с аудитом и не меняет SSOT.

**Альтернатива и цена.** Применять настройки к активной очереди немедленно: административно проще, но переписывает нумерацию и лимиты у пациентов, уже ожидающих в строке, — прямое нарушение «номер/владелец/история не мигрируют молча» (S-26).

**Разблокирует.** RQ-13 (жизненный цикл отделения), RQ-23 (эффективные настройки), опора RQ-27.b. Сценарии S-11, S-20, S-26.

**Риск и откат.** SSOT-функция — чистое вычисление над существующими строками; миграции схемы не требует. Откат — revert.

## D-07 — Повторяющиеся экраны и семантика счетчиков

> **APPROVED 2026-09-15 (см. «Решение владельца»).** Экраны сохраняются как отдельные рабочие задачи. Счётчик имеет единицу, дату, скоуп очереди и применённые фильтры; пациенты, записи и ожидающие не смешиваются; при пагинации число загруженных строк не выдаётся за общее количество записей; фронтенд и сервер используют согласованное определение метрики. Это правило приёмки, а не повод перестраивать все экраны. Текст ниже — исторический PROPOSED-вариант.

**Вопрос владельца.** Назначение повторяющихся экранов и значение счетчиков.

**Текущее поведение.**
- RQ-20 (`#3179`/`#3181`, E-011/E-012) согласовал заголовки/URL; RQ-21.a (`#3188`, E-014) развел «Нет совпадений» и «Очередь пуста». Счетчики вкладок — числа без единиц и без скоупа; повторяющиеся экраны (worklist vs профильная вкладка vs панель врача) показывают похожие списки без подписи различия.

**Предлагаемое поведение.**
1. Повторяющиеся экраны остаются отдельными рабочими задачами (объединение маршрутов запрещено без отдельной проверки — продолжение решения RQ-20.a по toggle-off); каждая поверхность подписана своим назначением.
2. Каждый счетчик подписан единицей и скоупом: «пациентов», «записей», «ожидают» — i18n ×5 локалей; скоуп счетчика вкладки — записи этого дня этой очереди, не глобальные числа (S-18).
3. Единица и скоуп выводятся из тех же данных, что и список под счетчиком (один источник — нет расхождений при смене даты/фильтра).

**Альтернатива и цена.** Слить повторяющиеся экраны в один универсальный список: меньше кода, но ломает роль-специфичные действия (call-next, лабораторные статусы) и уже опровергнута проверками RQ-20/RQ-21.a.

**Разблокирует.** RQ-21.b (согласованные счетчики), RQ-28 (инструкция опирается на подписанные экраны). Сценарий S-18.

**Риск и откат.** Минимальный: подписи и i18n — presentation-only, рэтчеты Regression Audit Gate соблюдаются (паттерн RQ-11/RQ-10). Откат — revert.

## Правила применения предложений

1. Каждое предложение вступает в силу только как строка APPROVED в разделе «Решения владельца продукта» PROGRESS.md (с датой и источником решения владельца). PROPOSED в таблице — статус черновика, не разрешение на runtime.
