# Решение владельца: lineage legacy-проекции lab_results (C → A+)

Status: APPROVED by product owner (2026-09-13, coordinator relay)
Origin: P1 finding on merged #3235 (overwrite of a sibling study's result on
`(order_id, test_code)` collision — e.g. `glucose` in `biochem_panel` blood vs
`urinalysis_oam` urine). This document is the binding contract for the fix
tracks. Runtime schema changes are NOT allowed outside the explicitly
sanctioned A+ track below.

## Клиническое правило

> Самостоятельное исследование — отдельная сущность. Исправленный бланк —
> новая версия того же исследования. Совпадение названия показателя не
> делает исследования одинаковыми.

Пример одного заказа:

| Бланк | Показатель | Значение (синтетика) | Смысл |
|---|---|---|---|
| Биохимия A | `glucose` | `5.4` | Самостоятельный результат |
| ОАМ B | `glucose` | `не обнаружено` | Другой самостоятельный результат |
| Ревизия A2 | `glucose` | `6.0` | Заменяет актуальное представление A, не трогая B |

Термин **lineage** — цепочка исходного бланка и его ревизий
(`A id=100 → A2 id=101 → A3 id=105`). Стабильный идентификатор цепочки — id
корневого бланка (`100`); он не меняется при ревизиях. Основа уже есть:
`revise()` пишет `supersedes_instance_id`; утверждённые instances и значения
неизменяемы. Вторая система версий не создаётся.

## Схема A+ (отдельная миграция, отдельный трек)

Два nullable-поля в `lab_results`:

| Поле | Назначение |
|---|---|
| `source_root_instance_id` | id исходного бланка — стабильная идентичность цепочки |
| `source_instance_id` | id конкретной утверждённой версии, давшей текущее значение |

Ключ управляемой проекции: `(source_root_instance_id, test_code)`.
НЕ `(order_id, test_code)` и НЕ `(source_instance_id, test_code)` — ревизия
получает новый instance id, поэтому одиночный source-ключ плодил бы строку
на каждую ревизию.

Ограничения:

- оба поля — FK на `lab_report_instances.id`, без каскадного удаления;
- управляемая строка: оба поля заполнены, `test_code` непустой;
- историческая строка неизвестного происхождения: оба поля `NULL`;
- уникальность `(source_root_instance_id, test_code)` — частичный уникальный
  индекс только для строк с установленным root;
- значения source/root определяет ТОЛЬКО сервер; клиент не может назначить
  их через `LabResultCreate`/`LabResultUpdate`.

## Правила актуальности (утверждены)

| Ситуация | Поведение |
|---|---|
| Создан самостоятельный бланк | Новая цепочка, даже если заказ и шаблон совпадают с другим бланком |
| Создан черновик ревизии | Актуальным остаётся предыдущий утверждённый результат |
| Ревизия утверждена | Обновляется только проекция её цепочки |
| Повторный sync того же утверждённого бланка | Нет новых строк и побочных действий |
| Re-sync старой версии после A3 | Значение не откатывается к старому |
| Конкурирующие ревизии одного предшественника | Первая утверждённая — текущая; вторая — контролируемый конфликт (не last-write-wins) |
| Показатель очищен в утверждённой ревизии | Прежнее значение больше не актуально (строка с `value=NULL`, актуальный `source_instance_id`, сброшенный `abnormal`; потребители показывают отсутствие значения, не «норму») |
| Цепочка повреждена / несколько несогласованных ветвей | Автовыбор запрещён; диагностика цепочки |

Актуальность определяется связями `supersedes_instance_id`, а не максимальным
id / `updated_at` / порядком запросов.

## Конкурентность (A+ runtime)

Транзакция: определить root → `SELECT … FOR UPDATE` root-instance →
перечитать состояние из БД (не ORM-кэш) → проверить пациента/заказ/
принадлежность цепочке/предшественника → проверить, что ревизию не обогнали →
утвердить instance + обновить только его lineage-проекцию → один commit →
уведомления после commit. Все пути берут блокировку в одинаковом порядке;
проверять на отдельных PostgreSQL-соединениях. Общая транзакция
финализации и проекции сохраняется (не коммитить утверждение раньше
проекции). Идемпотентность требуется от синхронизации проекции; это не
разрешение менять HTTP-контракт повторного `finalize()`.

## Старые данные и потребители

- Исторические строки в миграции НЕ переписывать и НЕ привязывать по
  эвристике `order_id + test_code`. Неизвестное происхождение остаётся
  неизвестным.
- Независимые legacy-писатели существуют (`crud/lab.py::add_results()`,
  `crud/lab_result.py`): отсутствие lineage не доказывает ошибочность строки.
- Production-backfill и исправление исторических данных — только после
  отдельного read-only census и подтверждения владельца.
- Управляемые (lineage) строки: обычные legacy CRUD-операции не изменяют и не
  удаляют их в обход канонического бланка — контролируемый отказ с указанием
  на `revise()`. Для строк без lineage прежнее поведение сохраняется.
- Разрешены минимальные изменения сериализации/отображения, необходимые для
  доказательства: биохимия и ОАМ не сливаются; ревизия видна как актуальное
  значение своей цепочки; строка без происхождения не выдаётся за доказанно
  актуальную проекцию.
- Уведомления: проверка критических значений использует `LabResult.created_at`
  — обновление строки ревизией не должно терять событие утверждённого
  исправления и не должно порождать повторные уведомления при техническом
  re-sync. Медицинские пороги и каналы доставки в этом треке не меняются.

## Этапы

| Этап | Объём | Условие завершения |
|---|---|---|
| **C — временная защита** | Отдельный минимальный PR: прекратить обновление результатов без доказанного происхождения | Старый результат не перезаписывается чужим бланком; неполнота legacy — явно открытое ограничение |
| **A+ — миграция** | Два поля, ограничения, частичный уникальный индекс, ORM, миграционные тесты | Fresh-install и upgrade проходят; исторические значения не изменены; RLS сохранён |
| **A+ — runtime** | Определение цепочки, транзакционная синхронизация, защита от устаревшей ревизии, проверки legacy-писателей/читателей | Полная regression-матрица на PostgreSQL |
| **Выкладка и данные** | Deployed SHA + применённая миграция + smoke; read-only census старых результатов | Подтверждение новой схемы и решение по историческим неоднозначностям |

Миграционный PR можно отделить от runtime-PR; runtime не выкатывать до
миграции. Откат — к варианту C, не к перезаписывающему коду #3235. Удаление
lineage-полей после начала использования — только по отдельному плану.
Номер Alembic-ревизии выбирается по свежему main и параллельным PR.

## Приёмочная матрица (A+)

| Тест | Ожидаемый результат |
|---|---|
| Биохимия + ОАМ, одинаковый код, оба порядка финализации | Два независимых результата |
| Два самостоятельных бланка одного шаблона | Две независимые цепочки |
| A → A2 → A3 | Одна актуальная проекция цепочки A; каноническая история сохранена |
| Re-sync A после A3 | A3 не заменяется старым значением |
| Две конкурирующие ревизии | Один переход, второй — конфликт без потери данных |
| Ошибка записи проекции | Финализация не коммитится частично |
| Очищение показателя | Старое значение не остаётся актуальным |
| Исторические строки без source | Не привязаны и не перезаписаны |
| Legacy update/delete управляемой строки | Обход запрещён |
| EMR/mobile/Telegram + уведомления | Не теряют самостоятельный результат, не смешивают источники |

## Промежуточный статус

- Этап C: реализуется отдельным PR (`codex/lab-projection-overwrite-guard`).
- Этапы A+ (миграция, runtime): НЕ начаты; требуют отдельных PR по обычной
  дисциплине после merge этапа C.
- Дефект перезаписи (#3235) считается закрытым только после реализации,
  PostgreSQL-регрессий и проверки потребителей — не самим этим документом.
