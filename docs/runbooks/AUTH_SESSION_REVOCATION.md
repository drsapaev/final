# Account and session revocation

`POST /api/v1/authentication/sessions/revoke-all?except_current=false` revokes the authenticated account's active access and refresh credentials, unfinished two-factor sessions, and outstanding password-reset tokens in one account-locked transaction. A recovery request started afterwards can create a new reset token. The endpoint does not know the number of distinct authenticated sessions and returns `revoked_count: null`. The bearer used for the request is revoked too; a new login is required.

Until access and refresh tokens have an authenticated, stable session binding, the application cannot reliably identify the current session or invalidate all access credentials belonging to one session. Therefore `GET /sessions/current`, `DELETE /sessions/{id}`, `POST /sessions/{id}/revoke`, and `POST /sessions/revoke-all` with its default `except_current=true` return HTTP 409 and do not revoke credentials. IP addresses and user agents are not session identity.

To restore selective revocation, introduce a persistent session identifier with a migration and mint it consistently in every login and token-rotation path. Bind both access and refresh credentials to that identifier, enforce its live status and ownership in every HTTP and WebSocket validator, and serialize issuance, rotation, and revocation under the account/session lock order. Define a rollout for credentials issued before the binding exists: either refuse selective operations while such credentials remain valid or explicitly invalidate them account-wide. Do not mix validator versions that disagree on session binding during rollout. Test current-session preservation, legacy credentials, token replay, database failure, and concurrent mint/revoke across all supported issuers before enabling the selective endpoints.
