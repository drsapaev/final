## 1. Принятые решения

- Публичный сайт — часть существующего React/Vite-приложения; публичные API — в существующем FastAPI. Отдельный BFF или новый backend-сервис не утверждены.
- Содержимое, цены и публикация управляются из админки Clinic OS. Новая запись попадает в существующую МИС; `website_appointments` не создавать.
- Поддерживаются оба режима: подтверждение свободного слота сразу и заявка регистратору. Настройка управляется из админки; результат определяет ответ backend.
- Языки — узбекский в латинице и русский; по умолчанию узбекский.
- По поручению владельца подробно внесены правила следующих этапов: услуги/врачи скрыты по умолчанию; категории выводятся по опубликованным услугам; slug фиксируется после первой публикации; узбекские страницы находятся в корне, русские — под `/ru/`. Storage-контракт этапа 2a и админские операции этапа 2b смёржены в `main` через PR #3636 и #3637. Полный контракт, границы PR и критерии — в [разделе 11 плана](2026-09-28-kosmed-public-site-plan.md#11-подробные-требования-к-публикации-адресам-и-этапам-2a4).
- Проверка телефона, защита от злоупотреблений и повторной отправки нужны в обоих режимах.
- Для публичного чтения цена берётся только из `Service.price` + `Service.currency`; при отсутствии суммы или валюты выводится «по запросу». `Doctor.price_default`/overrides не используются; `Doctor.cabinet` не публикуется. Услуга без активной/переведённой категории остаётся в каталоге с `category: null`; врач без подходящей локализованной специальности остаётся без её подписи. Эти решения записаны 2026-10-09.
- В PR #3641 отбор и сериализация проверяют обязательные тексты обеих локалей одной Python-проверкой после `strip()`: пробелы, табуляция и переводы строк сами по себе не дают опубликовать карточку. Некорректные записи пропускаются в списках; detail-route возвращает документированный типизированный `404` с `public_content_not_found`. Список категорий содержит уникальные очищенные названия запрошенной локали: совпадающие подписи объединяются, а внутренние ID/code остаются закрытыми.
- Для публичных страниц этапа 4 владелец выбрал Vercel Functions + Nitro SSR в текущем React/Vite-проекте. Серверная функция получает данные только через `/api/v1/public-site`; новую БД или бизнес-логику сайта не создавать. HTML страниц и sitemap формировать по запросу с `Cache-Control: no-store`, чтобы следующий запрос учитывал правку или снятие публикации. Статические ресурсы могут кэшироваться. Если API недоступен, вернуть контролируемую ошибку без прежней карточки. На preview оценить нагрузку API, задержку и расходы функции.

Storybook 9 использует встроенные Essentials/Interactions; конфиг сохраняет a11y и docs. Чтобы закрыть новую Storybook-зависимость с GHSA-82fw-gwwq-j7x9, `@vitest/mocker@4.1.11` переопределён только внутри Storybook; top-level Vitest 5.0.3 не затронут. ## 3. Настройки и публичные контракты

### Владелец настроек

`/admin/queue/settings` читает и пишет `ClinicSettings` / `clinic_settings`, а не отдельную модель `Setting` / `settings`: [CRUD](../../backend/app/crud/clinic.py), `get_settings_by_category`, `update_queue_settings`.

[QueueSettingsUpdate](../../backend/app/schemas/clinic.py) и CRUD разрешают определённый набор параметров QR-очереди. Добавление неизвестного `booking_mode` в JSON не сохраняет настройку. До реализации определить точное хранилище, типизированные DTO и endpoint настроек публичной записи. Предпочтение отдельному контракту этого канала в существующем backend — рекомендация, не принятое решение об endpoint.

Согласование `clinic_*` и `address/phone/...` закрыто PR #3625: экран админки использует канонические ключи, backend нормализует записи старого формата, а миграция 0078 копирует существующие значения без удаления legacy-строк. Не повторять пункт 1 таблицы реализации (раздел 6). PR не добавил публичное чтение настроек или режим записи на будущие даты; дневные лимиты QR-очереди по-прежнему не заменяют такой контракт.

### Публичная идентичность и публикация

- Каталог и будущая команда записи используют slug как общий стабильный публичный ключ услуги/врача, который backend разрешает во внутренний ID. Не публиковать служебные коды очереди вместо этого ключа.
- Slug уникален внутри вида сущности, включая скрытые/неактивные строки. До первой публикации он изменяем; после первой публикации фиксирован. Переименование, скрытие и мягкое удаление сохраняют адрес; повторная публикация использует тот же slug. Факт первой публикации сохраняется независимо от текущего флага видимости. История редиректов и физическое удаление опубликованной адресной идентичности не входят в этот вариант.
- `active`, публикация на сайте и разрешение записи — разные понятия; ограничения проверяются backend на отправке даже при устаревшей странице.
- Для существующих и новых услуг/врачей `show_on_website=false` по умолчанию. Публикация требует активности и проверенного контента обеих локалей; после деактивации необходима явная повторная публикация.
- Категория выводится, если активна, имеет названия обеих локалей и содержит доступную на сайте услугу. Отдельный флаг публикации категории не нужен этапу 2a; пустые категории исключаются. Доступная услуга без категории или в неактивной категории остаётся в каталоге с `category: null`.
- Публичные DTO возвращают только разрешённые поля. Скрытая/неактивная карточка и неизвестный slug дают публичный `404`; снятие с публикации также обновляет HTML, кеши и sitemap в согласованный срок этапа 4.
- До изменения DTO определить required/nullable поля, ошибки, результат записи и focused contract tests; обновлять OpenAPI и frontend generated types по репозиторному процессу.

## 4. Решения по онлайн-записи до кода

### Заявка и бронь

[AppointmentStatus.PENDING](../../backend/app/models/enums.py) означает ожидание оплаты. [Проверка занятости](../../backend/app/crud/appointment.py), `is_time_slot_occupied`, учитывает записи, кроме отменённых. Поэтому заявку с врачом, датой и временем нельзя без решения считать «не занимающей слот».

Нужно согласовать представление заявки в МИС или расширение её доменной модели, которое не создаёт отдельного сайта с собственным учётом записей. Определить:

1. Занимает ли заявка время, и если да — на какой срок.
2. Где регистратор видит её и как подтверждает или отклоняет.
3. Какая операция превращает заявку в подтверждённую запись и как проверяет конфликт.
4. Какие бизнес-состояния, ошибки и разрешённые действия возвращает backend.
5. Что происходит при смене режима между загрузкой формы и отправкой.

Не использовать оплату или очередь как замену состоянию подтверждения регистратором. Ответ сайта должен точно отражать фактический результат: заявка или подтверждённая бронь.

### Доступность и атомарность

Публичная доступность и создание записи должны использовать одни backend-правила: расписание, перерывы, длительность услуги, горизонт записи, активность врача/отделения и разрешение канала. Свободный слот сам по себе не доказывает допустимость времени.

Сверить порядок блокировок и проверки с [appointment_slot_guard.py](../../backend/app/services/appointment_slot_guard.py) и подключённым [patient portal writer](../../backend/app/api/v1/endpoints/patient_portal.py), включая разрешение и проверку конечного отделения. Не переносить весь controller в новый публичный endpoint как самостоятельную бизнес-логику.

Спроектировать guest idempotency: область ключа, одинаковый/изменённый повторный запрос, срок хранения, конкурентный повтор, ответ после сбоя связи. Существующий middleware с ключом пользователя не считать готовым анонимным решением.

### Телефон и карточка пациента

Уже есть публичный [patient-access API](../../backend/app/api/v1/endpoints/patient_access.py) и [OTP service](../../backend/app/services/patient_otp_service.py): ограничения запросов, защита от перечисления аккаунтов и одноразовое подтверждение. Сначала выполнить gap-анализ и переиспользовать пригодные компоненты. Текущий grant для входа не считать автоматически разрешением на создание брони; назначение и срок booking grant определить отдельно.

[Политика phone scope](../../backend/app/services/patient_phone_scope.py) допускает семейный номер на нескольких карточках. Подтверждение номера не разрешает произвольно присоединить запись к первой найденной карточке. Согласовать сценарии нового пациента, существующего пациента и родственника, а также разрешение неоднозначного совпадения. Не раскрывать наличие карточек, персональные сведения или клинические данные через ответы, логи и аналитику.

## 5. Публичные страницы, HTML и SEO

Для этапа 4 владелец выбрал Vercel Functions с Nitro SSR в текущем React/Vite-проекте. Серверный рендеринг читает данные из FastAPI по `/api/v1/public-site`; он не подключается к базе МИС напрямую и не хранит копию каталога. На первом запуске HTML страниц и sitemap формируются по запросу без CDN-кеша; ответы явно запрещают кеширование (`Cache-Control: no-store`), чтобы следующий запрос учитывал правку или снятие публикации. Это увеличивает число запросов к API и расходы на серверный рендеринг; оценить фактическую нагрузку и стоимость на preview. Если API недоступен, сайт показывает контролируемую ошибку без устаревшего содержимого; статические файлы могут кэшироваться.

- Прямой запрос страницы услуги/врача возвращает её содержимое, title, description и Open Graph в исходном HTML.
- После изменения или скрытия записи следующий запрос HTML и sitemap отражает опубликованное состояние API без ручного релиза сайта. Описаны сбой обновления и снятие с публикации.

Обновление кеша не заменяет SSR или пререндеринг. Обычный SPA fallback на общий `index.html` не является доказательством выполнения SEO-требования. До выбора рендеринга оценить совместимость с существующим размещением; новый процесс или сервис потребует отдельного архитектурного решения.

### Проверенные ограничения и выбранное решение

- В `vercel.json` сборка настроена на `frontend/dist`, а rewrite всех путей ведёт в общий `/index.html`. `frontend/Dockerfile` также собирает статический Vite output; `frontend/docker/nginx.conf` отдаёт его через Nginx с SPA fallback. Эти конфигурации сейчас не создают route-specific HTML.
- Vite SSR требует server entry и runtime, который исполняет его на запрос; это отдельный от текущей статической сборки режим ([Vite SSR guide](https://vite.dev/guide/ssr)). Vercel документирует вариант Vite + Nitro, где серверные маршруты становятся Vercel Functions ([Vercel Vite + Nitro](https://vercel.com/docs/frameworks/full-stack/vite-with-nitro)).
- **Проверка совместимости 2026-10-09:** проект закреплён на `vite@6.4.3`. Изолированная сборка с `nitro@3.0.260903-beta` и `vite@6.4.3` остановилась при загрузке Vite config с `Cannot read properties of undefined (reading 'meta')`; матрица пакета Nitro 3 заявляет совместимость интеграции с Vite 7/8 ([Nitro Vite guide](https://nitro.build/docs/vite), [package metadata](https://github.com/nitrojs/nitro/blob/main/package.json)). Владелец одобрил отдельный prerequisite Vite 7 + Storybook 9; он готовится в ветке `codex/vite7-prereq` от `8f3d325de`. Локальные `npm ci --legacy-peer-deps`, `npm run build` и `npm run build-storybook` прошли; Nitro integration не входит в эту ветку и должна быть проверена следующим PR. Новая moderate advisory Storybook закрыта override `@vitest/mocker@4.1.11`; полный audit всё ещё показывает 5 high advisory, совпадающих с базовым main и относящихся к Stylelint-зависимостям. В production-only audit — 0 уязвимостей. Не подключать Nitro к Vite 6 и не менять runtime молча.
- Vercel Functions превращают серверные маршруты Vite + Nitro в функции; текущие статические Vercel и Docker/Nginx конфигурации сами по себе route-specific HTML не создают. До production проверить на preview HTML обеих локалей, соединение server function с публичным API, свежесть публикации, `Cache-Control: no-store` и поведение при отказе API. API origin функции брать из серверной конфигурации окружения, не из клиентского bundle.

Карта локалей внесена в план: узбекский в корне, русский под `/ru/...`, один slug объекта для обеих локалей. Прямой URL определяет язык независимо от localStorage сотрудника. Учитывать canonical, hreflang (`uz-Latn`/`ru`), sitemap и `<html lang>`; `x-default` ведёт на узбекскую страницу. Сохранить действующие `/queue/join`, `/q/:publicCode`, `/confirm-visit` и их владельцев. Формы записи, страницы успеха и token-based маршруты исключать из публичного sitemap и индексирования по отдельной политике.

Аналитика публичного сайта означает агрегированные события вроде клика по телефону, открытия и отправки формы. Это не внутренняя аналитика очереди. Текущий объём сайта не включает показ пациенту позиции талона или ожидаемого времени; существующие `/queue/join` и `/q/:publicCode` сохраняются как сценарий входа в QR-очередь. Для живого статуса потребуется отдельное продуктовое решение и проверка публичного контракта, приватности и актуальности данных.

Решение по хранению и раздаче логотипа/фото нужно до интерфейсов их загрузки и публикации. Не публиковать всё содержимое каталога storage или закрытые вложения МИС как публичные медиа.

## 7. Как получить обновление в другом агенте

Изменение Markdown не обновляет уже загруженный контекст автоматически. Другой агент должен получить документационный commit через свой обычный Git/PR-процесс и перечитать файлы. Не делать reset, checkout или cherry-pick поверх его незакоммиченных изменений; при несовпадении веток согласовать применение документационного commit отдельно от runtime-кода.

Короткое сообщение в его чат:

> Перед следующим этапом сайта Doktor KosMed перечитай `AGENTS.md`, `docs/plans/2026-10-06-kosmed-public-site-handoff.md`, актуальные план и аудит. Проверь наличие документационного commit в своём checkout. Сохрани принятые языки, оба режима записи и общий backend. Открытые решения из заметки согласуй до соответствующих правок; сначала сообщи, какие пункты затрагивают текущий PR. Не сбрасывай свою работу.

Эту заметку обновлять при изменении статуса, решения или канонического владельца; каждый статус сопровождать датой и источником. Локальная автоматическая память помогает агентам одного clone, но не заменяет переносимые документы Git и не гарантирует уведомление другого клиента.
