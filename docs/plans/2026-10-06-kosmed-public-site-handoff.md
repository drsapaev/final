## 1. Принятые решения

- Публичный сайт — часть существующего React/Vite-приложения; публичные API — в существующем FastAPI. Отдельный BFF или новый backend-сервис не утверждены.
- Содержимое, цены и публикация управляются из админки Clinic OS. Новая запись попадает в существующую МИС; `website_appointments` не создавать.
- Поддерживаются оба режима: подтверждение свободного слота сразу и заявка регистратору. Настройка управляется из админки; результат определяет ответ backend.
- Решения владельца от 2026-10-14 для первого выпуска: записываться может только вошедший пациент и только в собственную карточку; заявка регистратору не резервирует слот, а при её принятии регистратор заново проверяет доступность; режим записи задаётся на всю клинику, с allowlist активных опубликованных услуг и врачей. Доступные интервалы строятся только по настроенному расписанию врача и длительности услуги; без расписания интервалы не показываются, горизонт задаётся в админке.
- Языки — узбекский в латинице и русский; по умолчанию узбекский.
- По поручению владельца подробно внесены правила следующих этапов: услуги/врачи скрыты по умолчанию; категории выводятся по опубликованным услугам; slug фиксируется после первой публикации; узбекские страницы находятся в корне, русские — под `/ru/`. Storage-контракт этапа 2a и админские операции этапа 2b смёржены в `main` через PR #3636 и #3637. Полный контракт, границы PR и критерии — в [разделе 11 плана](2026-09-28-kosmed-public-site-plan.md#11-подробные-требования-к-публикации-адресам-и-этапам-2a4).
- Проверка контактного телефона, защита от злоупотреблений и повторной отправки нужны в обоих режимах. Телефон не определяет карточку пациента и не заменяет вход в портал.
- Для публичного чтения цена берётся только из `Service.price` + `Service.currency`; при отсутствии суммы или валюты выводится «по запросу». `Doctor.price_default`/overrides не используются; `Doctor.cabinet` не публикуется. Услуга без активной/переведённой категории остаётся в каталоге с `category: null`; врач без подходящей локализованной специальности остаётся без её подписи. Эти решения записаны 2026-10-09.
- В PR #3641 отбор и сериализация проверяют обязательные тексты обеих локалей одной Python-проверкой после `strip()`: пробелы, табуляция и переводы строк сами по себе не дают опубликовать карточку. Некорректные записи пропускаются в списках; detail-route возвращает документированный типизированный `404` с `public_content_not_found`. Список категорий содержит уникальные очищенные названия запрошенной локали: совпадающие подписи объединяются, а внутренние ID/code остаются закрытыми.
- Для публичных страниц этапа 4 владелец выбрал Vercel Functions + Nitro SSR в текущем React/Vite-проекте. Серверная функция получает данные только через `/api/v1/public-site`; новую БД или бизнес-логику сайта не создавать. HTML страниц и sitemap формировать по запросу с `Cache-Control: no-store`, чтобы следующий запрос учитывал правку или снятие публикации. Статические ресурсы могут кэшироваться. Если API недоступен, вернуть контролируемую ошибку без прежней карточки. Реализация SSR слита PR #3647; Production deployment и оставшаяся приёмка описаны выше и в разделе 6. Нагрузку API, задержку и расходы функции на Production пока не измеряли.

## 3. Настройки и публичные контракты

### Владелец настроек

`/admin/queue/settings` читает и пишет `ClinicSettings` / `clinic_settings`, а не отдельную модель `Setting` / `settings`: [CRUD](../../backend/app/crud/clinic.py), `get_settings_by_category`, `update_queue_settings`.

[QueueSettingsUpdate](../../backend/app/schemas/clinic.py) и CRUD разрешают определённый набор параметров QR-очереди. Добавление неизвестного `booking_mode` в JSON не сохраняет настройку. До реализации определить точное хранилище, типизированные DTO и endpoint настроек публичной записи. Предпочтение отдельному контракту этого канала в существующем backend — рекомендация, не принятое решение об endpoint.

Согласование `clinic_*` и `address/phone/...` закрыто PR #3625: экран админки использует канонические ключи, backend нормализует записи старого формата, а миграция 0078 копирует существующие значения без удаления legacy-строк. Не повторять пункт 1 таблицы реализации (раздел 6). PR не добавил публичное чтение настроек или режим записи на будущие даты; дневные лимиты QR-очереди по-прежнему не заменяют такой контракт.

### Публичная идентичность и публикация

- Каталог и будущая команда записи используют slug как общий стабильный публичный ключ услуги/врача, который backend разрешает во внутренний ID. Не публиковать служебные коды очереди вместо этого ключа.
- Slug уникален внутри вида сущности, включая скрытые/неактивные строки. До первой публикации он изменяем; после первой публикации фиксирован. Переименование, скрытие и мягкое удаление сохраняют адрес; повторная публикация использует тот же slug. Факт первой публикации сохраняется независимо от текущего флага видимости. История редиректов и физическое удаление опубликованной адресной идентичности не входят в этот вариант.
- `active`, публикация на сайте и разрешение записи — разные понятия; ограничения проверяются backend на отправке даже при устаревшей странице.
- Для существующих и новых услуг/врачей `show_on_website=false` по умолчанию. Публикация требует активности и проверенного контента обеих локалей; после деактивации необходима явная повторная публикация.
- Категория выводится, если активна, имеет названия обеих локалей и содержит доступную на сайте услугу. Отдельный флаг публикации категории не нужен этапу 2a; пустые категории исключаются. Доступная услуга без категории или в неактивной категории остаётся в каталоге с `category: null`.
- Публичные DTO возвращают только разрешённые поля. Скрытая/неактивная карточка и неизвестный slug дают публичный `404`; снятие с публикации также обновляет HTML, кеши и sitemap в согласованный срок этапа 4.
- До изменения DTO определить required/nullable поля, ошибки, результат записи и focused contract tests; обновлять OpenAPI и frontend generated types по репозиторному процессу.

## 4. Решения по онлайн-записи до кода

### Решения владельца от 2026-10-14

1. В первой версии записывается только аутентифицированный пациент и только в собственную карточку `Patient`. Гостевая запись и запись родственников не входят в первый выпуск.
2. Заявка регистратору не удерживает слот. При её принятии регистратор повторно проверяет расписание и занятость; подтверждённая запись создаётся только если проверка прошла.
3. У клиники один режим записи, выбираемый в админке. В админке задаются allowlists активных опубликованных услуг и допущенных врачей; для услуги можно явно выбрать нескольких врачей, но только в пределах существующих правил допуска. Если услуга закреплена за конкретным врачом, эта привязка остаётся ограничением. Интервалы строятся только из настроенного расписания врача с учётом длительности услуги; если расписания нет, слот не показывается. Горизонт записи настраивается в админке.
4. Заявку вручную обрабатывает регистратор или администратор: её можно подтвердить или отклонить. Пока сотрудник не принял решение, пациент может отозвать заявку; необработанная заявка не исчезает автоматически.
5. Время показывается по часовому поясу Ташкента. Начала интервалов идут с шагом 20 минут от начала смены врача; длительность приёма берётся отдельно из настройки услуги, перерывы врача исключаются. Без настроенного расписания интервалы не выдаются.
6. Публичная запись изначально выключена и остаётся выключенной до заполнения обязательных настроек. Если политика записи изменилась, пока пациент заполнял форму, перед отправкой форма должна показать новую политику и получить подтверждение пациента.
7. Отмена и перенос записи в первом выпуске выполняются через регистратора; самостоятельные действия пациента на сайте не входят в v1.
8. Если телефон в аккаунте уже подтверждён, повторный код перед записью не нужен. Если нет — пациент подтверждает его SMS-кодом перед первой записью. Телефон не используется для выбора карточки пациента.

### Дополнительные решения владельца от 2026-10-14

- На официальный праздник интервалы можно показывать только после отдельного подтверждения клиники, что она работает в этот день.
- Сайт не обещает пациенту точный срок ответа регистратора по заявке.
- Первая версия онлайн-записи охватывает только приёмы у врачей. Запись на лабораторные услуги и другие ресурсы отложена.
- Новому пациенту карточку создаёт или активирует регистратор; самостоятельная регистрация с созданием карточки на сайте не входит в первый выпуск.
- Владелец выбрал современный образ медицинской клиники. Утверждённые материалы публикуются постепенно по мере готовности; примеры из приложенного исследования сами по себе не утверждают тексты, дизайн или данные.
- В первой версии допускается только грубая внутренняя агрегированная аналитика. Google Analytics, Яндекс Метрика и другие внешние трекеры не подключаются.
- Истории пациентов, отзывы и фотографии «до/после» отложены до отдельного решения о редакционном процессе и проверяемом согласии на публикацию.
- Публичное направление и направление записи можно анализировать параллельно, но их изменения остаются отдельными PR; циклическое правило требует завершить текущий PR до начала следующего.

### Заявка, подтверждение и занятость

[AppointmentStatus.PENDING](../../backend/app/models/enums.py) означает ожидание оплаты, а [проверка занятости](../../backend/app/crud/appointment.py) `is_time_slot_occupied` учитывает записи, кроме отменённых. Поэтому `PENDING` нельзя использовать как состояние заявки регистратору: такая запись занимала бы слот и смешивала бы два разных бизнес-состояния.

Решение владельца: заявка не резервирует время; её вручную обрабатывает регистратор или администратор, пациент может отозвать её до решения, а необработанная заявка не истекает автоматически. Если слот займут до решения сотрудника, заявку нельзя подтверждать: пациенту предлагают выбрать другое время. Остаётся определить владельца заявки в существующей МИС (расширение существующего домена или отдельная сущность внутри МИС), точные статусы и переходы, запись результата конфликта, права сотрудников, уведомления, аудит и срок обработки. Не создавать `website_appointments` или отдельный от МИС учёт.

Принятие заявки должно заново проверять допуск услуги/врача, расписание и занятость под существующей блокировкой врача; только затем можно создать обычный `Appointment` в той же транзакции. Сверить порядок с [appointment_slot_guard.py](../../backend/app/services/appointment_slot_guard.py) и подключённым [patient portal writer](../../backend/app/api/v1/endpoints/patient_portal.py), включая проверку конечного отделения. Не переносить controller в новый endpoint как самостоятельную бизнес-логику. Если политика изменилась во время заполнения формы, пациент должен увидеть её и подтвердить до отправки; технический способ обнаружить изменение и судьбу уже отправленных заявок при последующем переключении режима ещё нужно определить.

Не использовать оплату или очередь как замену состоянию подтверждения регистратором. Ответ сайта должен точно отражать результат: создана заявка или создана подтверждённая запись.

### Расписание, длительность и атомарность

Владелец утвердил источник доступности: настроенное расписание врача и длительность услуги; без расписания слот не показывается, fallback-слоты запрещены. Горизонт задаётся в админке. Используется местное время Ташкента, шаг начала интервалов — 20 минут, перерывы исключаются.

Владелец определил точку отсчёта 20-минутной сетки: начало смены врача. Официальный праздник считается рабочим только после отдельного подтверждения клиники. До кода остаётся определить хранение календарных исключений, реакцию на изменение расписания и безопасное поведение при отсутствующей или некорректной длительности. Текущая генерация доступности имеет часовую гранулярность и не учитывает длительность услуги; writers также не проверяют, что время входит в расписание. Поэтому показ доступности и команда записи должны использовать одну backend-политику и одну серверную проверку.

Сверить порядок блокировок с [appointment_slot_guard.py](../../backend/app/services/appointment_slot_guard.py) и все подключённые writers. Моментальный режим должен атомарно проверять актуальную доступность и создавать обычный `Appointment`; ответ об успехе означает принятие слота МИС, но не оплату.

### Идентификация пациента, контакт и повторы

В первой версии идентификатор карточки должен происходить из аутентифицированной сессии пациента портала и серверной связи с его собственной `Patient`. Каждый endpoint обязан проверять ownership; переданный клиентом чужой `patient_id` не даёт доступ к карточке. Телефон и OTP не выбирают карточку: [политика phone scope](../../backend/app/services/patient_phone_scope.py) допускает семейный номер. Гостевой режим, родственники и booking grant в v1 не реализуются; для них нужна отдельная авторизация владельца и новый контракт.

Владелец утвердил повторное использование уже подтверждённого телефона; если он ещё не подтверждён, перед первой записью пациент получает SMS-код. Телефон и OTP не выбирают карточку: [политика phone scope](../../backend/app/services/patient_phone_scope.py) допускает семейный номер. До кода определить технический контракт SMS-подтверждения, его сроки/лимиты и поведение при изменении номера. Для аутентифицированного потока проверить текущие scope и replay-семантику обязательного `Idempotency-Key` портала до повторного использования. Гостевые ключи и idempotency в первый выпуск не входят. Не раскрывать наличие карточек или персональные/клинические сведения через ответы, логи и аналитику.

### Настройки канала в админке

Владелец утвердил область настроек: режим общий для клиники, а допущенные активные опубликованные услуги и врачи выбираются через allowlists; горизонт также настраивается в админке. Для услуги можно указать несколько врачей, если они проходят действующие правила допустимости. Существующий pin услуги на врача остаётся ограничением и не снимается настройкой сайта. Канал записи выключен, пока обязательные настройки не заполнены; изменение политики во время заполнения формы требует повторного подтверждения пациентом. Публичная публикация карточки сама по себе не включает её в доступность для записи.

До реализации определить типизированный backend/admin-контракт, хранилище, роли, аудит изменений, точные критерии полной настройки канала и совместимость конкретных пар услуги/врача. Не добавлять неизвестные ключи в `/admin/queue/settings`: текущий endpoint сохраняет ограниченный набор параметров QR-очереди. Начальное выключенное состояние — утверждённое решение владельца.

## 5. Публичные страницы, HTML и SEO

Для этапа 4 владелец выбрал Vercel Functions с Nitro SSR в текущем React/Vite-проекте. Серверный рендеринг читает данные из FastAPI по `/api/v1/public-site`; он не подключается к базе МИС напрямую и не хранит копию каталога. На первом запуске HTML страниц и sitemap формируются по запросу без CDN-кеша; ответы явно запрещают кеширование (`Cache-Control: no-store`), чтобы следующий запрос учитывал правку или снятие публикации. Это увеличивает число запросов к API и расходы на серверный рендеринг; оценить фактическую нагрузку и стоимость на preview. Если API недоступен, сайт показывает контролируемую ошибку без устаревшего содержимого; статические файлы могут кэшироваться.

- Прямой запрос страницы услуги/врача возвращает её содержимое, title, description и Open Graph в исходном HTML.
- После изменения или скрытия записи следующий запрос HTML и sitemap отражает опубликованное состояние API без ручного релиза сайта. Описаны сбой обновления и снятие с публикации.

Обновление кеша не заменяет SSR или пререндеринг. Обычный SPA fallback на общий `index.html` не является доказательством выполнения SEO-требования. До выбора рендеринга оценить совместимость с существующим размещением; новый процесс или сервис потребует отдельного архитектурного решения.

### Проверенные ограничения и выбранное решение

## 7. Как получить обновление в другом агенте

Изменение Markdown не обновляет уже загруженный контекст автоматически. Другой агент должен получить документационный commit через свой обычный Git/PR-процесс и перечитать файлы.
