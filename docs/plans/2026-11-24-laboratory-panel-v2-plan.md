## 1. Организация разработки: изоляция до окончательной готовности

### 1.1. Где хранить план и реализацию

1. **Текущий отдельный Draft PR содержит только этот план.** Он сохраняется открытым как исходная постановка; текущая команда не начинает реализацию и не сливает PR.
2. После отдельной команды начать реализацию создать собственную ветку/worktree от свежего `origin/main`, например `codex/laboratory-panel-v2`, и **один Draft PR полной реализации**. Выбран вариант отдельной ветки; fork допустим при необходимости иной изоляции или отсутствии прав на ветку.
3. В начало PR реализации поместить ссылку на исходный план. Внести актуальную копию этого документа в ветку реализации; с этого момента её чекбоксы и журнал становятся единственным актуальным трекером исполнения. Исходный плановый PR остаётся исторической постановкой со ссылкой на PR реализации.
4. Все этапы выполнять последовательными тематическими коммитами в одной ветке реализации. Вспомогательные ветки агентов объединять в неё. Промежуточная готовность блока не означает готовность всей панели к merge.
5. До завершения разработки и финальной приёмки сохранять PR реализации Draft. Рабочий `main`, production API, рабочую БД и основные доменные привязки не использовать как площадку разработки.
6. Синхронизировать изолированную ветку со свежим `main` в контрольных точках и перед финальной приёмкой. Учитывать чужие изменения; не заменять их старой версией из плана.
7. Завершение плана означает проверенную панель целиком. Наличие прототипа, первого экрана или успешной сборки не закрывает задачу.

### 1.2. Порядок проверок по явному решению владельца

**Основная разработка P00–P09 → единый финальный цикл P10: DevBrain gate → тесты и CI → staging → устранение замечаний → повтор затронутых проверок → решение о готовности.**

- Между пакетами разработки не ставить обязательное ожидание полного DevBrain gate, общего CI, всех тестов или staging. Писать необходимые тестовые сценарии вместе с изменениями; обязательный итоговый запуск и сбор доказательств отнесены в P10.
- Небольшие локальные проверки, необходимые для понимания конкретной ошибки или продолжения разработки, допустимы без превращения их в отдельный процесс согласования. Они не дают статуса полной готовности.
- GitHub может автоматически запускать workflows при открытии и обновлении PR. Draft сам по себе не отключает такие запуски. Их можно учитывать как фоновые результаты; не ждать каждого полного прогона для перехода к следующему пакету.
- Не отключать workflows, required checks, branch protection, проверки секретов, hooks или проверки доступа. Не использовать фиктивные зелёные статусы, автоматическое снятие замечаний, пустые коммиты и изменение router для прохождения gate.
- Отложенная проверка остаётся **не выполненной**, пока она действительно не исполнена. `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `NOT_APPLICABLE` фиксируются честно и отдельно.
- В текущем `AGENTS.md` предусмотрена публикация непроверенных предложений в изолированных unmerged Draft PR с пометкой `gate not run; do not merge or deploy`. Этот план использует такой контур и фиксирует явно запрошенную владельцем последовательность работы. Глобальные инструкции и настройки репозитория не переписываются.
- Перед merge необходимы реальные результаты на окончательной версии кода: gate, обязательные GitHub checks, review и применимый staging. Отсутствие нужной среды блокирует выпуск, но не безопасную работу с изолированным предложением.
- Этот план не является разрешением отправлять данные реальных пациентов, выполнять производственные миграции или публиковать изменения в обход применимых полномочий.

### 1.3. Как обновлять прогресс

- `[ ]` — пункт не завершён. `[x]` — результат реализован/проверен в пределах явно указанного этапа и подкреплён ссылкой на коммит или доказательство.
- Чекбоксы реализации и чекбоксы финальной приёмки независимы: завершённый код до P10 имеет статус **IMPLEMENTED / UNVERIFIED**.
- После каждого существенного коммита обновлять чекбоксы и журнал в той же ветке. Указывать ID пункта, commit SHA, что изменилось, что остаётся непроверенным и следующий шаг.
- Не отмечать этап полностью, если внутри остаётся обязательный незавершённый подпункт. `NOT_APPLICABLE` требует основания и решения владельца для изменения обязательного объёма.
- В описании PR держать краткие чекбоксы этапов P00–P10 и ссылку на этот подробный документ. После передачи работы другой агент читает актуальные исходники, документ и последний журнал, сохраняя границы задачи.

## 2. Продуктовый результат и обязательный объём

Пользователь открывает лабораторию и сразу видит все исследования, требующие действий. Он находит пациента/заказ/пробу, вводит результаты без потери фокуса, видит применимые единицы и референсы, понимает препятствия к выпуску и может проследить результат до врача и последующего исправления.

Обязательные сценарии новой панели:

| Сценарий | Ожидаемый результат |
|---|---|
| Начало смены | Видны незавершённые исследования прошлых дней, срочные и просроченные; счётчики отражают полную область |
| Приём материала | Проба имеет собственную идентичность, материал, контейнер и документированные события |
| Ввод по пациенту | Рабочий список остаётся доступным рядом с выбранным заказом; идентификация закреплена |
| Массовый ввод | Однотипные исследования нескольких проб вводятся с явным сопоставлением и проверкой каждой строки |
| Проверка | Видны полнота, состояние пробы, применимый QC, отклонения, динамика и точная версия данных |
| Выпуск | Сервер фиксирует фактического сотрудника, время, неизменяемую версию и разрешённые действия |
| Частичная готовность | Видно, какие исследования выпущены и что удерживает остальные |
| Критический результат | Одно правило оценки используется в интерфейсе и уведомлениях; есть ответственный, попытки связи, подтверждение и эскалация |
| Исправление | Создаётся новая связанная версия с причиной и автором; предыдущая сохраняется |
| Выдача | PDF, ЭМК и интеграционные представления согласованы по значению, единице, оценке и версии |
| Проблема сети | Ввод не теряется, состояние сохранения достоверно, конфликт не маскируется |
| Русский/узбекский | Перевод не меняет смысл результата, статусы и основные сценарии доступны в поддерживаемых языках |

Роли: лаборант — пробы и ввод; уполномоченный проверяющий — проверка и выпуск; руководитель лаборатории — правила, QC, исключения и показатели; врач — результаты и подтверждение критического сообщения. Полномочия уточняются в существующей ролевой модели; новая роль не вводится только ради названия вкладки.

| Таблица результатов | Показатель, значение, единица, применимый референс, оценка, предыдущее значение |
| Контекст по запросу | История и график сопоставимых результатов, сведения о пробе, QC, комментарии, коммуникация |
| Действия | Достоверный статус сохранения, проверка, выпуск, PDF, исправление — по серверным полномочиям |

Desktop: список и редактор рядом; контекст раскрывается по необходимости. Mobile: последовательный переход с сохранением выбранного заказа, фильтров и позиции. Шаблоны/правила/администрирование — отдельная рабочая область. ИИ — дополнительный инструмент по запросу, без заполнения измерений или самостоятельного выпуска. Сохранить `requires_doctor_confirmation` для медицинских AI-ответов.

Основные состояния разделены:

- Заказ: состав назначений, частичная/полная готовность, отмена конкретного исследования с причиной.
- Проба: ожидается, взята, получена, принята, удержана, отклонена, повторно взята.
- Результат: отсутствует, введён, сохранён, оценён, проверен, выпущен, заменён исправленной версией.
- Коммуникация: требуется, задача создана, попытка/доставка, подтверждено, эскалация.

## 10. Риски, ограничения и восстановление

| Риск | Действие в плане |
|---|---|
| Новые правила изменяют смысл старого результата | Сохранять historical snapshots; исправлять через новую ревизию и прослеживаемое уведомление |
| Изменение catalog/unit ломает потребителей | Общий resolver, совместимые DTO/адаптеры, паритет V19 |
| Миграция требует недостоверного backfill | Хранить unknown, выделять сомнительные записи; не выдумывать provenance |
| Конфликт с параллельной работой в repo | Свежая база, ownership/scope, синхронизация и единый integration PR |
| Late response переносит контекст | Identity guards и V10; выбранная строка не меняется автоматически |
| Ошибка доставки critical | Устойчивая задача, retry/dedup, получатель и эскалация; release отдельно |
| Неизвестный протокол анализатора | Отдельный BLOCKED-пункт подключения; разработка общего контракта продолжается |
| Нет среды для gate/staging | Сохранить Draft и честный NOT_RUN; продолжать допустимую изолированную работу, не объявлять готовность |
| Разные FE/API версии | Проверить точные SHA/schema/aliases в P10; один Vercel READY не означает готовый контур |
| Производственный откат удалит новые записи | Расширяющие миграции, совместимый код и восстановление/forward fix; без разрушительного downgrade клинических данных |

Для самого планового PR восстановление тривиально: закрыть его или удалить только добавленный документ отдельным изменением; runtime не затронут. Для будущего выпуска конкретные шаги восстановления описываются и проверяются на синтетическом staging до release.
