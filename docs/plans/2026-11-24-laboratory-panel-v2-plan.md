### Подтверждение исходных данных

- `Admin` и `Lab` работают в `/lab`. Врач читает лабораторные отчёты через серверную проверку доступа к визиту. Назначения на полномочия проверяющего и выпускающего требуют подтверждения клиники.
- Список типов исследований и единиц задан каталогом, шаблонами и каноническими назначениями. Фактический объём смены, материалы и SLA по методикам требуют подтверждения клиники.
- Владелец уточнил, что модели анализаторов различаются между клиниками. Общий контракт и ручной/CSV-импорт входят в v2. Фактический перечень приборов и форматов обмена фиксируется для каждой клиники отдельно. Для инвентаризации используется существующая карточка оборудования `DeviceInfo` с типом, производителем и моделью.
- Для конкретного прибора нужны согласованный протокол, сопоставление с кодами аналитов и единицами каталога клиники, синтетический пример обмена и подтверждение на её стенде. Общий импорт принимает канонические строки и проходит отдельную приёмку.
- Пороги из seed и текущий канал доставки не подтверждают клиническое утверждение. Уполномоченное лицо должно утвердить матрицу выпуска, референсы и маршруты эскалации.

### Совместимость и восстановление

- Расширение схемы проходит через `0104_lab_specimens`, `0105_lab_review_release`, `0106_lab_result_contracts`, `0107_lab_rejection_reason`, `0108_lab_draft_replay`, `0109_lab_create_receipt` и объединяющую `0110_lab_emr_merge`. Квитанции связывают повторы сохранения и создания с точным запросом. Объединяющая ревизия сохраняет обе цепочки миграций. Новые связи и события записываются по мере работы. Отсутствующие исторические пробы, исполнители, QC, даты и категории отклонения остаются неизвестными.
- `LAB_MANAGED_RELEASE_ENABLED` по умолчанию выключен. После утверждения политики назначить существующие полномочия `lab:review`, `lab:release`, `lab:qc` конкретным группам. На синтетических данных проверить разделение обязанностей и локальный канал. Включение действует на новые бланки. Незавершённые управляемые бланки сохраняют свой режим.
- Обратный переход использует совместимый код и выключение нового режима для дальнейшего создания бланков. При наличии записей сохранять расширенную схему, использовать прямое исправление или восстановление из проверенной резервной копии в отдельную БД. Не удалять выпущенные документы, пробы, события или квитанции импорта.
- Пакетный ввод и CSV проходят предварительную проверку, затем запись по просмотренной версии. CSV использует UTF-8, стабильный UUID сообщения и поля `message_id,report_instance_id,specimen_barcode,analyte_code,unit_code,value,method_code,observed_at`. Опциональный столбец `instrument_flags` содержит JSON-массив кодов прибора. Ошибка одной группы `message_id` не блокирует корректные группы. Показатели CSV требуют кодов в опубликованном шаблоне. Ручной пакетный ввод поддерживает также точный ключ поля старого шаблона. Отклонённые при записи строки оставляют в общем аудите источник и код ошибки без значения результата и данных пациента. Подключение прибора выполняется адаптером для его подтверждённого протокола и каталога конкретной клиники.
- В API импорта у показателя могут быть исходные коды предупреждений прибора. Сохранённый показатель связан с квитанцией импорта. При переносе неизменённого измерения в исправление связь сохраняется, при ручной замене снимается. Трактовку кодов и правила работы с ними утверждает клиника.
- Метрики рабочего списка используют те же серверные критерии. Среднее время считается по явно связанным парам «проба–первичный отчёт» с известными временем получения и выпуска. Канон не выводит SLA при отсутствующем назначенном сроке.

### Решение о готовности

Статус выпуска — **NO-GO**. Для решения по общему контуру нужны утверждённая клиническая матрица полномочий, референсы и критические маршруты, а также полный staging по runbook на окончательном SHA. Фактические подключения входят в приёмку конкретной клиники по её согласованному перечню приборов и форматов. Порядок выкладки после этих подтверждений — расширение схемы, совместимое обновление API и фронтенда, затем назначение полномочий и включение управляемого выпуска.

Изолированная приёмка подтвердила вход и доступ лаборанта к рабочему списку и пробам. Проверены ограничения доступа врача, регистратора и неавторизованного пользователя. На отдельном PostgreSQL восстановлены данные 20 таблиц Lab, RLS восьми новых таблиц, связь пробы с отчётом и все четыре события её обработки.

## 2. Продуктовый результат и обязательный объём

Пользователь открывает лабораторию и сразу видит все исследования, требующие действий. Он находит пациента/заказ/пробу, вводит результаты без потери фокуса, видит применимые единицы и референсы, понимает препятствия к выпуску и может проследить результат до врача и последующего исправления.

Обязательные сценарии новой панели:

| Сценарий | Ожидаемый результат |
|---|---|
| Начало смены | Видны незавершённые исследования прошлых дней, срочные и просроченные; счётчики отражают полную область |
| Приём материала | Проба имеет собственную идентичность, материал, контейнер и документированные события |
| Ввод по пациенту | Рабочий список остаётся доступным рядом с выбранным заказом; идентификация закреплена |
| Массовый ввод | Однотипные исследования нескольких проб вводятся с явным сопоставлением и проверкой каждой строки |
| Проверка | Видны полнота, состояние пробы, применимый QC, отклонения, динамика и точная версия данных |
| Выпуск | Сервер фиксирует фактического сотрудника, время, неизменяемую версию и разрешённые действия |
| Частичная готовность | Видно, какие исследования выпущены и что удерживает остальные |
| Критический результат | Одно правило оценки используется в интерфейсе и уведомлениях; есть ответственный, попытки связи, подтверждение и эскалация |
| Исправление | Создаётся новая связанная версия с причиной и автором; предыдущая сохраняется |
| Выдача | PDF, ЭМК и интеграционные представления согласованы по значению, единице, оценке и версии |
| Проблема сети | Ввод не теряется, состояние сохранения достоверно, конфликт не маскируется |
| Русский/узбекский | Перевод не меняет смысл результата, статусы и основные сценарии доступны в поддерживаемых языках |

Роли: лаборант — пробы и ввод; уполномоченный проверяющий — проверка и выпуск; руководитель лаборатории — правила, QC, исключения и показатели; врач — результаты и подтверждение критического сообщения. Полномочия уточняются в существующей ролевой модели; новая роль не вводится только ради названия вкладки.

## 5. Целевой экран и модель взаимодействия

| Область | Содержимое |
|---|---|
| Верхняя строка | Поиск/сканирование, рабочая область, фильтры, состояние соединения |
| Рабочий список | Пациент, заказ, исследование/проба, срок, приоритет, прогресс, причина задержки |
| Закреплённая шапка | ФИО, дата рождения/возраст, ID пациента/заказа/отчёта, проба, время взятия |
| Таблица результатов | Показатель, значение, единица, применимый референс, оценка, предыдущее значение |
| Контекст по запросу | История и график сопоставимых результатов, сведения о пробе, QC, комментарии, коммуникация |
| Действия | Достоверный статус сохранения, проверка, выпуск, PDF, исправление — по серверным полномочиям |

Desktop: список и редактор рядом; контекст раскрывается по необходимости. Mobile: последовательный переход с сохранением выбранного заказа, фильтров и позиции. Шаблоны/правила/администрирование — отдельная рабочая область. ИИ — дополнительный инструмент по запросу, без заполнения измерений или самостоятельного выпуска. Сохранить `requires_doctor_confirmation` для медицинских AI-ответов.

Основные состояния разделены:

- Заказ: состав назначений, частичная/полная готовность, отмена конкретного исследования с причиной.
- Проба: ожидается, взята, получена, принята, удержана, отклонена, повторно взята.
- Результат: отсутствует, введён, сохранён, оценён, проверен, выпущен, заменён исправленной версией.
- Коммуникация: требуется, задача создана, попытка/доставка, подтверждено, эскалация.

## 10. Риски, ограничения и восстановление

| Риск | Действие в плане |
|---|---|
| Новые правила изменяют смысл старого результата | Сохранять historical snapshots; исправлять через новую ревизию и прослеживаемое уведомление |
| Изменение catalog/unit ломает потребителей | Общий resolver, совместимые DTO/адаптеры, паритет V19 |
| Миграция требует недостоверного backfill | Хранить unknown, выделять сомнительные записи; не выдумывать provenance |
| Конфликт с параллельной работой в repo | Свежая база, ownership/scope, синхронизация и единый integration PR |
| Late response переносит контекст | Identity guards и V10; выбранная строка не меняется автоматически |
| Ошибка доставки critical | Устойчивая задача, retry/dedup, получатель и эскалация; release отдельно |
| Неизвестный протокол анализатора | Отдельный BLOCKED-пункт подключения; разработка общего контракта продолжается |
| Нет среды для gate/staging | Сохранить Draft и честный NOT_RUN; продолжать допустимую изолированную работу, не объявлять готовность |
| Разные FE/API версии | Проверить точные SHA/schema/aliases в P10; один Vercel READY не означает готовый контур |
| Производственный откат удалит новые записи | Расширяющие миграции, совместимый код и восстановление/forward fix; без разрушительного downgrade клинических данных |

Для самого планового PR восстановление тривиально: закрыть его или удалить только добавленный документ отдельным изменением; runtime не затронут. Для будущего выпуска конкретные шаги восстановления описываются и проверяются на синтетическом staging до release.
