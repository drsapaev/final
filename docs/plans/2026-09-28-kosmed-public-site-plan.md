## 1. Цель и границы

Сделать публичный сайт для пациентов: рассказать об услугах и врачах клиники, помочь найти адрес и связаться, а затем — записаться.

Сайт будет частью существующего React/Vite-приложения, но получит отдельный публичный интерфейс и свои маршруты. Внутренние панели сотрудников останутся в МИС Clinic OS. Сайт не должен создавать собственные таблицы записей или самостоятельно определять расписание, доступность врача, цену и статус приёма: эти данные и правила должны оставаться под управлением backend.

Это соответствует текущей структуре проекта: `/` сейчас ведёт на страницу Clinic OS, а текущие метаданные страницы описывают продукт, не клинику ([Landing.tsx](../../frontend/src/pages/Landing.tsx), [index.html](../../frontend/index.html)). В репозитории есть шаблоны и pipeline Landing Factory, но готового сайта Doktor KosMed пока нет ([README фабрики](../../.ai-factory/landing/README.md)).

## 2. Этап 0 — подтвердить данные и ключевые решения

До дизайна и разработки собрать одобренные клиникой сведения:

- официальное название, логотип, домен и актуальные контакты;
- адрес, часы работы, инструкции для посетителей и ссылку на карту;
- действующие услуги и цены с датой актуальности;
- список врачей, специальности, квалификации и разрешённые к публикации фото;
- реальные отзывы, сертификаты и фотографии клиники, если их решено публиковать;
- тексты об услугах и врачах, проверенные ответственным от клиники.

Отдельно зафиксировать два решения:

1. **Языки.** Рекомендация для старта — русский и узбекский в латинице; узбекскую кириллицу включить, если клиника действительно будет поддерживать её в контенте. Само приложение поддерживает несколько локалей, но это не означает, что сайт автоматически получит готовые переводы ([useTranslation.ts](../../frontend/src/i18n/useTranslation.ts)). (Решено 2026-09-28: русский и узбекский латиницей, по умолчанию — узбекский; см. раздел 9.)
2. **Что означает запись.** Выбрать между подтверждённым бронированием свободного времени и заявкой, после которой регистратор связывается с пациентом. Не показывать сообщение «запись подтверждена», если backend только принял заявку. (Решено 2026-09-28: оба режима с настройкой из панели админа — см. раздел 8.)

Также составить карту источников данных: для каждой цены, услуги, врача и доступного времени указать, кто отвечает за актуальность и где находится источник истины. Не выводить на сайт закрытые данные МИС напрямую.

**Результат этапа:** утверждённый контентный бриф, языки, структура сайта, схема онлайн-записи и список доступных материалов.

## 3. Этап 1 — публичная структура и основная информация

Создать публичную оболочку `PublicLayout` отдельно от интерфейса сотрудников. Для начала предусмотреть такие страницы:

| Раздел | Назначение |
|---|---|
| `/` | Главная: чем помогает клиника, ключевые услуги, адрес и действия для связи |
| `/services` и `/services/:slug` | Список услуг и отдельные страницы подтверждённых направлений |
| `/doctors` и `/doctors/:slug` | Список врачей и профили с согласованными сведениями |
| `/prices` | Актуальные цены и пояснения |
| `/about` | Информация о клинике |
| `/contacts` | Телефон, график, адрес, карта и маршрут |
| `/faq` | Ответы на частые вопросы |
| `/reviews` | Только реальные, проверенные отзывы |
| `/privacy` | Информация о данных и обработке форм |

Для языков использовать отдельные индексируемые адреса: русский — без префикса, например `/services`; узбекский — с префиксом, например `/uz/services`. Если включается узбекская кириллица, определить для неё отдельный префикс. Существующие публичные маршруты очереди и подтверждения визита нужно учесть в реестре маршрутов, чтобы новая структура их не перекрыла ([routeRegistry.ts](../../frontend/src/routing/routeRegistry.ts)).

Главная должна иметь одно основное действие — «Записаться» или «Оставить заявку», в зависимости от решения этапа 0. Телефон и Telegram могут быть дополнительными действиями. На мобильном предусмотреть удобную панель связи и записи.

**Не включать в первый выпуск** неподтверждённые специальности, обещания времени ответа, придуманные отзывы и истории пациентов. Кейсы «до/после» оставить за пределами MVP.

## 4. Этап 2 — SEO, переводы и публичные данные

В текущем `index.html` общие title, description и Open Graph-теги Clinic OS. Для публичного сайта их недостаточно: у страницы каждой услуги, врача и контактов должны быть свои метаданные.

Сначала проверить, можно ли генерировать HTML для публичных маршрутов на этапе сборки в существующем Vite-приложении. Цель проверки — чтобы прямой запрос к странице услуги отдавал её содержимое и метаданные, а не только общую оболочку приложения. Если это не получается надёжно, выбрать подходящий способ серверного или статического рендеринга. Само добавление маршрутов React Router не считать выполненной SEO-работой.

Для опубликованных страниц подготовить:

- уникальные заголовки, описания, canonical и Open Graph;
- `sitemap.xml` и корректный `robots.txt`;
- связи между переводами страниц для поисковых систем;
- структурированные данные только с подтверждёнными сведениями о клинике, врачах и услугах;
- понятные хлебные крошки и перелинковку между услугами, врачами, ценами и записью.

Для сведений, которые часто меняются — например, расписания или цены, — перед реализацией определить безопасный источник. Если потребуется backend endpoint, он должен возвращать только публично разрешённые поля. Не использовать endpoint для внутренней панели как публичный.

## 5. Этап 3 — онлайн-запись

В существующем коде создание записи требует авторизации и сейчас не является готовым публичным потоком: это видно в appointment API и мобильном API ([appointments.py](../../backend/app/api/v1/endpoints/appointments.py), [mobile_api.py](../../backend/app/api/v1/endpoints/mobile_api.py)). Поэтому форма сайта не должна напрямую вызывать внутренний endpoint для сотрудников.

Если выбрано подтверждённое бронирование, добавить отдельный публичный backend-контракт. Он должен использовать существующие правила и проверки backend для врача и свободного времени. Проверить, как обрабатываются одновременные попытки занять один слот, повторная отправка формы, неверный или занятый слот и сбой после отправки.

Ожидаемый путь пациента:

1. выбрать услугу;
2. выбрать врача и доступное время;
3. ввести необходимые контактные данные;
4. отправить запрос;
5. получить результат, соответствующий фактическому статусу записи.

Успешный экран `/appointment/success` показывать только после ответа backend, подтверждающего именно тот результат, который обещает сайт. Если на первом этапе доступна только заявка, экран должен говорить «Заявка отправлена, клиника свяжется с вами», а не «Визит записан».

Если запись откладывается, первый выпуск сайта может вести на телефон или Telegram и содержать отдельную форму обратного звонка. Это позволит запустить информационный сайт без ложного обещания онлайн-бронирования.

## 6. Этап 4 — аналитика, приватность и качество

Сначала утвердить минимальный список событий, нужных клинике для понимания работы сайта: например, нажатие на телефон, открытие формы и отправка формы. Не отправлять в аналитику имя, телефон, ID записи, врача, специальность, услугу или другие сведения, которые могут раскрывать информацию о здоровье. Выбрать инструмент аналитики и правила хранения данных после проверки требований клиники.

Эта аналитика измеряет использование публичного сайта, а не внутреннюю статистику очереди. План не включает публичный экран с текущей позицией талона или временем ожидания. Действующие `/queue/join` и `/q/:publicCode` сохраняются как сценарии входа в очередь; их наличие не означает отображение живого состояния очереди на сайте. Если клинике понадобится такой экран, его следует согласовать отдельным требованием с отдельной проверкой публичного контракта и приватности.

Перед публикацией проверить:

- работу всех маршрутов напрямую по URL, на мобильных и на поддерживаемых языках;
- корректность телефонов, ссылок на Telegram, адреса, цен и сведений о врачах;
- уникальные SEO-метаданные, индексируемые страницы, карту сайта и ссылки между переводами;
- ошибки и отказы формы, включая занятое время и недоступность backend;
- доступность, клавиатурную навигацию, контрастность и альтернативные тексты изображений;
- отсутствие личных данных пациентов в аналитике, логах и сообщениях об ошибках;
- аналитику без передачи медицинских и персональных данных.

Для сайта провести маршрутную, SEO-, доступностную и мобильную проверки. Если при запуске заявляется, что система работает или развёртывание завершено, соблюдать репозиторный [чеклист staging-валидации](../runbooks/STAGING_VALIDATION.md) и сообщить, какие проверки прошли и какие нет.

## Критерии готовности

Сайт можно считать готовым к публикации, когда:

- клиника утвердила все отображаемые сведения и переводы;
- пациент может найти услугу, врача, цену и контакты;
- каждая публичная страница имеет подходящие ей метаданные и доступна по прямой ссылке;
- форма не заявляет о подтверждённой записи, если backend её не подтвердил;
- при полноценной онлайн-записи новая запись создаётся в существующей МИС и конфликт слота не приводит к ложному успеху;
- аналитика не передаёт персональные или медицинские сведения;
- публичные страницы визуально и функционально отделены от панелей сотрудников.

## 7. Дополнение (2026-09-28): сайт берёт данные из Clinic OS, публикацией управляет админка

Да. Сайт может брать данные из Clinic OS, а админка может стать местом, где сотрудники управляют тем, что видно пациентам. Это лучше, чем отдельно поддерживать цены, услуги и врачей в коде сайта.

Но после проверки проекта вывод такой: часть нужных данных уже есть, а готового публичного интерфейса для всего сайта и анонимной записи пока нет.

### Что уже есть

| Данные или функция | Состояние в приложении | Что понадобится сайту |
|---|---|---|
| Название клиники, адрес, телефон, email, логотип | Есть в настройках клиники | Отдельный безопасный публичный API: нынешние настройки доступны авторизованному персоналу |
| Услуги и цены | Редактируются в каталоге услуг. Список услуг уже можно получить без входа | Публичный ответ должен показывать только разрешённые услуги и поля: общий каталог содержит также служебные данные для очередей и маршрутизации |
| Врачи | Админка управляет базовыми данными: врач, специальность, отделение, активность | Нужны публичная выдача и, если требуется, редактируемые био, фото, описание и адрес страницы |
| Расписание и лимиты очереди | В приложении есть расписания и настройки очереди | Нужно отдельно определить, какие сведения можно показывать пациенту и как получать актуальную доступность |
| Запись на приём по дате и времени | Бизнес-логика и хранение записей в МИС есть, но текущие API записи и просмотра свободного времени требуют авторизации | Для анонимного посетителя сайта нужен отдельный публичный сценарий записи, который использует существующие правила backend |

Например, настройки клиники сейчас доступны через закрытый endpoint, а GET /services открыт, но возвращает технические поля, которые сайту не нужны. Поэтому сайт следует подключать к специальному публичному представлению данных, а не напрямую к административным интерфейсам ([настройки клиники](../../backend/app/api/v1/endpoints/admin_clinic.py), [каталог услуг](../../backend/app/api/v1/endpoints/services_ep/_services.py), [поля ответа услуг](../../backend/app/api/v1/endpoints/services_ep/_helpers.py)).

### Важно различать два вида онлайн-записи

В приложении уже настраиваются время открытия и лимиты QR-очереди на текущий день. Это возможность занять место в очереди, а не обязательно забронировать приём у врача на выбранную дату и время. Для плановых визитов используются расписания и appointment API; существующее создание записи сайта без входа не обслуживает ([настройки очереди](../../frontend/src/components/admin/QueueSettings.tsx), [запись с требованием авторизации](../../backend/app/api/v1/endpoints/appointments.py)).

Обе возможности могут управляться из админки, но для сайта их нужно обозначить и настроить отдельно. Например, выключатель QR-очереди не должен случайно выключать запись на будущие даты, и наоборот.

### Как я бы это спланировал

1. Провести инвентаризацию данных. Для каждой страницы определить, где сейчас редактируются соответствующие сведения: в настройках клиники, каталоге услуг, карточках врачей или расписании. Отметить недостающие поля — например, описание услуги, фотографию врача, публичность и тексты на языках сайта. То, что уже хранится в приложении, повторно вручную вносить не нужно.
2. Добавить в админку управление публикацией. Администратор выбирает, какие услуги и врачи показываются на сайте. Там же редактируются недостающие публичные поля и переводы. Если для них понадобятся новые поля базы, добавить их через Alembic-миграцию, а не хранить копию каталога отдельно.
3. Создать публичное чтение данных в backend. Сайт получает только опубликованные сведения, нужные пациенту: услугу, отображаемое название, цену и информацию о враче. Из ответа исключаются внутренние идентификаторы и поля очередей, учётных записей и персонала. После публикации из админки изменения автоматически появляются на сайте.
4. Подключить сайт и SEO к этим данным. До реализации публичных страниц определить две вещи: как прямой запрос получает HTML с содержимым и метаданными нужной страницы и как правка из админки обновляет HTML, метаданные и sitemap без ручного релиза сайта. Серверное формирование или пререндеринг решают выдачу HTML; обновление кеша решает актуальность и не заменяет рендеринг. Зафиксировать способ и срок обновления, включая снятие с публикации.
5. Отдельно спроектировать запись с сайта. В админке должны настраиваться доступность записи через сайт и допущенные услуги или врачи. Свободные интервалы и итоговое создание записи проверяет backend; новая запись попадает в существующую МИС и видна регистратору. Новую таблицу website_appointments не создавать.
6. Зафиксировать, что получает пациент после отправки. Если запись сразу создаётся и слот закреплён — показать подтверждение. Если запрос должен проверить или подтвердить регистратор — назвать его заявкой и не обещать пациенту забронированный приём. Для публичного сценария также нужно определить проверку телефона, защиту от повторных и автоматических заявок и сопоставление с существующей карточкой пациента.
7. Проверить весь путь целиком. Изменить цену или скрыть врача в админке → убедиться, что сайт показывает новые сведения; отключить запись → проверить, что backend тоже перестал принимать её; занять один слот из двух одновременных запросов → убедиться, что подтверждён только один; созданную запись найти в существующей панели регистратора.

Схему можно представить так:

```
Админка Clinic OS
  ├─ услуги, цены, врачи, данные клиники
  ├─ публикация на сайте
  └─ настройки канала записи
           ↓
Backend Clinic OS — источник данных и правил
  ├─ публичное чтение одобренных данных
  └─ проверка слотов и создание записи
           ↓
Публичный сайт
           ↓
Та же запись отображается в рабочем интерфейсе клиники
```

Итог: да, это реализуемо, и такой вариант лучше соответствует вашему процессу. В сохранённом плане стоит сделать главным принципом «админка Clinic OS управляет публичными данными сайта». Первый этап тогда — не сбор всех цен и врачей вручную, а аудит того, что админка уже умеет редактировать, и список недостающих публичных полей. Главный вопрос, который ещё надо решить для записи: сайт сразу подтверждает свободный слот или сначала отправляет заявку регистратору (решено 2026-09-28 — оба режима с настройкой из панели админа; см. раздел 8).

## 8. Решение по онлайн-записи (2026-09-28): оба режима, настройка из панели админа

Главный вопрос раздела 7 решён: публичная запись поддерживает **оба режима**, а какой из них действует, задаётся настройкой в панели администратора — в области «настройки канала записи» из схемы раздела 7:

1. **Подтверждение слота сразу.** Backend проверяет свободное время существующими правилами и закрепляет слот; сайт показывает подтверждение записи.
2. **Заявка регистратору.** Backend фиксирует заявку; сайт показывает «Заявка отправлена, клиника свяжется с вами» и не обещает забронированный приём.

Следствия для реализации (в дополнение к разделам 5 и 7):

- публичный контракт записи возвращает явный признак результата — подтверждённая запись или созданная заявка; сайт выбирает экран по ответу backend, а не по локальному состоянию формы;
- ответ backend на момент отправки — источник истины: если режим изменился между загрузкой страницы и отправкой, пациенту показывается фактический результат, а не ранее обещанный;
- настройка режима, доступность записи через сайт и допущенные услуги или врачи управляются из админки и не требуют релиза сайта;
- гранулярность настройки (вся клиника целиком, отдельные услуги или врачи) определяется на этапе аудита данных (раздел 7, шаг 1);
- проверка телефона, защита от повторных и автоматических заявок действуют в обоих режимах;
- в режиме подтверждения новая запись создаётся в существующей МИС и видна регистратору; таблицу `website_appointments` не создаём (раздел 7, шаг 5).

Языки решены — см. раздел 9. Контентный бриф и остальные открытые вопросы перечислены в разделе 6 [актуальной заметки передачи](2026-10-06-kosmed-public-site-handoff.md); согласовать их до зависящей реализации.

## 9. Решение по языкам (2026-09-28): русский и узбекский латиницей, по умолчанию — узбекский

Решение Этапа 0 зафиксировано: сайт запускается на двух языках — **узбекский (латиница) по умолчанию** и русский. Узбекская кириллица не включается.

Следствия для реализации:

- все тексты интерфейса и утверждённый контент (услуги, врачи, страницы) нужны сразу в двух локалях; переводы контента управляются из админки (раздел 7, шаг 2), а не генерируются автоматически;
- требуется уточнить карту URL-адресов: раздел 3 исходно фиксировал «русский — без префикса, узбекский — под /uz/», но выбор узбекского языком по умолчанию означает, что корневые адреса должны отдавать узбекский вариант. Окончательная схема (например, корень — узбекский и `/ru/...` для русского, либо корень — русский с редиректом на `/uz/`) фиксируется в начале Этапа 1: от неё зависят canonical, hreflang и sitemap (раздел 4);
- язык по умолчанию для новых страниц, sitemap и структурированных данных — узбекский;
- инфраструктура локалей в приложении уже есть ([useTranslation.ts](../../frontend/src/i18n/useTranslation.ts)), но она не даёт сайту готовых переводов контента.

Контентный бриф и остальные открытые вопросы перечислены в разделе 6 [актуальной заметки передачи](2026-10-06-kosmed-public-site-handoff.md); выбор языков не закрывает эти решения.
