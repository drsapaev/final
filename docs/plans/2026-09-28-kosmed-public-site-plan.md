## 1. Цель и границы

Сделать публичный сайт для пациентов: рассказать об услугах и врачах клиники, помочь найти адрес и связаться, а затем — записаться.

Сайт будет частью существующего React/Vite-приложения, но получит отдельный публичный интерфейс и свои маршруты. Внутренние панели сотрудников останутся в МИС Clinic OS. Сайт не должен создавать собственные таблицы записей или самостоятельно определять расписание, доступность врача, цену и статус приёма: эти данные и правила должны оставаться под управлением backend.

Это соответствует текущей структуре проекта: `/` сейчас ведёт на страницу Clinic OS, а текущие метаданные страницы описывают продукт, не клинику ([Landing.tsx](../../frontend/src/pages/Landing.tsx), [index.html](../../frontend/index.html)). В репозитории есть шаблоны и pipeline Landing Factory, но готового сайта Doktor KosMed пока нет ([README фабрики](../../.ai-factory/landing/README.md)).

## 2. Этап 0 — подтвердить данные и ключевые решения

До дизайна и разработки собрать одобренные клиникой сведения:

- официальное название, логотип, домен и актуальные контакты;
- адрес, часы работы, инструкции для посетителей и ссылку на карту;
- действующие услуги и цены с датой актуальности;
- список врачей, специальности, квалификации и разрешённые к публикации фото;
- реальные отзывы, сертификаты и фотографии клиники, если их решено публиковать;
- тексты об услугах и врачах, проверенные ответственным от клиники.

Отдельно зафиксировать два решения:

1. **Языки.** Рекомендация для старта — русский и узбекский в латинице; узбекскую кириллицу включить, если клиника действительно будет поддерживать её в контенте. Само приложение поддерживает несколько локалей, но это не означает, что сайт автоматически получит готовые переводы ([useTranslation.ts](../../frontend/src/i18n/useTranslation.ts)). (Решено 2026-09-28: русский и узбекский латиницей, по умолчанию — узбекский; см. раздел 9.)
2. **Что означает запись.** Выбрать между подтверждённым бронированием свободного времени и заявкой, после которой регистратор связывается с пациентом. Не показывать сообщение «запись подтверждена», если backend только принял заявку. (Решено 2026-09-28: оба режима с настройкой из панели админа — см. раздел 8.)

Также составить карту источников данных: для каждой цены, услуги, врача и доступного времени указать, кто отвечает за актуальность и где находится источник истины. Не выводить на сайт закрытые данные МИС напрямую.

**Результат этапа:** утверждённый контентный бриф, языки, структура сайта, схема онлайн-записи и список доступных материалов.

## 3. Этап 1 — публичная структура и основная информация

Создать публичную оболочку `PublicLayout` отдельно от интерфейса сотрудников. Для начала предусмотреть такие страницы:

| Раздел | Назначение |
|---|---|
| `/` | Главная: чем помогает клиника, ключевые услуги, адрес и действия для связи |
| `/services` и `/services/:slug` | Список услуг и отдельные страницы подтверждённых направлений |
| `/doctors` и `/doctors/:slug` | Список врачей и профили с согласованными сведениями |
| `/prices` | Актуальные цены и пояснения |
| `/about` | Информация о клинике |
| `/contacts` | Телефон, график, адрес, карта и маршрут |
| `/faq` | Ответы на частые вопросы |
| `/reviews` | Только реальные, проверенные отзывы |
| `/privacy` | Информация о данных и обработке форм |

Для языков использовать отдельные индексируемые адреса: узбекский латиницей — без префикса, например `/services`; русский — под `/ru/`, например `/ru/services`. Обе локали одной услуги или врача используют один slug. Узбекская кириллица в первый выпуск не входит. Существующие публичные маршруты очереди и подтверждения визита нужно учесть в реестре маршрутов, чтобы новая структура их не перекрыла ([routeRegistry.ts](../../frontend/src/routing/routeRegistry.ts)); подробная карта локалей — в разделе 11.

Главная должна иметь одно основное действие — «Записаться» или «Оставить заявку», в зависимости от решения этапа 0. Телефон и Telegram могут быть дополнительными действиями. На мобильном предусмотреть удобную панель связи и записи.

**Не включать в первый выпуск** неподтверждённые специальности, обещания времени ответа, придуманные отзывы и истории пациентов. Кейсы «до/после» оставить за пределами MVP.

## 4. Этап 2 — SEO, переводы и публичные данные

В текущем `index.html` общие title, description и Open Graph-теги Clinic OS. Для публичного сайта их недостаточно: у страницы каждой услуги, врача и контактов должны быть свои метаданные.

Сначала проверить, можно ли генерировать HTML для публичных маршрутов на этапе сборки в существующем Vite-приложении. Цель проверки — чтобы прямой запрос к странице услуги отдавал её содержимое и метаданные, а не только общую оболочку приложения. Если это не получается надёжно, выбрать подходящий способ серверного или статического рендеринга. Само добавление маршрутов React Router не считать выполненной SEO-работой.

Для опубликованных страниц подготовить:

- уникальные заголовки, описания, canonical и Open Graph;
- `sitemap.xml` и корректный `robots.txt`;
- связи между переводами страниц для поисковых систем;
- структурированные данные только с подтверждёнными сведениями о клинике, врачах и услугах;
- понятные хлебные крошки и перелинковку между услугами, врачами, ценами и записью.

Для сведений, которые часто меняются — например, расписания или цены, — перед реализацией определить безопасный источник. Если потребуется backend endpoint, он должен возвращать только публично разрешённые поля. Не использовать endpoint для внутренней панели как публичный.

## 5. Этап 3 — онлайн-запись

В существующем коде создание записи требует авторизации и сейчас не является готовым публичным потоком: это видно в appointment API и мобильном API ([appointments.py](../../backend/app/api/v1/endpoints/appointments.py), [mobile_api.py](../../backend/app/api/v1/endpoints/mobile_api.py)). Поэтому форма сайта не должна напрямую вызывать внутренний endpoint для сотрудников.

Если выбрано подтверждённое бронирование, добавить отдельный публичный backend-контракт. Он должен использовать существующие правила и проверки backend для врача и свободного времени. Проверить, как обрабатываются одновременные попытки занять один слот, повторная отправка формы, неверный или занятый слот и сбой после отправки.

Ожидаемый путь пациента:

1. выбрать услугу;
2. выбрать врача и доступное время;
3. ввести необходимые контактные данные;
4. отправить запрос;
5. получить результат, соответствующий фактическому статусу записи.

Успешный экран `/appointment/success` показывать только после ответа backend, подтверждающего именно тот результат, который обещает сайт. Если на первом этапе доступна только заявка, экран должен говорить «Заявка отправлена, клиника свяжется с вами», а не «Визит записан».

Если запись откладывается, первый выпуск сайта может вести на телефон или Telegram и содержать отдельную форму обратного звонка. Это позволит запустить информационный сайт без ложного обещания онлайн-бронирования.

## 6. Этап 4 — аналитика, приватность и качество

Сначала утвердить минимальный список событий, нужных клинике для понимания работы сайта: например, нажатие на телефон, открытие формы и отправка формы. Не отправлять в аналитику имя, телефон, ID записи, врача, специальность, услугу или другие сведения, которые могут раскрывать информацию о здоровье. Выбрать инструмент аналитики и правила хранения данных после проверки требований клиники.

Эта аналитика измеряет использование публичного сайта, а не внутреннюю статистику очереди. План не включает публичный экран с текущей позицией талона или временем ожидания. Действующие `/queue/join` и `/q/:publicCode` сохраняются как сценарии входа в очередь; их наличие не означает отображение живого состояния очереди на сайте. Если клинике понадобится такой экран, его следует согласовать отдельным требованием с отдельной проверкой публичного контракта и приватности.

Перед публикацией проверить:

- работу всех маршрутов напрямую по URL, на мобильных и на поддерживаемых языках;
- корректность телефонов, ссылок на Telegram, адреса, цен и сведений о врачах;
- уникальные SEO-метаданные, индексируемые страницы, карту сайта и ссылки между переводами;
- ошибки и отказы формы, включая занятое время и недоступность backend;
- доступность, клавиатурную навигацию, контрастность и альтернативные тексты изображений;
- отсутствие личных данных пациентов в аналитике, логах и сообщениях об ошибках;
- аналитику без передачи медицинских и персональных данных.

Для сайта провести маршрутную, SEO-, доступностную и мобильную проверки. Если при запуске заявляется, что система работает или развёртывание завершено, соблюдать репозиторный [чеклист staging-валидации](../runbooks/STAGING_VALIDATION.md) и сообщить, какие проверки прошли и какие нет.

## Критерии готовности

Сайт можно считать готовым к публикации, когда:

- клиника утвердила все отображаемые сведения и переводы;
- пациент может найти услугу, врача, цену и контакты;
- каждая публичная страница имеет подходящие ей метаданные и доступна по прямой ссылке;
- форма не заявляет о подтверждённой записи, если backend её не подтвердил;
- при полноценной онлайн-записи новая запись создаётся в существующей МИС и конфликт слота не приводит к ложному успеху;
- аналитика не передаёт персональные или медицинские сведения;
- публичные страницы визуально и функционально отделены от панелей сотрудников.

## 7. Дополнение (2026-09-28): сайт берёт данные из Clinic OS, публикацией управляет админка

Да. Сайт может брать данные из Clinic OS, а админка может стать местом, где сотрудники управляют тем, что видно пациентам. Это лучше, чем отдельно поддерживать цены, услуги и врачей в коде сайта.

Но после проверки проекта вывод такой: часть нужных данных уже есть, а готового публичного интерфейса для всего сайта и анонимной записи пока нет.

### Что уже есть

| Данные или функция | Состояние в приложении | Что понадобится сайту |
|---|---|---|
| Название клиники, адрес, телефон, email, логотип | Есть в настройках клиники | Отдельный безопасный публичный API: нынешние настройки доступны авторизованному персоналу |
| Услуги и цены | Редактируются в каталоге услуг. Список услуг уже можно получить без входа | Публичный ответ должен показывать только разрешённые услуги и поля: общий каталог содержит также служебные данные для очередей и маршрутизации |
| Врачи | Админка управляет базовыми данными: врач, специальность, отделение, активность | Нужны публичная выдача и, если требуется, редактируемые био, фото, описание и адрес страницы |
| Расписание и лимиты очереди | В приложении есть расписания и настройки очереди | Нужно отдельно определить, какие сведения можно показывать пациенту и как получать актуальную доступность |
| Запись на приём по дате и времени | Бизнес-логика и хранение записей в МИС есть, но текущие API записи и просмотра свободного времени требуют авторизации | Для анонимного посетителя сайта нужен отдельный публичный сценарий записи, который использует существующие правила backend |

Например, настройки клиники сейчас доступны через закрытый endpoint, а GET /services открыт, но возвращает технические поля, которые сайту не нужны. Поэтому сайт следует подключать к специальному публичному представлению данных, а не напрямую к административным интерфейсам ([настройки клиники](../../backend/app/api/v1/endpoints/admin_clinic.py), [каталог услуг](../../backend/app/api/v1/endpoints/services_ep/_services.py), [поля ответа услуг](../../backend/app/api/v1/endpoints/services_ep/_helpers.py)).

### Важно различать два вида онлайн-записи

В приложении уже настраиваются время открытия и лимиты QR-очереди на текущий день. Это возможность занять место в очереди, а не обязательно забронировать приём у врача на выбранную дату и время. Для плановых визитов используются расписания и appointment API; существующее создание записи сайта без входа не обслуживает ([настройки очереди](../../frontend/src/components/admin/QueueSettings.tsx), [запись с требованием авторизации](../../backend/app/api/v1/endpoints/appointments.py)).

Обе возможности могут управляться из админки, но для сайта их нужно обозначить и настроить отдельно. Например, выключатель QR-очереди не должен случайно выключать запись на будущие даты, и наоборот.

### Как я бы это спланировал

1. Провести инвентаризацию данных. Для каждой страницы определить, где сейчас редактируются соответствующие сведения: в настройках клиники, каталоге услуг, карточках врачей или расписании. Отметить недостающие поля — например, описание услуги, фотографию врача, публичность и тексты на языках сайта. То, что уже хранится в приложении, повторно вручную вносить не нужно.
2. Добавить в админку управление публикацией. Администратор выбирает, какие услуги и врачи показываются на сайте. Там же редактируются недостающие публичные поля и переводы. Если для них понадобятся новые поля базы, добавить их через Alembic-миграцию, а не хранить копию каталога отдельно.
3. Создать публичное чтение данных в backend. Сайт получает только опубликованные сведения, нужные пациенту: услугу, отображаемое название, цену и информацию о враче. Из ответа исключаются внутренние идентификаторы и поля очередей, учётных записей и персонала. После публикации из админки изменения автоматически появляются на сайте.
4. Подключить сайт и SEO к этим данным. До реализации публичных страниц определить две вещи: как прямой запрос получает HTML с содержимым и метаданными нужной страницы и как правка из админки обновляет HTML, метаданные и sitemap без ручного релиза сайта. Серверное формирование или пререндеринг решают выдачу HTML; обновление кеша решает актуальность и не заменяет рендеринг. Зафиксировать способ и срок обновления, включая снятие с публикации.
5. Отдельно спроектировать запись с сайта. В админке должны настраиваться доступность записи через сайт и допущенные услуги или врачи. Свободные интервалы и итоговое создание записи проверяет backend; новая запись попадает в существующую МИС и видна регистратору. Новую таблицу website_appointments не создавать.
6. Зафиксировать, что получает пациент после отправки. Если запись сразу создаётся и слот закреплён — показать подтверждение. Если запрос должен проверить или подтвердить регистратор — назвать его заявкой и не обещать пациенту забронированный приём. Для публичного сценария также нужно определить проверку телефона, защиту от повторных и автоматических заявок и сопоставление с существующей карточкой пациента.
7. Проверить весь путь целиком. Изменить цену или скрыть врача в админке → убедиться, что сайт показывает новые сведения; отключить запись → проверить, что backend тоже перестал принимать её; занять один слот из двух одновременных запросов → убедиться, что подтверждён только один; созданную запись найти в существующей панели регистратора.

Схему можно представить так:

```
Админка Clinic OS
  ├─ услуги, цены, врачи, данные клиники
  ├─ публикация на сайте
  └─ настройки канала записи
           ↓
Backend Clinic OS — источник данных и правил
  ├─ публичное чтение одобренных данных
  └─ проверка слотов и создание записи
           ↓
Публичный сайт
           ↓
Та же запись отображается в рабочем интерфейсе клиники
```

Итог: да, это реализуемо, и такой вариант лучше соответствует вашему процессу. В сохранённом плане стоит сделать главным принципом «админка Clinic OS управляет публичными данными сайта». Первый этап тогда — не сбор всех цен и врачей вручную, а аудит того, что админка уже умеет редактировать, и список недостающих публичных полей. Главный вопрос, который ещё надо решить для записи: сайт сразу подтверждает свободный слот или сначала отправляет заявку регистратору (решено 2026-09-28 — оба режима с настройкой из панели админа; см. раздел 8).

## 8. Решение по онлайн-записи (2026-09-28): оба режима, настройка из панели админа

Главный вопрос раздела 7 решён: публичная запись поддерживает **оба режима**, а какой из них действует, задаётся настройкой в панели администратора — в области «настройки канала записи» из схемы раздела 7:

1. **Подтверждение слота сразу.** Backend проверяет свободное время существующими правилами и закрепляет слот; сайт показывает подтверждение записи.
2. **Заявка регистратору.** Backend фиксирует заявку; сайт показывает «Заявка отправлена, клиника свяжется с вами» и не обещает забронированный приём.

Следствия для реализации (в дополнение к разделам 5 и 7):

- публичный контракт записи возвращает явный признак результата — подтверждённая запись или созданная заявка; сайт выбирает экран по ответу backend, а не по локальному состоянию формы;
- ответ backend на момент отправки — источник истины: если режим изменился между загрузкой страницы и отправкой, пациенту показывается фактический результат, а не ранее обещанный;
- настройка режима, доступность записи через сайт и допущенные услуги или врачи управляются из админки и не требуют релиза сайта;
- гранулярность настройки (вся клиника целиком, отдельные услуги или врачи) определяется на этапе аудита данных (раздел 7, шаг 1);
- проверка телефона, защита от повторных и автоматических заявок действуют в обоих режимах;
- в режиме подтверждения новая запись создаётся в существующей МИС и видна регистратору; таблицу `website_appointments` не создаём (раздел 7, шаг 5).

Языки решены — см. раздел 9. Контентный бриф и остальные открытые вопросы перечислены в разделе 6 [актуальной заметки передачи](2026-10-06-kosmed-public-site-handoff.md); согласовать их до зависящей реализации.

## 11. Подробные требования к публикации, адресам и этапам 2a–4

Этот раздел задаёт целевое поведение для будущей реализации; добавление текста не означает, что поля, API, интерфейс или миграция уже созданы. Последовательность исполнительных PR определяется разделом 6 заметки передачи; номера исходных «Этапов» в разделах 2–6 описывают общую структуру проекта.

### 11.1. Правила публикации

| Объект | Правило для сайта | Что остаётся под управлением МИС |
|---|---|---|
| Услуга | Существующие и новые строки по умолчанию не опубликованы; администратор включает публикацию явно | Активность, цена, длительность, связи с врачами и отделениями |
| Врач | Существующие и новые строки по умолчанию не опубликованы; администратор проверяет профиль и включает публикацию | Пользователь врача, специальность, расписание, операционные ограничения |
| Категория | Показывается, если активна, имеет проверенные названия на двух языках и содержит хотя бы одну доступную на сайте услугу | Существующие `ServiceCategory.name_ru`, `name_uz`, `active` и связи с услугами |
| Возможность записи | Определяется отдельными правилами канала и backend на момент отправки | Режим заявки/брони, доступность времени, идентификация и защита повторной отправки |

Публичная видимость услуги/врача требует одновременно `active=true`, `show_on_website=true` и заполненных обязательных публичных данных. Одного `active=true` недостаточно. Флаг публикации не разрешает автоматически онлайн-запись и не отменяет проверки backend.

Отдельный флаг публикации категории в этап 2a не входит. Пустые категории и категории, содержащие только скрытые или неактивные услуги, исключаются из меню и публичной выдачи категорий. Для услуг без категории и услуг в неактивной категории перед этапом 3 отдельно определить доступность в общем списке и по прямому адресу; производное правило категории не решает этот случай автоматически.

При снятии с публикации карточка исчезает из списков и публичного API; её HTML, метаданные и запись в sitemap должны быть удалены в рамках механизма обновления этапа 4. Публичный запрос к скрытой карточке возвращает `404`, без содержимого черновика. Авторизованный предварительный просмотр не должен использовать общедоступный обход этого правила.

Деактивация услуги/врача прекращает публичную выдачу. Повторное включение `active` само по себе не восстанавливает публикацию: нужна явная операция администратора. Этап 2b должен охватить существующие пути деактивации и повторного включения, сохраняя постоянный адрес карточки.

### 11.2. Стабильный адрес страницы и публичный ключ

Slug — читаемая часть адреса, например `/services/<slug>` или `/doctors/<slug>`. Он является стабильным публичным ключом; backend разрешает его во внутренний ID. `service_code`, `queue_tag`, `department_key` и другие операционные коды не заменяют публичный ключ.

1. До первой публикации slug можно выбрать и изменить в админке. Предложение, вычисленное из названия, требует проверки администратором; изменение названия не пересчитывает slug автоматически.
2. Формат slug: строчные латинские буквы, цифры и одиночные дефисы между частями, без пробелов, путей и завершающего дефиса. Максимальная длина — 160 символов. Пустая строка не является допустимым публичным ключом; у черновика без выбранного адреса хранится `null`.
3. Slug уникален среди всех услуг, включая скрытые и неактивные; для врачей действует отдельная уникальность. Одинаковый slug услуги и врача допустим, поскольку маршруты имеют разные префиксы.
4. Первая успешная публикация фиксирует slug. Переименование, перевод, снятие с публикации и мягкое удаление его не освобождают и не позволяют изменить. Повторная публикация использует прежний адрес.
5. Факт первой публикации сохраняется отдельно от текущего флага видимости. Рабочее поле для этапа 2a — `website_first_published_at`: nullable UTC timestamp, который заполняется один раз в операции публикации этапа 2b и не очищается при скрытии.
6. Backend запрещает изменение фиксированного slug, включая обновление скрытой карточки и конкурентные административные запросы. Уникальность обеспечивается PostgreSQL; обработка конфликтов должна возвращать понятную ошибку админке.
7. Редиректы старых slug и таблица истории адресов в этот вариант не входят. Если понадобится исправить уже опубликованный адрес или физически удалить строку с зарезервированным slug, сначала нужно отдельное решение с сохранением адресной идентичности.

Для списка, страницы и будущей команды записи использовать один публичный ключ одной сущности. Публичный каталог и команда записи не должны по-разному интерпретировать его; публикация не означает наличие свободного времени.

### 11.3. Переводы и готовность контента

Все публичные карточки выпускаются сразу на русском и узбекском латиницей. Тексты создают и проверяют ответственные сотрудники через админку. Машинный перевод или копирование русского текста в узбекское поле не являются автоматическим заполнением миграции.

| Сущность | Источник/поле для этапа 2a | Условие публикации в этапе 2b |
|---|---|---|
| Название услуги на русском | Существующее `Service.name` | Непустое, проверенное название для пациента |
| Название услуги на узбекском | Новое `Service.name_uz` | Непустой проверенный перевод |
| Описание услуги | Новые `description_ru`, `description_uz` | Оба описания заполнены и одобрены клиникой |
| Имя врача | Существующее `User.full_name`, связанное с `Doctor.user_id` | Есть доступное для публикации имя; историческая строка врача без пользователя не публикуется с выдуманным именем |
| Биография врача | Новые `Doctor.bio_ru`, `bio_uz` | Оба текста заполнены и одобрены клиникой |
| Название категории | Существующие `name_ru`, `name_uz` | Оба названия заполнены перед публичной выдачей категории |
| Название специальности | Существующий справочник `MedicalSpecialty` | Публичный контракт этапа 3 разрешает код в проверенные названия обеих локалей; неизвестный код не превращается в выдуманную специальность |

Поля переводов/описаний nullable для существующих строк и черновиков. Публикация проверяет непустые значения после удаления внешних пробелов и отклоняет неполную карточку с ошибками по полям. Для уже опубликованной карточки удаление обязательного текста запрещается, если той же операцией её не снимают с публикации.

Имя врача не требует искусственной транслитерации на две локали. Био хранится в `Doctor`; общий `UserProfile.bio` не становится публичным источником без явного контракта. Формат описаний на первом шаге — обычный текст; публикация произвольного HTML и загрузка медиа требуют отдельного решения.

Фото, логотип, сертификаты, отзывы и юридические тексты подготавливаются отдельно. Этап 2a не вводит URL на закрытые вложения МИС или новое хранилище. Цена и кабинет не становятся публичными обязательными полями до решений об их отображении.

### 11.4. Карта языковых адресов

| Назначение | Узбекский латиницей | Русский |
|---|---|---|
| Главная | `/` | `/ru` |
| Каталог и услуга | `/services`, `/services/:slug` | `/ru/services`, `/ru/services/:slug` |
| Врачи и профиль | `/doctors`, `/doctors/:slug` | `/ru/doctors`, `/ru/doctors/:slug` |
| Цены | `/prices` | `/ru/prices` |
| Контакты | `/contacts` | `/ru/contacts` |
| Остальные контентные страницы | `/<page>` | `/ru/<page>` |

Локаль определяется адресом страницы. Сохранённый язык сотрудника в localStorage не должен менять язык прямого публичного URL. Переключатель языка ведёт на тот же объект с тем же slug в другой локали.

У каждой локали свой canonical; `hreflang` связывает две опубликованные версии. Для узбекского использовать `uz-Latn`, для русского — `ru`; `x-default` ведёт на соответствующую узбекскую страницу. Значение `<html lang>` соответствует фактическому тексту. В sitemap входят обе локали только опубликованных страниц.

Эта карта относится к новому контентному сайту. Действующие `/queue/join`, `/q/:publicCode`, `/confirm-visit`, маршруты сотрудников и входа сохраняют канонических владельцев. Перед этапом 4 проверить пересечения в `routeRegistry.ts`. Не создавать автоматически `/uz/...` и редиректы для адресов, которых ещё не было; обнаруженные существующие публичные ссылки рассматриваются отдельно.

### 11.5. Этап 2a — минимальное расширение хранения

**Цель:** подготовить хранение публичного контента, не публикуя действующий каталог автоматически.

| Модель | Добавляемые поля | Начальное состояние |
|---|---|---|
| `Service` | `show_on_website`, `name_uz`, `description_ru`, `description_uz`, `slug`, `website_first_published_at` | Флаг `false`; новые тексты, slug и время первой публикации — `null` |

Планируемые типы: флаг — Boolean NOT NULL; `name_uz` — String(256), как существующее название; описания/биографии — Text; slug — String(160); время первой публикации — DateTime с часовым поясом. 5. Проверить новую цепочку и DDL на отдельном PostgreSQL с синтетическими данными: upgrade, значения старых строк, новые defaults, nullable-поля и конфликты slug. Проверку downgrade, если она предусмотрена, выполнять только на одноразовой БД; потеря новых столбцов не является безопасным rollback production.
6. Выполнить узкие проверки изменённого контракта хранения, `git diff --check` и обязательные проверки PR; перечислить фактически выполненное. Если PostgreSQL недоступен, зафиксировать отсутствие проверки и не заявлять подтверждённый upgrade.

**Граница PR:** модели, новая Alembic revision и необходимые focused tests хранения. Админские DTO/API/формы относятся к 2b, публичное чтение — к 3, страницы — к 4. Новые таблицы выбранному варианту не нужны; если они потребуются, остановиться и согласовать расширение с учётом RLS и регистрации моделей.

**Критерий завершения 2a:** новая цепочка имеет один head, модель и таблица согласованы, прежние строки остаются неопубликованными, внутренние данные сохраняются, проверки и статус PR зафиксированы. Начало 2b — после зелёного и слитого PR 2a и завершения его рабочего цикла.

### 11.6. Этап 2b — управление публикацией из админки

Канонические DTO услуг сейчас находятся в [services_ep/_helpers.py](../../backend/app/api/v1/endpoints/services_ep/_helpers.py), а врачей — в [schemas/clinic.py](../../backend/app/schemas/clinic.py). Не выбирать одноимённую legacy-схему по названию файла. Перед DTO-правками применить репозиторный процесс OpenAPI/сгенерированных типов.

Администратор получает редактирование переводов, адреса черновика, состояния публикации и понятный список недостающих данных. Операции сохранения черновика, первой публикации, снятия с публикации и повторной публикации имеют явные результаты backend. Момент первой публикации и фиксация slug сохраняются атомарно; первая публикация не может обойти правила при двух одновременных запросах.

Backend проверяет право администратора, полноту контента, неизменность фиксированного slug, конфликт уникальности и запрет публикации неактивной строки. Снятие с публикации и деактивация сохраняют `website_first_published_at` и slug. Сервисные поля и токены не включаются в публичный предварительный просмотр.

**Критерий завершения 2b:** сохранение и повторное чтение сохраняют все новые значения; неполная публикация, занятый slug и изменение фиксированного slug отклоняются; снятие/повторная публикация и деактивация работают по указанным правилам. Проверить существующие Admin/RBAC ограничения и интерфейс после обычного сохранения без ручного обновления страницы. Медиа добавляется отдельным шагом после решения по хранению и раздаче.

### 11.7. Этап 3 — безопасное публичное чтение

В существующем FastAPI реализуется отдельный read-only контракт под `/api/v1/public-site`: `GET /clinic`, `GET /services`, `GET /services/{slug}`, `GET /categories`, `GET /doctors` и `GET /doctors/{slug}`. Для локализованных ответов каталогов обязателен `locale=uz-Latn|ru`; неподдерживаемая или отсутствующая локаль отклоняется, язык не подменяется.

Списки и детали применяют одинаковую проверку активности, `show_on_website`, slug и полноты двух локалей. Услуга без категории или с неактивной категорией остаётся доступной, но получает `category: null`; список категорий содержит только активные категории с обоими названиями и хотя бы одной доступной услугой. Для скрытого, неактивного или неизвестного slug используется одинаковый публичный `404`. DTO не раскрывают ID, служебные коды, настройки очереди, кабинет врача или закрытые профили.

Переводы выдаются строго для запрошенной локали. Публичная цена берётся только из `Service.price` и `Service.currency`; при отсутствии суммы или валюты сумма возвращается как `null`, что означает «по запросу». `Doctor.price_default` и `DoctorPriceOverride` не используются. `Doctor.cabinet` не публикуется. Специальность разрешается по `MedicalSpecialty`; неизвестная или непереведённая подпись становится `null`, не скрывая врача и не раскрывая код. Настройки клиники ограничены `clinic_name`, `clinic_address`, `clinic_phone` и `clinic_email`; медиа, часы работы и расписание сюда не входят. Будущая команда записи использует те же slug, но повторно проверяет разрешение канала, активность и допустимость операции на backend.

**Критерий завершения 3:** contract tests доказывают allowlist полей, фильтрацию списков/деталей, пустые категории, обе локали и ошибки. Если готового HTML пока нет, готовность API не объявлять готовностью SEO или всего сайта.

### 11.8. Этап 4 — страницы, HTML и обновление

Реализовать `PublicLayout`, маршруты из разделов 3 и 11.4, каталог, профили, контакты и языковой переключатель. Перед существенной работой над экраном применить `clinic-ui-ux-master`; данные получать через контракт этапа 3.

До кода выбрать совместимый с текущим размещением механизм HTML и отдельно срок обновления контента из админки. Для обоих решений описать источник данных, обновление цены/текста, публикацию/скрытие, сбой обновления и восстановление. Отдельный сервис или процесс требует архитектурного решения; общий SPA `index.html` не выполняет требование HTML.

Прямой HTTP-запрос опубликованной страницы должен возвращать содержимое нужной локали, title, description, canonical, hreflang и Open Graph в исходном HTML. Удаление страницы из публикации обновляет HTML, кеши и sitemap в согласованный срок; после его истечения устаревший HTML не должен продолжать раскрывать скрытую карточку. До запуска должна быть проверена фактическая граница этого срока.

**Критерий завершения 4:** проверены прямые запросы обеих локалей, содержимое HTML, метаданные, мобильное отображение, навигация и сценарий изменения/скрытия из админки без ручного релиза сайта. Запись и внутреннее состояние очереди не считаются реализованными этим этапом.

### 11.9. Матрица приёмки и оставшиеся решения

| Сценарий | Ожидаемое поведение | Где доказывается |
|---|---|---|
| Upgrade на существующем каталоге | Все прежние строки неопубликованы; внутренние значения сохранены | 2a, отдельный PostgreSQL |
| Новая строка без параметров сайта | `show_on_website=false`, новые nullable-поля пусты | 2a |
| Одинаковый slug у двух услуг/двух врачей | Конфликт уникальности, включая скрытые строки | 2a/2b |
| Одинаковый slug у услуги и врача | Допустим в разных пространствах маршрутов | 2a/3 |
| Неполные переводы или нет имени врача | Публикация отклонена с ошибкой по данным | 2b |
| Изменение slug до публикации | Сохраняется, если формат и уникальность соблюдены | 2b |
| Первая публикация | Адрес и факт первой публикации фиксируются атомарно | 2b |
| Переименование или снятие с публикации | Фиксированный slug сохраняется | 2b |
| Повторная публикация | Тот же адрес, без новой первой публикации | 2b/3 |
| Деактивация и повторное включение активности | Карточка скрыта до явной повторной публикации | 2b/3 |
| Пустая/неактивная категория | Исключена из публичной выдачи категорий; доступная услуга остаётся в каталоге с `category: null` | 3 |
| Скрытый или неизвестный slug | Публичный `404`, без внутренней карточки | 3/4 |
| Переключение языка | Тот же объект и slug, локализованный адрес/текст | 4 |
| Прямой запрос страницы | Содержимое и метаданные присутствуют в HTML | 4 |
| Правка/скрытие из админки | HTML, кеши и sitemap обновлены в согласованный срок | 4 |

Открытые решения сгруппированы по первому зависимому этапу. Решения этапа 3, принятые владельцем 2026-10-09, отражены в требованиях 11.7 и соответствующих строках матрицы: источник цены, видимость кабинета, отсутствие категории и неполный перевод специальности.

- **До медиа и этапа 4:** хранилище и раздача разрешённых изображений, механизм HTML, срок обновления и поведение при его сбое, утверждённый контент остальных страниц.
- **До этапа 5:** хранилище/состояния заявки, резервирование слота, действия регистратора, идентификация при семейном номере, booking grant, guest idempotency, расписание, длительность, перерывы, горизонт и точный контракт настроек канала. Подробности — в разделе 4 заметки передачи.
