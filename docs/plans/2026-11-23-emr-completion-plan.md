## 1. Цель и конечное состояние

Врач открывает нужного пациента и видит актуальные проблемы, препараты, аллергии, прошлый план и важные результаты рядом с записью текущего приёма. Сегодняшние показатели доступны сразу. Повторный приём оформляется через изменения и проверку актуальности сведений. Фоновое сохранение не прерывает набор. Источники перенесённого текста различимы. Назначение, рецепт, лабораторный заказ, выполнение, результат и врачебный просмотр имеют собственные состояния.

Основной клинический сценарий:

1. Открыть пациента и текущий визит.
2. Просмотреть сводку и прошлый план.
3. Уточнить изменения, лекарства и аллергии.
4. Заполнить сегодняшние жалобы, измерения, осмотр, оценку и план.
5. Оформить необходимые назначения через существующие механизмы.
6. Проверить итоговый документ и подписать согласованную версию.
7. Позже открыть подписанную запись, результаты и динамику; исправления выполнять через предусмотренную поправку.

Приоритет — действующий кардиологический приём и общий EMR v2. Изменения shared-компонентов должны быть проверены для всех реально подключённых специальностей. Отдельная полноценная ЭМК общей панели /doctor не предполагается существующей: её фактический маршрут уточняется в M00.

## 2. Формат разработки и границы

### Один PR до готовности

- Использовать указанную изолированную ветку и один Draft PR в main. Весь последующий код, тесты и обновления этого плана накапливать в том же PR.
- Отдельный fork сейчас не нужен: ветка обеспечивает изоляцию и не создаёт второй источник прогресса. При реальной необходимости fork сохранить единственный канонический PR и этот checklist.
- Для параллельной работы использовать собственные worktree/временные ветки от общего кандидата, явное владение файлами и одного интегратора. Не создавать конкурирующие независимые реализации одинакового контракта.
- Промежуточные этапы не сливать в main и не публиковать на production. PR сохранять Draft до функциональной готовности и финальной приёмки.
- Эта задача заканчивается публикацией плана. Она не запускает реализацию, не разрешает merge и не является разрешением на production deploy. Последующее поручение реализации может использовать этот PR без повторного согласования уже зафиксированных обычных решений.

### Режим первоначальной публикации плана

Mode: direct_execute, documentation-only plan/dossier. Основание: создание известного документа без изменения поведения, политик выполнения, клинических контрактов или инфраструктуры. Согласно AGENTS.md планы готовятся непосредственно; реальный launcher нужен на соответствующей границе исполнения и перед merge авторского PR.

**Разрешено сейчас:** один новый файл docs/plans/2026-11-23-emr-completion-plan.md, изолированная ветка, коммит и описание Draft PR.

**Reference-only сейчас:** все исходники, миграции, тесты, AGENTS.md, runbooks и workflows.

**Первая остановка текущей задачи:** необходимость изменить runtime, workflow, политику или окружение выходит за поручение «исключительно план»; такие изменения в этот коммит не включать.

## 3. Быстрый цикл: что делать по ходу, что оставить на конец

Пожелание владельца: тяжёлые проверки не должны останавливать каждый шаг разработки. Для этой задачи используется уже разрешённый AGENTS.md режим proposed/unverified в изолированном, неслитом Draft PR. До реального успешного launcher сохраняется точная пометка **gate not run; do not merge or deploy**. Это не замена обязательного gate и не разрешение обходить инструментальные ограничения.

Исключение AGENTS.md относится к размещению непроверенного предложения через remote-GitHub-only workflow. Оно не даёт разрешения обходить обязательные ограничения локального исполнителя или выполнять операции с защищёнными окружениями. Переход в другое окружение требует сверки действующих правил; действие, для которого обязательный контроль ещё не выполнен, остаётся непроверенным proposal. Сейчас публикуется только план, поэтому запуск исполнения не происходит.

| Когда | Что выполнять |
|---|---|
| Внутри функционального блока | Чтение текущего контракта, реализация, минимальные проверки конкретного риска |
| Перед осмысленным коммитом | Просмотр diff, git diff --check, актуализация checklist и evidence |
| Отправка на GitHub | Пакет связанных законченных коммитов вместо push после каждой мелкой правки |
| Фоновый автоматический CI | Может запускаться существующими workflows; не ждать каждого полного прогона для независимой локальной работы |
| После завершения функциональности | Полный scope review, реальный DevBrain launcher, required CI, полная staging-приёмка, исправление замечаний |
| Перед merge/deploy | Подтверждение точных SHA, актуальных разрешений и всех применимых требований |

Draft PR сам по себе не выключает CI. Текущий Unified workflow запускается по pull_request в main; frontend/src/** включает frontend E2E. В этой задаче workflows не меняются. Ускорение достигается накопительными push, переиспользованием выполненных проверок на неизменившемся коде и отсутствием ненужных ручных полных dispatch.

Во время разработки сохраняются небольшие проверки, обнаруживающие конкретную регрессию: например, ввод во время autosave или запрет переноса данных другого пациента. Откладывание всех проверок до конца повышает стоимость исправлений; полный комплекс остаётся финальной стадией.

Нельзя подменять результат проверки пропуском теста, continue-on-error, фиктивным PASS, skip ci, пустым коммитом для scanners, изменением required checks или отключением защит. Если существующий обязательный контроль не позволяет действие, сохраняется непроверенный proposal и фиксируется конкретная граница; контроль не обходится.

## 5. Как вести прогресс

Каждый идентификатор Mxx.yy — отдельный наблюдаемый результат. Отмечать его [x] только после выполнения описанного результата и его узкой проверки; при отсутствии запуска писать NOT_RUN, а не PASS. Пункты финальной приёмки отмечаются отдельно.

Для каждого закрытого этапа записывать:

| Поле | Что указать |
|---|---|
| Этап | Mxx |
| Изменение | Короткое описание поведения |
| Коммит реализации | Полный SHA |
| Узкая проверка | Точная команда/сценарий, результат, ссылка |
| Непроверенное | Явное NOT_RUN/BLOCKED/NOT_VERIFIED |
| Остаток | Ошибки, зависимости, следующий шаг |

Статусы не смешивать: **реализовано → проверено локально → проверено CI → проверено на staging → принято к выпуску**. Галочка функционального этапа не означает readiness к merge.

Основной checklist находится в этом файле. В описании PR зеркалируются только этапы; синхронизировать их при завершении блока. В конце сессии оставлять краткий checkpoint с последним SHA и следующим незавершённым пунктом. Использовать предусмотренный DevBrain memory helper, когда он доступен; не имитировать его запуск или сохранение памяти.

**Цели сравнительного пилота:** ноль потерь/смешиваний данных в проверенных сценариях; основные сведения доступны без выхода из записи; отсутствие остановки набора при autosave. Сокращение времени документирования повторного приёма на 30% — проверяемая проектная гипотеза относительно измеренного baseline, а не уже достигнутый факт. Зафиксировать размер и состав пилота, включая разные уровни опыта врачей.

## 7. Definition of Done

Полная реализация означает одновременно:

- завершённые функциональные этапы, а не только нарисованный интерфейс;
- единые данные между вводом, сводкой, историей, рецептами и печатью;
- сохранность версии/подписи/поправки и контролируемые конфликты;
- RU/UZ, keyboard/mobile и проверенные врачебные сценарии;
- реальные результаты обязательного DevBrain, CI, review и staging на соответствующих SHA;
- отсутствие незакрытых обязательных проверок и существенных известных дефектов;
- понятный путь выпуска/отката и инструкция пользователя.

Готовность к merge, готовность к deployment и факт deployment — отдельные состояния. Текущий документационный PR не достигает ни одного из них.
