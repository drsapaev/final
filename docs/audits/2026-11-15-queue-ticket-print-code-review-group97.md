## NEW `QUEUEPRINT-FE-001` — P2: successful single-ticket print is never recorded in component state; reprint all includes already-printed tickets

**Exact source** [`MultipleTicketsPrinter.tsx:33–63, 75–89, 162–179`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/components/tickets/MultipleTicketsPrinter.tsx#L27-L89).

`printedTickets` is a React `Set`. In `printSingleTicket(ticket)`, the app calls `await printPanelTicketInBrowserAsync(buildPanelTicketPayload(ticket))`, returns `Boolean(result?.opened && result?.success)` but never calls `setPrintedTickets` on success; the surrounding component ignores this returned boolean. The **only** `setPrintedTickets` is in successful batch print. Thus printing a ticket using its per-card «Печать» button never shows the printed checkmark, never changes `pending=tickets.filter(!printedTickets.has(...))`, and «Печать всех» will submit the same ticket again (with actual print dialog invoked twice when the operator accepts both).

Existing [batchActivation tests:139–155](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/components/tickets/__tests__/MultipleTicketsPrinter.batchActivation.test.tsx#L139-L156) assert only that single-print function was called and **do not assert printed-state transition**, negative popup failure or batch exclusion.

**Acceptance:** synthetic 3 distinct tickets; click single on ticket1 with mocked `{opened:true,success:true}`, expect ticket1 marked as printed, «Печать всех» sends **only ticket2 and ticket3**, and no duplicate print. False result leaves ticket1 pending. No claim about actual physical printer completing a print job: status means browser print preview/print invocation as existing code contract, not paper delivery verification. Use existing per-card and batch test file with fail-first regression.

## NEW `QUEUEPRINT-FE-002` — P2: queue ID is not ticket identity; shared queue collisions corrupt printed/remaining state

**Exact source** [`MultipleTicketsPrinter.tsx:16–20, 33, 47, 75–89, 126–149, 189–215`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/components/tickets/MultipleTicketsPrinter.tsx#L16-L215). State `Set<string | number>`, `pending` filter, card state, all-printed count and remaining count ALL use **`ticket.queue_id`**. But backend [`visit_confirmation_service.py:944–1009`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/backend/app/services/visit_confirmation_service.py#L944-L1009) emits `queue_id` as the **DailyQueue** row identifier and `queue_number` separately. A DailyQueue has many tickets/entries. `queue_id` therefore cannot uniquely identify the ticket (same queue+day, distinct numbers / visits).

**Deterministic state case:** `tickets=[{queue_id:17,queue_number:4},{queue_id:17,queue_number:5}]`. Successful batch stores `new Set([17,17])` → **size=1** for 2 printed tickets. The UI condition `allPrinted=printedTickets.size>=tickets.length` is **false**, while `hasUnprinted=tickets.some(!printedTickets.has(ticket.queue_id))` is **false**: it presents neither a correct «all printed» completion banner nor any way to print pending. If the list is refreshed in the same mounted instance to add a new number under queue 17, it will incorrectly treat the NEW ticket as already printed and omit it. `currentPrinting` also keys by queue_id and may show the spinner on multiple cards simultaneously.

The [existing test fixture](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/components/tickets/__tests__/MultipleTicketsPrinter.batchActivation.test.tsx#L43-L48) uses `q1,q2,q3` **all distinct queue_id**, so it cannot catch this bug.

**Acceptance:** use a canonical distinct **ticket/queue-entry identity** (if provided), or a carefully validated composite `queue_id + visit_id + queue_number` with explicit collision handling; do not use shared queue ID as the unique key. Test two different numbers in same queue; single-print state isolates exactly one, batch prints only the remaining one, full count/any printed state correct, and adding/replacing a ticket with same queue_id never marks it printed by accident. Avoid collapsing multiple visits/services sharing one legitimate queue number without an SSOT policy decision.

## NEW `QUEUEPRINT-FE-003` — P1/P2 conditional: internal record IDs silently fabricated into the displayed queue ticket number

**Exact source:** [`panelPrint.ts:161–238`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/services/panelPrint.ts#L161-L241), [`buildPanelTicketPayload`:584–645](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/services/panelPrint.ts#L584-L645).

`extractQueueNumberCandidate` checks `obj.queue_number,number,ticket_number,...,display_number,obj.id` and returns the first; `resolveQueueNumber` calls it on `row.queue_entry` or `row.queue_ticket`. Therefore an otherwise legitimate partial display object `{ queue_entry:{id:862,queue_id:17}, visit_id:42 }` (no issued queue number) gets `queue_number="862"` printed as **«Очередь №862»** even though 862 is the **global queue-entry PK**, not its per-DailyQueue sequence number. The real backend contract stores a distinct pair [`OnlineQueueEntry.id` vs `OnlineQueueEntry.number`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/backend/app/models/online_queue.py#L276-L291); a missing `number` cannot be derived from PK.

A second unsafe fallback: if no queue number is found, `buildPanelTicketPayload` uses `getFirstDefined(row.visit_id,row.id)` and prints `"В-"+value` but `row.id` is **not proven to be a Visit PK** (e.g. appointment, payment or aggregate row). So a record with `record_kind:"appointment",id:701` lacking a ticket number is printed as **«В-701»**, falsely representing an appointment identifier as a visit-based ticket. Existing [test](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/services/__tests__/panelPrint.test.ts#L203-L222) covers explicit `visit_id` but does **not** prove `row.id` is a visit ID. Both are one trust-boundary root cause: **fabrication of displayed ticket identity from unrelated IDs**.

**Acceptance:** never treat generic nested `id`, `queue_id`, `appointment_id`, or ambiguous row `id` as an issued per-queue number or a Visit ID. Prefer server-provided `number/queue_number`; only permit explicitly typed `visit_id` fallback on verified queue-less/desk/lab visit records (separate visually from queue ticket). Otherwise honest non-printable error/print disabled with recoverable lookup, without guessing a number. Add unit tests for nested-id only, appointment-only, valid `visit_id` and genuine queue number.

## NEW `QUEUEPRINT-FE-004` — P2: unknown per-ticket price is rendered as a real zero price when settings enable it

**Exact source** [`panelPrint.ts:390–443, 462–551, 724–752, 1128–1134`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/services/panelPrint.ts#L390-L552). `resolveServicePriceForTicket` attempts a direct number from print ticket or matches service names against **queue-name/tag labels**; when there are candidates but no exact service-name match it returns **`{}`**, not `null`. The merged per-ticket row then assigns this object to `service_price,price,cost`. `renderPanelTicketMarkup` computes `showPriceValue = settings.show_price && ... && Number(servicePrice)!==0`; with an object, `Number({})` is **NaN**, and `NaN !== 0` is **true**. `formatMoney({})` sanitizes `String({})="[object Object]"` to empty digits and emits **"0 UZS"**. Thus a missing/unresolved service price is falsely labeled as a genuine zero-charge ticket.

**Real supported input shape:** [`backend/app/services/visit_confirmation_service.py:973–1009`](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/backend/app/services/visit_confirmation_service.py#L973-L1009) emits `print_tickets` with `queue_tag, queue_name, queue_number` but no `price`/ `service_price`. Example `row={print_tickets:[{queue_tag:"cardiology_common",queue_name:"Кардиолог",queue_number:12}],services:[{name:"Консультация кардиолога",price:100000}]}` → the queue label "Кардиолог" is **not** the same as the service name "Консультация кардиолога", so candidate non-match leads to `{}`; if administrator enables `show_price=true` in [ticket print settings](https://github.com/drsapaev/final/blob/3dbb6f95c25f8dd3e9e6a0c1c96520b4e77ae4a8/frontend/src/api/ticketPrintSettings.ts#L1-L68), a physical ticket can show `Цена: 0 UZS` despite a paid service. **Conditional on that admin setting**; default `show_price=false` and does not display it.

**Acceptance:** unknown/non-numeric/ambiguous per-ticket cost must remain **null/unknown**, never `{}` or `0`; only show a real nonnegative finite price from an authoritative service identity/mapping (ID or SSOT direct price). If one queue covers multiple services, do not invent one service's cost from the queue tag; use clear aggregate policy or omit per-ticket price. Test direct numeric price, missing price with nonmatching label, multi-service queue, legitimately zero-price service, toggled show_price true/false and lack of fallback to aggregate invoice total.
