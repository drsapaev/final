## New source-backed findings — not runtime-reproduced

### RETRO-3953-01 — P1 candidate — changing authenticated doctor on the SAME mounted hook leaves previous doctor's personal templates visible

**Origin:** [#3953](https://github.com/drsapaev/final/pull/3953); [`frontend/src/hooks/useDoctorSectionTemplates.ts:100-123`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L100-L123), [`frontend/src/hooks/useDoctorSectionTemplates.ts:150-178`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L150-L178), [`frontend/src/hooks/useDoctorSectionTemplates.ts:245-248`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L245-L248).

The module-wide cache is correctly cleared/re-keyed when the principal changes, but `templates` is a **per-hook `useState` initialized only once**. `syncSectionTemplateCacheOwner()` does not reset `templates`, and `fetchTemplates` begins loading without clearing the previous array. If a still-mounted doctor-template panel re-renders on A→B authenticated-user change, B can still see **A's local personal clinical phrases** until B's GET resolves; with network delay or B's denied GET, the stale view remains until the failure completes. This is a privacy/integrity gap at the presentation boundary despite correct server-side permissions and cache keying. The added regression only **unmounts A before mounting B**; it never tests a principal swap inside a mounted hook.

**Required test:** mount one hook as doctor A and load a unique synthetic A phrase, change mocked auth principal to B while retaining the same hook, defer B's GET and assert A's phrase **is immediately absent and no Apply/Edit UI is enabled**; after B's 403 assert A's data never reappears, and after B's 200 assert only B's templates render. **Fix direction:** principal/section-keyed synchronous render gate or keyed remount plus state reset on principal/context change before showing old data, as well as epoch + owner checks on every async completion.

### RETRO-3953-02 — P2 — changing section/ICD or disabling the section leaves previous templates (indefinitely if section becomes empty)

**Origin:** [#3953](https://github.com/drsapaev/final/pull/3953); [`frontend/src/hooks/useDoctorSectionTemplates.ts:101-109`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L101-L109), [`frontend/src/hooks/useDoctorSectionTemplates.ts:150-163`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L150-L163), [`frontend/src/hooks/useDoctorSectionTemplates.ts:245-248`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L245-L248).

On an in-place `section/ICD/limit` change, the new request epoch protects against **late result replacement** but does not clear or hide the *already displayed* old array while the new request is pending. If `section` becomes falsy, `fetchTemplates` returns immediately at line 151 and **never clears templates or error at all**. Thus a different diagnosis (or no section) may render or apply unrelated previously selected therapeutic phrases even though no stale asynchronous response was committed. Existing tests assert only the **final list after both requests complete**, not that old options disappear immediately or for an empty section.

**Required test:** I10→I20 with deferred I20 load, assert I10 template not rendered/actionable during loading; then section→undefined, assert `templates=[]` / `hasTemplates=false` immediately and permanently. Add explicit ownership/render gating on context change.

### RETRO-3953-03 — P2 — `forceRefresh` can reuse a stale in-flight GET after a successful template mutation

**Origin:** [#3953](https://github.com/drsapaev/final/pull/3953); [`frontend/src/hooks/useDoctorSectionTemplates.ts:153-173`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L153-L173), [`frontend/src/hooks/useDoctorSectionTemplates.ts:280-298`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L280-L298).

The `forceRefresh=true` branch explicitly calls `joinInFlightRequest(epoch, cachedEntry.promise)` if a previous GET is pending. `updateTemplate` sends PUT and then calls `fetchTemplates(true)`; if an old pre-update GET is pending, the forced refresh **joins that old response instead of issuing a fresh read after the successful PUT**. A valid response carrying the old template text can overwrite the post-edit view, while `updateTemplate` still returns `{success:true}` and the edit modal closes. This is distinct from the intended read-side promise deduplication, which is fine for concurrent *readers* before a mutation.

**Required test:** defer a GET containing old text, complete PUT with new text, invoke `fetchTemplates(true)` through the mutation, then resolve old GET; assert an actual post-mutation GET occurred and UI shows newly persisted text; no false fresh success based on old result. Fix with cache invalidation/generation or bypassing pre-mutation promise on forced refresh (while protecting concurrent call order).

### RETRO-3953-04 — P2 — failed shared GET is shown to a joining subscriber as an empty *successful* list

**Origin:** [#3953](https://github.com/drsapaev/final/pull/3953); [`frontend/src/hooks/useDoctorSectionTemplates.ts:129-145`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L129-L145), [`frontend/src/hooks/useDoctorSectionTemplates.ts:180-216`](https://github.com/drsapaev/final/blob/c7d5e0380fa3af8917f608819de21016fdbcfaca/frontend/src/hooks/useDoctorSectionTemplates.ts#L180-L216).

The originating hook's `catch` sets `error` then returns `[]` (a resolved promise); the second hook's `joinInFlightRequest.then` consumes `[]`, calls `setError(null)` and `setLoading(false)`. On a 403/500/offline failure of a shared GET, **originator has an error, joiner has no error and presents an empty list as if there are no clinical templates**. A regression suite tests only shared-promise success and originator unmount, never failure.

**Required test:** mount two hooks for the same key, reject the shared GET (403 + 500), assert one GET, both hooks independently show a failure status and no false "no templates" success. Fix by preserving typed error/status in shared outcome rather than laundering failure into `[]`.

### RETRO-3947-01 — P2 — Echo Retry overwrites user-entered measurements after hydration failed

**Origin:** [#3947](https://github.com/drsapaev/final/pull/3947); [`frontend/src/components/cardiology/EchoForm.tsx:245-299`](https://github.com/drsapaev/final/blob/dd4d2cf8e0fbb62d287762d1aad3b88d81ccad30/frontend/src/components/cardiology/EchoForm.tsx#L245-L299), [`frontend/src/components/cardiology/EchoForm.tsx:301-314`](https://github.com/drsapaev/final/blob/dd4d2cf8e0fbb62d287762d1aad3b88d81ccad30/frontend/src/components/cardiology/EchoForm.tsx#L301-L314), [`frontend/src/components/cardiology/EchoForm.tsx:442-446`](https://github.com/drsapaev/final/blob/dd4d2cf8e0fbb62d287762d1aad3b88d81ccad30/frontend/src/components/cardiology/EchoForm.tsx#L442-L446), [`frontend/src/components/cardiology/EchoForm.tsx:499-517`](https://github.com/drsapaev/final/blob/dd4d2cf8e0fbb62d287762d1aad3b88d81ccad30/frontend/src/components/cardiology/EchoForm.tsx#L499-L517).

The good fail-closed patch sets `hydrationFailed=true` after an initial GET error and disables **Save**, but does **not disable inputs**. The doctor can enter EF, EDD or conclusion while the canonical read has failed. Pressing **Retry** increments `hydrationAttempt`, starts the effect, and successful hydration unconditionally runs `setEchoData(deepMerge(DEFAULT_ECHO_DATA, storedEcho))` (and resets dirty state), silently destroying those manually typed unsaved values. The same scenario was identified in the P2 inline thread of [#3948](https://github.com/drsapaev/final/pull/3948), but **#3948 was never merged**, and the current merged #3947 code still has this path. Existing merged tests cover failure→Retry success and in-flight save edits, not input between failure and Retry.

**Required test:** first GET 500, enter EF=45 in failed state, Retry GET returns an old saved EF=55; assert the 45 entry is preserved as an unsaved draft or requires an explicit confirm-discard, not silently overwritten. Fix direction: disable editing until successful hydration OR merge/preserve the doctor's local draft after canonical read, with explicit conflict UX. Prefer no data loss and no destructive server write.
