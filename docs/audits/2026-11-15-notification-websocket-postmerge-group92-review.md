A revoked JTI or expired JWT can now cause WS 1008; two new fake-resolver unit tests prove that *if* the resolver returns `None`, the socket closes. This is a real partial remediation; do not say #4079 did nothing.
- Residual: `db = SessionLocal()` occurs once for the entire WS lifespan. `authenticate_websocket_token` loads the mapped `User` into this session's identity map. SQLAlchemy ORM can return the already-loaded entity without overwriting `User.is_active` or `User.role` when another transaction updates them.

- **Acceptance:** an actual accepted test websocket, JWT with long expiry, 2 independent PostgreSQL sessions, connected user initially active and no JTI blacklist; another session updates `User.is_active=False` + commit. Await 15s simulated via patch 0.01s: must close WS 1008 and remove manager registry without an incoming frame. ## Existing open P1 independently still present — `NOTIFYPOOL-BE-001`

This is NOT a new finding ID: [group40 original source-backed audit](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/docs/audits/2026-11-13-notification-websocket-postmerge-round40.md). `notification_websocket.py:45, 54–75, 85–90, 105–126, 250–280` retains one `SessionLocal` through the entire `receive_text` loop and closes it only in `finally`. Initial JWT `User`/blacklist and unread-count queries have already checked out a DB connection. No `db.commit/rollback/close` ends that read transaction before idle wait. [`db/session.py` engine](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/app/db/session.py#L119-L149) defaults to **pool_size=8, max_overflow=2, pool_timeout=60s**. Legitimate sustained WS subscriptions can consume every pool connection, starve HTTP clinical API and create idle-in-transaction sessions.

**Independent illustrative execution (NOT project test):** SQLAlchemy 2.0.50 with disposable SQLite/QueuePool `pool_size=1, max_overflow=0`: after `Session.execute(select(1))`, `pool.checkedout()==1` until `Session.close()`, after which checkedout==0. This establishes the session mechanics, not production concurrency measurements.

The #4079 claim “no additional checkout per idle socket” is technically compatible with a serious problem: it avoids a *new* checkout on recheck because it **continues pinning the original connection** for the entire socket lifetime. A separate short-lived session per recheck plus no long-lived handshake session is preferred. Do not invent a new finding or mark existing `NOTIFYPOOL-BE-001` closed.

**Fail-first:** disposable PostgreSQL `DB_POOL_SIZE=1, DB_POOL_OVERFLOW=0`, accept one valid synthetic socket, leave it idle, concurrently execute an unrelated DB query; assert the unrelated query succeeds promptly (pool checkout returns to zero between message processing and periodic rechecks). Check a dozen sockets and expected bounded checkout at 8+2. Ensure each recheck closes its session without violating scoped inbox or broadcast semantics.
