## Focused source re-review: route anchors can resurrect a completed visit

The previous positive runtime CI failure (old head `c517b12b`, [CI 43857614308](https://github.com/drsapaev/final/actions/runs/43857614308), **4350 passed / 1 failed**) revealed that confirmed completion set local `activeTab='queue'` but left the browser at `?tab=visit`, which the panel's URL synchronization effect restored. The initial #4106 follow-up synchronized the tab to the route.

**New independent read of the current owner source** identified a second route-related risk in the **same post-completion path**, not merely a static formatting issue: `hydratePatientFromUrl` [CardiologistPanelUnified.tsx #L672–780](https://github.com/drsapaev/final/blob/1532acda4adc0d5109e941b0681fb8091c6dd5b5/frontend/src/pages/CardiologistPanelUnified.tsx#L672-L782) is a `useCallback` that runs in an effect whenever the selected patient changes. If the URL still has `?patientId=A&visitId=V_A` after confirmed completion clears `selectedPatient`, this effect can begin a new patient fetch and re-select A, because the live ref is now null and therefore does not contradict the old URL. Separately the URL-appointment synchronization effect [same source #L793–846](https://github.com/drsapaev/final/blob/1532acda4adc0d5109e941b0681fb8091c6dd5b5/frontend/src/pages/CardiologistPanelUnified.tsx#L793-L846) may restore matching appointment context on list refresh. Thus **both tab and old patient/visit URL anchors must be cleared** after an authoritative completed visit. This is source-confirmed potential rehydration, not production incident proof; no personal data was viewed.

**Current #4106 revision** (`c1532ed35`) changes the already-in-scope `CardiologistPanelUnified.tsx` successful branch only:
- Before rendering the confirmed queue tab, take the existing URL parameters, set `tab=queue`, remove `patientId`, `visitId`, `visit_id`, and call `navigate({pathname,search}, {replace:true})`, alongside the established selected-patient cleanup. **Other search terms** are not silently rewritten.
- This branch remains inaccessible for stale, rejected, unknown or network-failed A completion responses after B has been selected. The existing completion ownership predicate and stale error-drop remain. Backend queue command, EMR model, permissions and data persistence not changed.
- `frontend/src/pages/__tests__/CardiologistPanel.deferredCompletion.test.tsx` now mounts the positive completion with **actual router search** `?tab=visit&patientId=11&visitId=101`, derives URL IDs in the mocked navigation hook, and has `RouteQueryProbe` asserting the queue tab and the absence of all three completed deep-link keys. Stale A→B scenarios assert B's `?tab=visit` remains unchanged; unit fixture uses synthetic people/visits only.
- This narrow flow preserves the existing direct post-server-confirmed completion transition; it does **not** establish that the broad dirty-draft guard has been fully tested against all route transitions. That requires clinical workflow acceptance. A different patient being selected while the earlier completion is pending must remain protected by the post-POST live ref check.
