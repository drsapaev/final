## Executive overview

**Six findings: 3 P1 candidates, 3 P2 candidates.** The most urgent are competing EMR writes from ToothModal and DentalVisitScreen, and an open tooth modal retained across visit/patient transitions. Other findings concern signed-record editing posture, a tooth preview changing before user confirmation, failure transparency at visit completion and an uncommitted dermatology procedure draft persisting between visits.

These are **source-observed findings** with synthetic reproduction/test proposals, **not** tested production incidents. No actual clinical data or API/DB writes used. Existing tests exercise dental save version ordering, failure and patient-switch form reset ([`DentalVisitScreen.persistence.test.tsx:84–109`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/__tests__/DentalVisitScreen.persistence.test.tsx#L84-L109), [`DentalVisitScreen.persistence.test.tsx:130–159`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/__tests__/DentalVisitScreen.persistence.test.tsx#L130-L159), [`DentalVisitScreen.persistence.test.tsx:261–289`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/__tests__/DentalVisitScreen.persistence.test.tsx#L261-L289)) and dermatology procedure add/remove/disabled modes ([`DermatologySection.cosmeticProcedures.test.tsx:45–115`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/emr-v2/sections/specialty/__tests__/DermatologySection.cosmeticProcedures.test.tsx#L45-L115)); neither group currently covers the scenarios enumerated below.

### DENTMODAL-FE-001 — P1 candidate: ToothModal performs an independent server write and then re-saves through a parent whose row_version is stale

**Source path and behavior.** A normal tooth-save click in `ToothModal` first executes `GET /v2/emr/{visit}`, builds a whole-record payload from the server snapshot with the tooth change [`ToothModal.tsx:87–116`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/ToothModal.tsx#L87-L116), then executes its own `POST /v2/emr/{visit}` [`ToothModal.tsx:337–358`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/ToothModal.tsx#L337-L358). Only **after** success does it invoke `onSave(dataToSave)`. The DentalVisitScreen parent `onSave` binding [`DentalVisitScreen.tsx:1278–1288`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1278-L1288) calls `handleToothSave`, which updates local `specialty_data.tooth_status` and schedules **another** queued autosave [`DentalVisitScreen.tsx:1153–1161`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1153-L1161) / [`DentalVisitScreen.tsx:1015–1027`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1015-L1027). Its `rowVersionRef` was updated only on the parent's own `persistDraft` response [`DentalVisitScreen.tsx:966–982`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L966-L982); it is **not** informed of the modal's independent successful POST. The modal's first request advances backend row_version N→N+1, while the parent's next POST commonly uses stale N. The modal payload and parent payload do not include a shared `client_session_id` [`ToothModal.tsx:103–115`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/ToothModal.tsx#L103-L115) / [`DentalVisitScreen.tsx:91–97`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L91-L97), so the backend's same-session exception does not protect this conflicting pair [`emr_v2_service.py:296–317`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/backend/app/services/emr_v2_service.py#L296-L317).

**Impact/preconditions.** In the common sequence with no intervening parent save, adding a tooth procedure can result in a **successful first server write followed by 409 on the parent's second write**. Subsequent local patient notes or pending tooth edits may remain unsaved until an explicit reload/conflict resolution. There is no evidence that the first saved tooth procedure is deleted by that second failed request; the risk is duplicate write conflict and preservation of other uncommitted content.

**Synthetic fail-first:** mount a real `ToothModal` with real DentalVisitScreen callback using mocked GET and POST at row_version 3. Click Save with a synthetic procedure; assert **one** authoritative EMR write (or an explicit version-synchronized transaction), no follow-up POST with stale row_version 3, no false success notification on conflict, and full preservation of simultaneous doctor notes. Repeat with an outstanding autosave and hard 409. The existing parent-only persistence tests mock TeethChart/ToothModal ([`DentalVisitScreen.persistence.test.tsx:22–27`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/__tests__/DentalVisitScreen.persistence.test.tsx#L22-L27)) and cannot catch this interaction.

**Repair direction:** make DentalVisitScreen the sole writer for this visit, and `ToothModal` a pure controlled editor that returns tooth data without an independent GET/POST. Alternatively perform one coordinated write with returned row_version and reconciliation of all dirty fields, but do not retain two uncoordinated clinical writers.

### DENTMODAL-FE-002 — P1 candidate: a tooth modal opened for patient A can write its still-open form to patient B after the selected visit changes

**Source path and behavior.** DentalVisitScreen maintains `selectedTooth` and `toothModalOpen` as local state [`DentalVisitScreen.tsx:831–855`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L831-L855). On visit switch, `loadEMR` clears draft/version/saving state [`DentalVisitScreen.tsx:862–920`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L862-L920) but **never closes the modal or clears selected tooth**. The modal is rendered outside the visit-dependent loading/field-disabled branch and receives the *current* `visitId` prop with the *previous* `selectedTooth.data` [`DentalVisitScreen.tsx:1278–1288`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1278-L1288). `ToothModal` initializes local clinical form data from `toothData` when `open` or `toothData` changes but **not** when `visitId` changes [`ToothModal.tsx:245–295`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/ToothModal.tsx#L245-L295). On Save it calls `loadExistingEmrDraft(visitId)` and POST for that new visit [`ToothModal.tsx:337–358`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/ToothModal.tsx#L337-L358), then invokes the parent `onSave`, which now binds to current B's data [`DentalVisitScreen.tsx:1153–1161`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1153-L1161).

**Conditional effect:** if a doctor has tooth A/16 editor open, switches to B/42 in the same mounted screen, and saves the still-open modal, the A tooth form can be submitted to **B's EMR**. Requires an actual same-mounted visit transition while dialog remains open; it is not claimed to happen on a full page reload or a guaranteed route remount. Distinct from prior DENTCHART-FE-001 in PR #3886 (stale TeethChart render state): this concerns the **modal's direct server write using current visitId with old selected form**.

**Synthetic fail-first:** use React rerender from `patient={visit 41, patient 7}` to `visit 42, patient 8` while modal has a synthetic procedure for tooth 16; assert modal auto-closes, form/selectedTooth reset and no `POST /v2/emr/42` carries A's procedure. Verify a newly opened B modal uses only B's status and that delayed asynchronous modal writes cannot cross into B after a visit change.

**Repair direction:** key and reset all modal state by visit+patient identity; abort or block outstanding tooth writes at visit transition; require write-time correspondence between modal opening visit and active visit; enforce backend authorization and row-version constraints.

### DENTVISIT-FE-001 — P2: the standalone dentist visit screen does not honor signed/amended EMR status when deciding whether clinical fields are editable

**Source.** `loadExistingEMR()` types and returns only `data` and `row_version` for use [`DentalVisitScreen.tsx:81–89`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L81-L89). `loadEMR` copies data/version but ignores backend `status` ([`DentalVisitScreen.tsx:886–919`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L886-L919)); `fieldsDisabled` is only `completing || !isEMRLoaded` [`DentalVisitScreen.tsx:1173–1176`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1173-L1176). It passes this to clinical fields/tooth chart/protocol [`DentalVisitScreen.tsx:1221–1265`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1221-L1265). Backend ordinary save rejects the signed status [`emr_v2_service.py:287–294`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/backend/app/services/emr_v2_service.py#L287-L294), so editable text for a signed record cannot normally be persisted and autosave reports an error.

**Impact:** a dentist may modify a signed record in an enabled editor, then only discover failure after autosave/queue exit, without a clearly indicated signed/read-only state. No claim a signed record is thereby changed on backend.

**Synthetic fail-first:** GET returns `status:'signed'` (then `amended`, `locked`) plus synthetic clinical data; assert all mutation controls disabled while chart/history remain inspectable, no autosave dispatched and clear signed/amended badge shown. For `draft/in_progress` verify editing still works.

**Repair:** explicitly retain and interpret canonical status on load; gate edit, modal write, completion and save controls on finalized states and surface the correct read-only message; keep server-side signed protections mandatory.

### DENTVISIT-FE-002 — P2: queue completion callback failure is silently swallowed after EMR save

**Source.** `handleCompleteVisit` handles a failed `persistDraft` with an error alert and retry [`DentalVisitScreen.tsx:1034–1064`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1034-L1064). But when the save succeeds and `await onCompleteVisit?.(snapshot)` throws, its nested `catch` only logs a warning [`DentalVisitScreen.tsx:1066–1075`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1066-L1075) and does not set `saveError`, notify the user, expose a retry state, or reflect failed queue completion. Its button re-enables without a completion-specific explanation.

**Impact:** the EMR may be safely persisted but the actual queue/visit completion may fail; the clinician sees no actionable UI indication and may assume visit closure succeeded. This is distinct from the same screen's existing tests of failed **EMR saving** and from the prior EMRContainerV2 completion code reviewed in #3886.

**Synthetic fail-first:** persist an authorized synthetic EMR successfully; make `onCompleteVisit` reject with network error; assert a visible queue-completion-failed status and safe retry action without duplicated unsafe data writes. Ensure saved EMR data remain intact and no fake “complete” success appears.

**Repair:** separate persisted-clinical-document state from queue completion result, report completion failure distinctly and keep a guarded retry path keyed by visit ID.

### DENTVISIT-FE-003 — P2 candidate: clicking a tooth changes local displayed diagnosis/status before the editing modal is accepted

**Source.** The `TeethChart` click path [`TeethChart.tsx:69–98`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/TeethChart.tsx#L69-L98) calls `setTeethData(newData)` and assigns `status:selectedStatus` (default `CARIES`) **before** emitting `onToothClick`; in DentalVisitScreen the callback merely opens `ToothModal` [`DentalVisitScreen.tsx:1147–1151`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1147-L1151). Only a confirmed modal save [`DentalVisitScreen.tsx:1153–1161`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1153-L1161) updates canonical `specialty_data.tooth_status`. Cancel [`DentalVisitScreen.tsx:1278–1288`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1278-L1288) closes the modal but does not restore `TeethChart`'s locally changed status. The parent also renders a `ToothSummary` from canonical `toothStatus` [`DentalVisitScreen.tsx:1238–1249`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/dental/DentalVisitScreen.tsx#L1238-L1249).

**Conditional effect:** clicking a healthy tooth solely to inspect/edit its procedure opens a modal, but the chart already shows default caries while summary/backend still show healthy. Cancelling leaves the inconsistent visual state until remount or reload. This is not a claim the cancellation modified persisted EMR. Distinct from PR #3886 DENTCHART-FE-003 (Clear All local-only).

**Synthetic fail-first:** controlled chart starts healthy/missing and is clicked to open modal; cancel immediately; assert original tooth color/status and summary remain consistent and no mutation. Confirm a modal Save updates parent and chart once, with exactly selected clinical status.

**Repair:** make tooth clicks selection-only in modal workflows, and commit visual state exclusively from the canonical parent after confirmed save; decouple standalone quick-edit mode from selection mode.

### DERMAPROC-FE-001 — P1/P2 candidate: unfinished dermatology procedure draft survives same-mounted visit changes and can be added to another patient's EMR

**Source.** `DermatologySection` supports visit/patient props [`DermatologySection.tsx:57–84`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/emr-v2/sections/specialty/DermatologySection.tsx#L57-L84) but destructuring ignores both; local `showProcedureForm`/`procedureDraft` are initialized once [`DermatologySection.tsx:91–94`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/emr-v2/sections/specialty/DermatologySection.tsx#L91-L94) with no identity-keyed reset. Form inputs write local draft [`DermatologySection.tsx:273–349`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/emr-v2/sections/specialty/DermatologySection.tsx#L273-L349). `handleProcedureAdd` [`DermatologySection.tsx:96–114`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/emr-v2/sections/specialty/DermatologySection.tsx#L96-L114) appends this draft to the **current** `cosmeticProcedures` prop by `onChange('cosmetic_procedures',...)`. The parent `EMRContainerV2` supplies current visit/patient props and an onChange targeting the active `specialty_data` [`EMRContainerV2.tsx:1087–1106`](https://github.com/drsapaev/final/blob/3de30426154cdb031b62c858fa6ff06a9b65aabc/frontend/src/components/emr-v2/EMRContainerV2.tsx#L1087-L1106) but does not key the child by visit.

**Conditional clinical effect:** open an unsaved synthetic procedure for patient A, type product and area but do not press Save, then switch visit to patient B while React reuses the same mounted DermatologySection. The old procedure form remains visible; pressing Save appends A's procedure into B's EMR. This depends on same-mounted transitions, not full application reload. Comparable to prior EMRPRES-FE-001 prescription draft cross-visit in #3886, but a different component, update target and test boundary.

**Synthetic fail-first:** mount A with `visitId=41` and `patientId=7`, open procedure form, type synthetic data; rerender with B `visitId=42`/`patientId=8`; assert prior draft/form is not available to save to B, and B's `cosmetic_procedures` remains untouched. Test switch while disabled, then reenabled.

**Repair:** use visit-scoped modal/editor keys or reset local draft on identity change; if preserving drafts across navigation, bind their storage and save eligibility to original visit and explicit user confirmation, never silently redirect to the active patient.
