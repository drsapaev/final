### QPOSAUTH-BE-001 — P1: any authenticated user can enumerate the full queue through stats

**Evidence:** [`GET /queue/position/stats/queue/{queue_id}`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/queue_position.py#L352-L382) requires only `get_current_user` and never checks role, linked patient identity, or queue ownership. It fetches the queue and [all visible entry rows](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/repositories/queue_position_api_repository.py#L85-L98), then returns [`QueuePositionNotificationService.get_queue_position_info`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_position_notifications.py#L419-L477) for *each*: queue-entry ID, queue number, status, priority, timestamps, queue tag, cabinet and specialist name. An unrelated logged-in patient can iterate numerical queue IDs and inspect other patients' *operational queue records*. **The response does not include patient name, diagnosis or phone by default; do not overclaim disclosure of those fields.**

**Synthetic red-first:** Create Patient A with their ticket in Queue Q1 and Patient B with Q2; logged in as A, call `/api/v1/queue/position/stats/queue/Q2`. Expect 403/404 or properly aggregate-only explicitly public data, not the detailed entry list. Verify Registrar/Admin intended access and doctor ownership rules; assert no patient labels/secrets are accidentally included. Use 2 separate queue IDs; do not mistake authentication for authorization.

**Repair direction:** explicit per-queue staff RBAC or patient-owned/aggregated status endpoint. Gate Doctor visibility against specialty and established owner policy. Avoid exposing internal entry IDs to unrelated patients.

### QPOSAUTH-BE-002 — P1/P2: owner guard is bypassed for queue entries with `patient_id=NULL`

**Evidence:** both [`GET /queue/position/{entry_id}`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/queue_position.py#L111-L143) and [`GET /queue/position/by-number/{queue_number}`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/queue_position.py#L145-L178) only run patient ownership verification when `entry.patient_id` is truthy. Non-staff users querying a queue-only/QR/legacy `OnlineQueueEntry` with `patient_id=None` **skip ownership checks entirely** and receive that row's queue position, status, priority, queue and cabinet metadata. QR join explicitly permits unlinked entries; absence of patient ID is not proof that any authenticated caller owns the ticket.

**Synthetic red-first:** Logged-in Patient A requests a synthetic unlinked entry `E.patient_id=NULL` by global ID and by queue number; require denied access unless a separate verified queue-session/claim capability authorizes the caller. Positive control for A's linked entry, negative for B's linked entry. No real patient IDs or sessions in tests.

**Repair direction:** fail closed for patient-role read when patient linkage is missing, or use a cryptographically bound session/ownership capability; role-independent generic 'staff' exceptions must be explicit and audited.

### QPOSCALL-BE-001 — P2: notification-only 'call patient' endpoint sends a false called message without validating queue state

**Evidence:** [`POST /queue/position/notify/call`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/queue_position.py#L212-L238) loads an arbitrary entry, checks staff role/doctor scope, and calls [`notify_patient_called`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_position_notifications.py#L70-L112). Neither function verifies `entry.status == 'called'`, nor moves the entry into called state atomically. `notify_patient_called` always constructs a high-priority **“Вас вызывают!”** message and payload `status='called'`. A valid Registrar/Admin (or authorized doctor) can send it for a **waiting**, **no_show**, or **served** entry. This is not an anonymous access path; it is a misleading manual notification and workflow-state mismatch.

**Synthetic red-first:** For matching patient with a synthetic enabled push target, call endpoint on waiting and terminal tickets; assert 409/no delivery. For a genuinely called ticket, assert one delivered notification and no duplicate state transition. Test `cabinet_number` against canonical resource/doctor cabinet; currently the caller may supply arbitrary string, creating a second misleading message possibility.

**Repair direction:** status guard and auditable/manual resend semantics, with anti-duplicate policy; any new status transition belongs in the canonical queue service, not notification sender.

### QPOSFAIR-BE-001 — P2: positions undercount equal-timestamp or null-timestamp predecessors

**Evidence:** [`_count_people_ahead`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_position_notifications.py#L316-L334) counts a waiting predecessor only if it has greater priority or equal priority and **strictly smaller `queue_time`**. It lacks the queue's deterministic `id` tie-break and any `created_at` fallback. Meanwhile [canonical staff call-next ordering](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_svc/_helpers.py#L84-L115) is priority descending, `coalesce(queue_time, created_at)` ascending, then `id` ascending. Two equal-priority waiting entries with identical `queue_time` therefore both report zero patients ahead, and a waiting entry with `queue_time=NULL` also ignores earlier peers with populated timestamps (SQL comparisons with NULL are unknown).

**Synthetic red-first:** Insert E1/E2 with identical timestamps but E1.id < E2.id; and E3 with `queue_time=NULL`/older `created_at`. Compare displayed `people_ahead` to canonical call-next ordering. Assert E2 reports at least one ahead and all positions reflect the same queue SSOT ordering; both queue-tag/resource and doctor-queue controls. Preserve priority fairness and original QR queue_time.

**Repair direction:** share one ordering predicate/rank query with call-next; include null fallback and deterministic id tie-break, avoiding divergent service-local queue logic.

### QPOSBATCH-BE-001 — P2: batch change notifications filter by numeric ticket instead of actual priority order

**Evidence:** [`notify_queue_changes_batch`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_position_notifications.py#L171-L248) restricts recipients to `OnlineQueueEntry.number > changed_after_number`, but decides actual position using [priority/queue_time](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_position_notifications.py#L316-L334). Ticket numbers are not a serving rank after VIP/recovery priority changes. When a high-priority patient with number 6 is served, an ordinary waiting number 5 may move ahead even though `number <= changed_after_number=6` and is excluded from notification. Conversely numbers above the threshold can be re-notified when their position did not change.

**Synthetic red-first:** Q contains E5 number=5 priority=0, E6 number=6 priority=2, both waiting. Call/complete E6; trigger batch with `changed_after_number=6`. Assert E5 gets notified when and only when its actual `people_ahead` decreases, regardless of ticket number. Add a no-change control and provider failure response audit.

**Repair direction:** identify affected positions from before/after queue ordering (snapshot/event delta) or conservatively enumerate eligible waiting entries and compare stored last-notified rank; do not use printed number as a rank surrogate. Keep anti-noise thresholds and provider preferences.

### DISPLAYWS-BE-001 — P1 (urgent privacy): unauthenticated department WebSocket sends patient names and queue status

**Source evidence:** The mounted [`/api/v1/display/ws/queue/{department}`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/api.py#L337-L342) is implemented at [`websocket_queue_department`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/display_websocket.py#L162-L228). It calls `manager.connect(websocket, board_id)` and then `_send_department_queue_state` without `extract_ws_token`, `authenticate_websocket_token`, any role/claim check or origin policy. The route's own comment admits token enforcement is not implemented. [Manager.connect](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket.py#L46-L76) accepts the anonymous connection. The [snapshot service](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket_api_service.py#L196-L232) returns `patient_name`, queue number, status and source, potentially for all active queues that day.

**Conditional reachability:** This is an actively mounted endpoint, but actual external exposure depends on reverse-proxy/WebSocket routing, firewall, and deployment policy. It is a code-level privacy control failure, **not evidence that public Internet clients have already accessed patient data**.

**Synthetic red-first:** seed two fake entries with names `SYNTHETIC ALPHA/BETA` in disposable PostgreSQL. Use TestClient.websocket_connect without any credentials to `/api/v1/display/ws/queue/cardiology`; require WS close 1008 before any payload. Repeat with invalid JWT and valid role/approved board-scoped credentials. Ensure no patient identifiers are returned on rejected sessions. Integrate shared WS token resolution and authorization before `connect`, and do not treat an Origin check as authentication.

### DISPLAYWS-BE-002 — P1: any authenticated user can subscribe to any board and its full clinic-day queue snapshot

**Source evidence:** [`websocket_display_board`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/display_websocket.py#L66-L124) verifies that a JWT resolves to **some** `User`, but never checks staff/board scope, `board_id` ownership or patient relationship. It passes the user to [manager.connect](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket.py#L46-L75), which immediately sends [`_send_current_state`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket.py#L402-L499) containing entries from **all active DailyQueue rows** for clinic today, including patient names (full if board's `show_patient_names='full'`; otherwise initials/none by configuration), specialist and queue IDs. Knowing a board_id is not a capability/authorization check.

**Synthetic red-first:** synthetic Patient A with valid token connects to configured board B whose visibility is full, while unrelated Patient B has an entry in another active queue. Assert unauthorized Patient role is rejected before any `initial_state`. Test staff role and board-specific grants, and ensure client-selected arbitrary board ID cannot bypass a board visibility policy. The absence of strong board scope is a separate issue from the entirely anonymous department route.

### DISPLAYWS-BE-003 — P1/P2: the department queue snapshot ignores the requested department and returns all queues

**Source evidence:** [`get_department_queue_state_payload(department)`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket_api_service.py#L196-L232) passes only `day=self._clinic_today()` into [`list_active_entries_for_day`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/repositories/display_websocket_api_repository.py#L29-L39), whose SQL filters `DailyQueue.day` and `active` — **not** queue tag, department or resource. It serializes **every returned entry** into `entries` but labels the entire response with the requested `department`. Thus `/ws/queue/cardiology` can include laboratory, dental and dermatology patients. Repairing WS authentication alone would still leave cross-department data leakage and incorrect total_waiting/current_number counters. This finding is about **data scoping**, not authentication, and survives adding a token check.

**Synthetic red-first:** seed an authorized cardiology queue and an unrelated lab queue with different synthetic names and statuses. Call service with department='cardiology'; require only cardiology entries plus scoped totals; call 'lab' and assert the complementary set. Define the exact department/tag/resource ownership mapping from backend SSOT, not a fragile frontend label string.

### DISPLAYCALL-BE-001 — P1: display call command can resurrect served/cancelled/no-show entries as called

**Source evidence:** Mounted [`POST /display/call-patient`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/display_websocket.py#L129-L159) accepts Admin/Registrar/Doctor and delegates to [`DisplayWebSocketApiService.call_patient`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket_api_service.py#L123-L151). The service fetches an entry, checks only Doctor queue ownership, then unconditionally sets `entry.status='called'` and commits. **It does not check status='waiting', queue.active or visit lifecycle/payment state.** A legitimate staff caller can change an already `served`, `cancelled`, `no_show`, `diagnostics` or `in_progress` ticket back to `called` and issue a false TV call. [Doctor-panel call endpoint](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/api/v1/endpoints/doctor_integration/_queue_ops.py#L598-L605) already enforces allowed `waiting` actions; this mounted display route does not.

**Synthetic red-first:** for each terminal/active-nonwaiting status, POST as authorized Registrar; assert 409, unchanged queue/Visit state and zero broadcasts. Positive control waiting-to-called exactly once, and active queue required. Use canonical transition policy and a transactional CAS/lock; do not let display UI status become a second queue lifecycle writer.

### DISPLAYCALL-BE-002 — P1/P2: quick-call assigns 'next' by printed ticket number instead of fairness order

**Source evidence:** [`quick_call_next`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket_api_service.py#L278-L298) delegates next selection to [`get_next_waiting_entry`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/repositories/display_websocket_api_repository.py#L198-L214) which sorts `OnlineQueueEntry.number ASC` only. The actual staff queue fairness selector [`staff_call_next_patient`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/queue_svc/_helpers.py#L83-L104) sorts `priority DESC`, then `coalesce(queue_time, created_at) ASC`, then `id ASC`. A restored patient with `priority=1` and ticket #12 is bypassed by a later `priority=0` ticket #3 on quick-call; the reverse is also possible if numbering was reordered. This violates the same queue's established fairness policy and is **not a duplicate** of round 29's QPOSFAIR-BE-001 (read-only people_ahead) or QPOSBATCH-BE-001 (notification recipient filter).

**Synthetic red-first:** queue Q has waiting E3 (number 3, priority 0) and E12 (number 12, priority 1). Perform `POST /display/quick/call-next`; require E12 becomes called, E3 remains waiting and the returned payload is #12. Tie-break equal priority by queue_time/created_at/id. Keep resource queue floor and QR original registration order intact.

### DISPLAYCALL-BE-003 — P1/P2: simultaneous display quick calls can select/call the same waiting entry twice

**Source evidence:** [`get_next_waiting_entry`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/repositories/display_websocket_api_repository.py#L198-L214) uses a normal read `.first()` without `FOR UPDATE`, `SKIP LOCKED`, or a conditional transition. [`quick_call_next`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket_api_service.py#L278-L298) separately fetches that row, then [`call_patient`](https://github.com/drsapaev/final/blob/a3506ffde854371a5f746584483bb61a608b4c21/backend/app/services/display_websocket_api_service.py#L123-L151) re-reads/mutates/commits without checking whether it is still waiting. Two concurrent requests can both select the same entry before either commits, and then both return success and emit calls; the next person in line remains waiting. This is a **concurrency defect**, distinct from BE-001's single-request terminal-state acceptance.

**Synthetic red-first (PostgreSQL, two independent sessions):** two simultaneous quick-call requests for a queue holding at least two synthetic waiting patients; force both reads to overlap. Assert at-most-once claim of each entry with distinct called identities and no duplicate TV event. Lock/compare status in one transaction and emit a durable event only for the winner after commit; preserve per-queue priority fairness. Do not treat SQLite or a sequential unit test as proof of concurrency correctness.
