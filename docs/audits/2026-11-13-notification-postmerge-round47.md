## NOTIFYPATIENTOWNER-BE-001 — P1 conditional: generic doctor may schedule outbound patient notifications for unrelated patients/visits

**Source.** The active [`backend/app/api/v1/endpoints/notifications.py:270–410`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/api/v1/endpoints/notifications.py#L270-L410) exposes at least three direct patient-targeted routes: `POST /notifications/send-appointment-reminder` (body/query `patient_id` plus caller-chosen appointment date, doctor name, department), `POST /notifications/send-visit-confirmation` (caller-chosen `visit_id`), and `POST /notifications/send-payment-notification` (caller-chosen `visit_id,amount,currency`). Each endpoint grants access via `Depends(require_roles(["admin","doctor"]))` but makes **no owner/relationship check** between a generic doctor and the target `patient_id` or `visit_id`. Patient and visit CRUD are looked up by provided ID alone; the actual `patient.email`/`patient.phone` and request-scoped `db` are passed to `background_tasks.add_task(notification_sender_service.send_...)` with an HTTP “sent” acknowledgment. For the reminder sender, [`notifications_pkg/_appointments.py:17–84`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notifications_pkg/_appointments.py#L17-L84) attempts push/email/SMS/Telegram based on those details.

**Risk and qualification.** A **valid but unassigned doctor** can invoke patient-targeted communications for arbitrary patient or visit IDs, including misleading payment/booking details, **unless separate business rules intentionally authorize every doctor to communicate with every patient**. The code shown has no doctor/visit ownership verification in these specific routes. Actual provider delivery, scope of authorized clinic staff, absence of upstream route policy and whether these endpoints are used in production require runtime/product confirmation. This is **not** a proven PHI disclosure, external delivery or financial transaction. Distinct from group-46 `NOTIFYQUEUEACTOR-BE-001`: that finding addresses **department queue status publication**, while this one targets **individual patient contact channels and arbitrary visits**.

**Synthetic fail-first:** seed Doctor A assigned patient/visit 1, Doctor B unassigned patient/visit 1, an Admin allowed by documented policy, and a target patient with dummy email/phone. As B, call each of the three notification routes targeting patient/visit 1; require denial (403 or documented safe 404), **no BackgroundTask queued**, no email/SMS/Telegram/push, no changes to underlying financial/visit state. As assigned Doctor A, check server-authoritative sender/visit relationship and non-forgeable payment/appointment details; as Admin verify explicit audited override. Include inactive users, missing assignment and ID enumeration safety. If global-staff messaging is an approved policy, document it and test specific authorized roles instead of assuming doctor assignment. Mandatory auth/clinical/DB gate before any code fix.

## NOTIFYBURSTCROSSTYPE-BE-001 — P2 conditional: anti-noise rule suppresses a distinct queue/diagnostics realtime event solely due to shared queue entity

**Source.** [`notification_platform/_base.py:54–74`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notification_platform/_base.py#L54-L74) includes **`queue_update`, `queue_position`, `queue_reminder`, `diagnostics_return_needed`, `queue_status_changed`** in a common **45-second** burst-suppression family. [`notification_platform/_policy.py:223–276`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notification_platform/_policy.py#L223-L276) checks the latest existing delivery from **any** family member with the same recipient/channel and, after joining the event, suppresses the new event's WS broadcast if its `entity_type,entity_id` match. It does **not require the event types or messages to match** for that `same_entity` branch. The typed [`notifications_pkg/_canonical.py:352–390`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notifications_pkg/_canonical.py#L352-L390) queue-family producer passes `entity_type="queue"` and `entity_id=(metadata or {}).get("queue_id")` for these events. The [`_broadcast_delivery_with_policy`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notification_platform/_policy.py#L280-L325) uses this anti-noise guard *after persistence* to decide whether to send realtime.

**Conditional failure.** User receives `queue_position` for queue Q and, **under 45 seconds later**, a *different and actionable* `diagnostics_return_needed` for the same queue Q. If both share `entity_type=queue, entity_id=Q`, the second **persists** but its realtime WS delivery is suppressed even though the domain type, title and actual action differ. The user may not see the return-needed prompt until inbox refresh. The existing [same-type duplicate anti-noise regression tests](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/tests/unit/test_notification_platform_contract.py#L316-L444) cover repeated `queue_update` and explicitly exempt `queue_call`; they do **not** test unlike event types sharing a queue entity. This is **not** the group-45 occurrence dedup issue (both different events have distinct DB delivery IDs), nor the group-41 general blocked-socket fan-out issue. P2 conditional on such a same-queue event transition and expected realtime prompt behavior.

**Synthetic fail-first:** create synthetic user with enabled realtime and queue Q, no DND; record a `queue_position` then `diagnostics_return_needed` for same Q with different messages, <45s apart. Assert two persisted deliveries AND **two WS events** (unless documented product policy consciously excludes the action); repeat same-type duplicate `queue_update` with modified retry metadata and assert intentional burst suppression retained; verify `queue_call` remains never suppressed. Include a different queue/entity negative case and no cross-principal delivery. Any fix should match **event-semantic equivalence**, not just common queue ID, via mandatory queue/WS gate.

## NOTIFYMUTATIONTOAST-FE-001 — P2: seen/read/archive state changes emit a new toast or desktop notification rather than quietly updating an existing item

**Source.** The canonical state-mutators [`notification_platform/_rest.py:442–479`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notification_platform/_rest.py#L442-L479) call `_broadcast_delivery(user.id, updated)` for each successful `mark_seen`, `mark_read` and `archive`. That method [`_broadcast_delivery` lines 16–57](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notification_platform/_rest.py#L16-L57) emits a personal frame with **`type: "notification"`**, same `delivery_id`, and status flags `is_seen/is_read/is_archived`; no distinct mutation-only transport type. The [`NotificationWebSocketContext.tsx:248–297`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/frontend/src/contexts/NotificationWebSocketContext.tsx#L248-L297) suppresses toasts for explicit `notification_*_ack` frames but **any** `transportType==="notification"` falls into the *new delivery* branch, calls `appendNotification` and unconditionally displays `notify[toastType](...)`; hidden tabs also create a native `Notification` when permission granted.

**Concrete result:** user receives a lab or message notification, clicks “Read”/“Archive” in one tab, and the update is delivered via WS to the same user: the event triggers **another popup/sound/native notification** with the old original content on their tabs. The UI merges the delivery ID, but only dedupes the **inbox row**, not the foreground toast. It can spuriously re-alert private clinical content on a desktop after the user intentionally acknowledged it.

**Distinctness:** previous group-40 `NOTIFYTOAST-FE-001` concerned **duplicate delivery frames** of the *same new notification* being replayed by the transport. This is a distinct **server-originated state mutation** with changed `read/seen/archive` flags; a fix must classify new deliveries versus mutations, regardless of repetition. Group-46 `NOTIFYMUTATIONTIME-BE-001` addressed duplicate mutation timestamp integrity, not toasting. No live notification permission was exercised.

**Synthetic fail-first:** Vitest render two tabs/contexts or WebSocket mock with one existing unread delivery ID. Emit first `type:"notification"` new-event => one toast; simulate POST /{id}/read and receive the server `type:"notification",is_read:true` for same delivery => **zero additional toasts, zero native notifications**, but badge/inbox state becomes read. Repeat seen/archive and queue/system transport types; an independent **new** ID must still toast once and second-tab state converge. No content should leak into logs. Preserve future muted/critical exception policy and the separate older duplicate-delivery dedup test. Source fix requires WS/client contract gate and exact-head test proof.

## NOTIFYCHATDEEPLINK-BE-001 — P2: canonical incoming-chat notifications link to an unmounted SPA route and use the wrong query contract

**Source.** [`notifications_pkg/_system.py:244–308`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notifications_pkg/_system.py#L244-L308) records an actionable `message_received` delivery and has the correct `conversation_id` inside `payload_snapshot.metadata`, but explicitly sets **`deep_link=f"/messages?user={sender.id}"`**, ignoring the conversation ID. The notification UI's [`NotificationInbox.resolveNotificationTarget` lines 75–93](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/frontend/src/components/notifications/NotificationInbox.tsx#L75-L93) prioritizes **explicit `deepLink` over any event-type fallback**. The fallback for chat is `/messages?conversation=<conversation_id>`, **not** `?user=<sender.id>`. The [frontend inbox route tests](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/frontend/src/components/notifications/__tests__/NotificationInbox.test.tsx#L129-L170) mock-register a `/messages` Route and test the fallback case without the producer's explicit deepLink. The actual [`frontend/src/routing/routeRegistry.ts`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/frontend/src/routing/routeRegistry.ts) **has no `/messages` or chat route** in its canonical registered paths, while [`App.tsx:465–494`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/frontend/src/App.tsx#L465-L494) renders SPA paths exclusively from `ROUTE_REGISTRY` plus legacy redirects, then sends everything else to `/not-found`.

**Effect:** clicking a persisted incoming-message notification with the backend's explicit link takes the SPA to `/messages?user=...`, a path not mounted in the canonical app. Because it is explicit, the UI cannot fall back to the metadata's `conversation_id`. The guarded navigator itself may correctly enforce unsaved-lab-draft protection, but the **target route is not a usable chat conversation**. Source-verified routing inconsistency; no live browser run and no claim that a hidden old route is still mounted.

**Distinction:** earlier `NOTIFYOPENBLOCK-FE-001` was failure to navigate after HTTP mark-as-read error; here **navigation is attempted/succeeds to an invalid route** after an otherwise successful click. Earlier group-44 had known route fallback context but no source-anchored specific producer URL/registry mismatch. This does not duplicate general unread/WS issues.

**Synthetic fail-first:** obtain one synthetic canonical `message_received` delivery from actual backend producer with `conversation_id="1:2"`; assert `deep_link` is either an allowed registered chat destination using this conversation ID or an explicit, safe UI action for the existing chat panel — **not** an unregistered `/messages?user=2` route. Mount the **real** route registry, click notification via guarded nav, assert a chat surface opens for the correct conversation without falling through `/not-found` and without allowing wrong-role/other-account access. Add contract test that uses actual producer payload rather than a test-only synthetic fallback. Any fix must resolve real chat route ownership, not guess `/messages` exists; mandatory route/UI/backend contract gate.
