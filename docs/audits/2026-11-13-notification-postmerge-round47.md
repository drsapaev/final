## NOTIFYPATIENTOWNER-BE-001 — P1 conditional: generic doctor may schedule outbound patient notifications for unrelated patients/visits

**Source.** The active [`backend/app/api/v1/endpoints/notifications.py:270–410`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/api/v1/endpoints/notifications.py#L270-L410) exposes at least three direct patient-targeted routes: `POST /notifications/send-appointment-reminder` (body/query `patient_id` plus caller-chosen appointment date, doctor name, department), `POST /notifications/send-visit-confirmation` (caller-chosen `visit_id`), and `POST /notifications/send-payment-notification` (caller-chosen `visit_id,amount,currency`). Each endpoint grants access via `Depends(require_roles(["admin","doctor"]))` but makes **no owner/relationship check** between a generic doctor and the target `patient_id` or `visit_id`. Patient and visit CRUD are looked up by provided ID alone; the actual `patient.email`/`patient.phone` and request-scoped `db` are passed to `background_tasks.add_task(notification_sender_service.send_...)` with an HTTP “sent” acknowledgment. For the reminder sender, [`notifications_pkg/_appointments.py:17–84`](https://github.com/drsapaev/final/blob/3c37aa46b1508c49568a280ef28102d282ca233d/backend/app/services/notifications_pkg/_appointments.py#L17-L84) attempts push/email/SMS/Telegram based on those details.

**Risk and qualification.** A **valid but unassigned doctor** can invoke patient-targeted communications for arbitrary patient or visit IDs, including misleading payment/booking details, **unless separate business rules intentionally authorize every doctor to communicate with every patient**. The code shown has no doctor/visit ownership verification in these specific routes. Actual provider delivery, scope of authorized clinic staff, absence of upstream route policy and whether these endpoints are used in production require runtime/product confirmation. This is **not** a proven PHI disclosure, external delivery or financial transaction. Distinct from group-46 `NOTIFYQUEUEACTOR-BE-001`: that finding addresses **department queue status publication**, while this one targets **individual patient contact channels and arbitrary visits**.

**Synthetic fail-first:** seed Doctor A assigned patient/visit 1, Doctor B unassigned patient/visit 1, an Admin allowed by documented policy, and a target patient with dummy email/phone. As B, call each of the three notification routes targeting patient/visit 1; require denial (403 or documented safe 404), **no BackgroundTask queued**, no email/SMS/Telegram/push, no changes to underlying financial/visit state. As assigned Doctor A, check server-authoritative sender/visit relationship and non-forgeable payment/appointment details; as Admin verify explicit audited override. Include inactive users, missing assignment and ID enumeration safety. If global-staff messaging is an approved policy, document it and test specific authorized roles instead of assuming doctor assignment. Mandatory auth/clinical/DB gate before any code fix.
