## NEW P2 conditional current-main finding — `NOTIFYLABSMSRACE-BE-001`: check-then-send history is not an atomic delivery claim

1. [`LabNotificationService._lab_sms_delivery_exists`](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/services/lab_notification_service.py#L102-L118) checks for a completed/sent `NotificationHistory` row matching patient, order, channel, and notification type.
2. [`_notify_patient_results_ready` around L182–239](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/services/lab_notification_service.py#L182-L239) acts on this **read-only result** and awaits the external `send_sms` provider **before** adding/flushing the history row. [`check_and_notify_ready_results` around L121–143](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/services/lab_notification_service.py#L121-L143) commits the history only after iterating all ready orders.
3. [`NotificationHistory` ORM](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/models/notification.py#L184-L230) has no uniqueness constraint on (patient, order, channel, type). Two concurrent jobs or workers can both observe no history, both call the provider, and then both insert `status='sent'`. There is no row lock, atomic claim, durable outbox lease, or provider idempotency key in this path.
4. **Existing coverage:** [`test_lab_result_sms_success_is_recorded_and_not_repeated`](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/tests/unit/test_notification_audit_round47_52.py) calls the service **sequentially** in one `db_session` and asserts one send. This does not cover overlapping independent transactions.
5. **Scope/dedup:** distinct from `NOTIFYEVENTDEDUPRACE-BE-001` (notification event/inbox persistence); this candidate concerns **external SMS** accepted by provider before history exists. It is not a report of a reproduced customer incident. Severity **P2 conditional**: repeat SMS and potential duplicate cost/noise under simultaneous invocations.

**Required fail-first validation:** Use disposable PostgreSQL and two independently opened sessions, one completed synthetic `LabOrder` and synthetic phone, a barrier in the stub SMS provider to overlap the interval after the absent-history check and before history insertion. Launch `check_and_notify_ready_results()` concurrently; assert at most one provider delivery attempt per order in the overlapping-success case, exactly one durable sent marker and a valid retry on failed/unacknowledged delivery. Test process restart/retry, timeout/expired lease and a correction to prior result separately. Do **not** use SQLite to claim lock/concurrency correctness. Proposed fix should use a durable claim/lease or a transactional outbox with unique key + lease/expiry and provider idempotency when supported; a unique index on the *post-send* history row alone cannot undo a duplicate external send. Respect DB/Alembic first-touch and mandatory protected source gate before implementation.

## Additional review-only lifecycle candidate — request-scoped SQLAlchemy session passed to background notification tasks

[Mounted `notifications.py` send-appointment/visit/payment/queue/system/bulk routes](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/api/v1/endpoints/notifications.py#L318-L509) pass a `db: Session = Depends(get_db)` object into `BackgroundTasks.add_task` instead of passing plain IDs. [`db/session.py:get_db`](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/db/session.py#L200-L230) closes the session in dependency `finally`. [`AppointmentsMixin.send_appointment_reminder`](https://github.com/drsapaev/final/blob/2329735d4580b00621d6803d1854ab1e8ffd76a3/backend/app/services/notifications_pkg/_appointments.py#L10-L83) can issue DB queries, then await external sends via the session.

This pattern is structurally fragile (dependency lifetime/thread ownership and long external awaits). FastAPI guidance says background tasks should create their own resources and take scalar identifiers rather than request-bound sessions; SQLAlchemy `Session.close()` normally resets and permits reuse, so **do not assume** a simple "closed session" exception: depending on framework scope, re-use can implicitly open a new transaction after request cleanup. No current-head background-lifecycle test or observed pool exhaustion has been established. This was **already present before #4060**, and its exact impact must be evaluated against the installed FastAPI version, not attributed to #4060. **No new issue ID added here pending runtime reproduction.**

**Focused test:** instrument `SessionLocal` checkout/checkin and dependency-finally behavior on the installed FastAPI version for each relevant route with a slow/failing stub sender. Require each background handler to own and close its own short-lived session; no request session should be reused after its scope ends, and provider hangs must not pin a transaction for the entire await. Compare 10+ concurrent sends to pool limits. Separate any resulting source fix from the lab SMS claim fix.
