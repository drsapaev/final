### Independent high-risk P1 conditional — new callback writes a payment-equivalent status without payment verification (proposed fix only)

**Code:** [#4076 `backend/app/services/telegram/bot.py:317–352`](https://github.com/drsapaev/final/blob/a775c70b368f2fc1cbb21d12a3febf40e69e3033/backend/app/services/telegram/bot.py#L317-L352) introduces `_handle_appointment_decision` for `confirm_<appointment_id>`. It checks `TelegramUser.patient_id == Appointment.patient_id` then, for `appt.status in ("pending", "scheduled")`, unconditionally sets **`appt.status = "confirmed"; db.commit()`**.

**Conflict with source-of-truth:** [current `backend/app/models/enums.py`](https://github.com/drsapaev/final/blob/b142a30dc433dbd2486a421f1b8ba1c0a5cabb9a/backend/app/models/enums.py) defines `APPOINTMENT_STATUS_MAPPING = {"scheduled": PENDING, "confirmed": PAID, ...}`, `normalize_appointment_status("confirmed") -> AppointmentStatus.PAID`, lifecycle `PENDING→PAID→IN_VISIT→COMPLETED`, and `can_transition_status`. [CRUD `update_status`/ `mark_paid`](https://github.com/drsapaev/final/blob/b142a30dc433dbd2486a421f1b8ba1c0a5cabb9a/backend/app/crud/appointment.py#L332-L394) validates transitions and marks paid using the payment state, whereas the new Telegram handler does not look up paid payment/invoice or capture RSVP separately. Any consumer normalizing `confirmed` now sees a **paid-equivalent** appointment after a patient's button click without payment evidence. This creates potential billing/clinical workflow inconsistency; **no real bypass of visit-start/payment acceptance has been demonstrated**. P1 conditional due financial lifecycle semantics and protected medical workflow.

**Accepted remediation:** obtain explicit product/owner distinction between *RSVP acknowledgment* and *financial PAID*, persist RSVP separately or via an owner-approved policy/event, preserve payment SSOT before any normalized PAID transition, and add a real endpoint/DB test for an unpaid appointment which confirms via Telegram yet remains financially unpaid. Don't "fix" by changing global normalization without assessing other consumers; use mandated gate.

### Independent P2 — new Telegram cancel callback violates NO_SHOW terminal state

The same [`bot.py:342–350`](https://github.com/drsapaev/final/blob/a775c70b368f2fc1cbb21d12a3febf40e69e3033/backend/app/services/telegram/bot.py#L342-L350) blocks `cancelled` and `completed`, but on `cancel_<id>` it accepts `no_show` and commits `status="cancelled"`. [Canonical `can_transition_status`](https://github.com/drsapaev/final/blob/b142a30dc433dbd2486a421f1b8ba1c0a5cabb9a/backend/app/models/enums.py) explicitly sets `AppointmentStatus.NO_SHOW: []` (**terminal**). [`CRUDAppointment.update_status`](https://github.com/drsapaev/final/blob/b142a30dc433dbd2486a421f1b8ba1c0a5cabb9a/backend/app/crud/appointment.py#L332-L361) rejects that transition, but the new Telegram code writes SQLAlchemy model status directly. A stale reminder button can therefore rewrite a finalized no-show into cancelled, affecting no-show accounting and lifecycle. Add failing test: linked patient, existing appointment `no_show` + `cancel_<id>` → status unchanged and explicit denial; then use canonical transition/locking logic. Also consider simultaneous confirm and cancel on same row. This remains a proposed-fix regression, not a new main ID.
