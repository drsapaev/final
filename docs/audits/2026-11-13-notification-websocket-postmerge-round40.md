### NOTIFYPOOL-BE-001 — P1 conditional: personal WebSocket sessions pin SQLAlchemy/PostgreSQL pool capacity

**Source evidence.** The mounted [`websocket_notifications` handler](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/backend/app/api/v1/endpoints/notification_websocket.py) starts with `db = SessionLocal()`, uses that same session in `authenticate_websocket_token` (user lookup, token blacklist), calls `get_notification_platform_service(db)` and `get_unread_counts` (database query), then enters a potentially unlimited `while True: await websocket.receive_text()`. **`db.close()` appears only in the final `finally` after disconnect**. No transaction-ending `commit`, `rollback`, or session `close` occurs after the initial reads and before the awaited receive loop. SQLAlchemy 2's implicit read transaction normally retains its checked-out connection until the session transaction ends. The backend [`db/session.py`](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/backend/app/db/session.py) defaults to a PostgreSQL engine pool of 8 connections plus 2 overflow per process and a 60-second checkout timeout. Ten legitimate concurrent personal-notification sockets could therefore exhaust the application's per-process DB pool or leave sessions `idle in transaction`, so unrelated API operations wait/fail.

**Important boundary.** Holding an unqueried Session object does not by itself check out a DB connection; this concern depends on the confirmed authentication and unread-query calls before the first long await. The real PostgreSQL pool behavior has **not** been measured by this reviewer. This is **a different mounted endpoint and database/session owner** from `LEGACYWSPOOL-BE-001` in round 39, despite analogous mechanism.

**Synthetic fail-first.** Run an isolated FastAPI/WS test against disposable PostgreSQL configured with `DB_POOL_SIZE=1, DB_POOL_OVERFLOW=0`. After a valid synthetic staff JWT and successful `connection_established` from one held-open WS, query another endpoint in parallel and assert immediate pool availability. Inspect `engine.pool.checkedout()` or `pg_stat_activity`; no WebSocket-auth connection may persist as `idle in transaction`. Repeat with two sockets and an unread-count lookup, plus negative auth rejection. Re-check after socket closes and after notification seen/read/sync frames. Repair through **short-lived handshake and per-action DB session scopes** and stable primitive principal identity, not long-lived ORM sessions; preserve security/role checks. The existing #3974 frontend suite does not exercise this PostgreSQL lifetime contract.

### NOTIFYRELAY-BE-001 — P2 conditional: personal WS ignores false Redis SUBSCRIBE and has no same-socket recovery

**Source evidence.** [`NotificationWebSocketManager.connect`](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/backend/app/services/notification_websocket.py#L41-L49) accepts the socket, adds it to `active_connections`, then awaits `_ensure_user_subscription`. In [lines 69–86](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/backend/app/services/notification_websocket.py#L69-L86), the manager creates/caches `_pubsub_handlers[user_id]` then simply executes `await self._pubsub.subscribe(...)` in a `try` block; **the boolean return is discarded**, and only an exception logs a warning. The shared [`RedisPubSubBridge.subscribe` contract](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/backend/app/services/ws_redis_pubsub.py#L117-L163) expressly returns `False` when Redis is unavailable or the subscription fails and removes its handler on failure. The still-live personal socket is reported as connected, but **no per-user Redis subscription exists on that worker**. There is no periodic `_ensure_user_subscription` retry while that socket stays connected; a future *new* socket might retry, but does not repair an already stable one. Local same-worker sends may work, disguising the cross-worker outage.

**Scope.** This is not the previously audited/fixed `DISPLAYRELAY-BE-003` or `QUEUEWS-POST4008-SUBSCRIBE-01`: those concern separate board and queue managers. It is also distinct from the round-36 `NOTIFYDELIVERY-BE-001` dead-socket send pruning issue and the frontend replay-on-reconnect `NOTIFYREPLAY-FE-001`. Redis currently disabled by configuration may be an intentional single-worker mode; a real cross-worker claim requires Redis-enabled deployment.

**Synthetic fail-first.** With two synthetic worker managers, use a controlled Redis bridge whose first `subscribe` returns `False` and later recovers. Keep one authenticated socket open with **no new connects**. After recovery, publish a remote event on `user:<id>` and assert that the live socket eventually receives it, or is clearly marked degraded and reconnects. Test initial subscription raising, successful true result, two sockets sharing a user, last-disconnect unsubscribe and reconnect races. Use bounded re-subscribe/recovery, retaining handler only when the bridge confirms success. Do not log notification payloads.

### NOTIFYTOAST-FE-001 — P2: delivery-ID deduplication does not deduplicate toasts or native notifications

**Source evidence.** The current [notification context handler, lines 244–278](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/frontend/src/contexts/NotificationWebSocketContext.tsx#L244-L278), calls `appendNotification` for each accepted notification frame and **unconditionally** calls `notify[toastType](toastMessage)`; when document is hidden and browser permission is granted, it also **unconditionally** creates `new Notification(...)`. In [`NotificationCenterContext.tsx`'s `appendNotification`](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/frontend/src/contexts/NotificationCenterContext.tsx), the same stable delivery ID updates an existing item by identity and returns `normalized`, but provides no duplicate-vs-new flag to the caller. The shared [`notify` wrapper](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/frontend/src/services/notify.ts) passes only a message and generic options to `react-toastify`; it does not use a stable `toastId`. Hence two identical WS frames with the same `delivery_id` leave one inbox record but trigger two toasts and (when hidden) potentially two OS notifications.

**Scope and non-duplication.** The #3974 implementation plan explicitly mentions duplicate toast as a separate adjacent concern, not fixed by its single-envelope routing patch; this is the separately reviewed candidate. Backend/reconnect duplicates are *possible*, not a measured frequency. Do not claim repeated database persistence or duplicate notification deliveries when only the UI alert is repeated.

**Synthetic fail-first.** In the active provider Vitest suite, send identical `{type:"notification",notification:{delivery_id:"synthetic-1",event_type:"lab_results",...}}` twice. Assert **one visible toast and one native notification** for that delivery ID while inbox still has one entry, and two distinct IDs produce two alerts. Re-mount or reconnect and define bounded dedup lifetime. One solution is stable `toastId`/client-side delivery-ID cache with bounded memory and clear user-session isolation. Do not suppress legitimate manual resend events with distinct IDs.

### NOTIFYREJECT-FE-001 — P2 conditional: rejected personal WebSocket reconnects forever every three seconds

**Source evidence.** The [provider's `scheduleReconnect`](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/frontend/src/contexts/NotificationWebSocketContext.tsx) sets a **fixed 3000ms timeout** and calls `connectRef.current?.()` while `shouldReconnect.current` remains true. `socket.onclose` schedules it for **every** close regardless of code or reason. The next `connect` only checks `tokenManager.getAccessToken()` and `isTokenValid()`, whose client-side logic validates JWT format/`exp`, not account deactivation or backend revoke-all sentinel. The server [rejects failed notification JWT auth before accept](https://github.com/drsapaev/final/blob/33de660fae922001becb52048cab6559d542ca2a/backend/app/api/v1/endpoints/notification_websocket.py). Therefore a still-unexpired but server-revoked/disabled-user token repeatedly attempts the WS handshake approximately every three seconds for as long as the provider remains on a protected route, even when rejection is permanent. Pre-accept denial often manifests as browser `1006` rather than a clean `1008`; the client has no terminal-vs-transient distinction, and no capped exponential backoff/jitter.

**Scope.** This is a personal-notification provider-specific network/UX issue, **not** the existing display-board `DISPLAYWS-FE-004` reconnect exhaustion issue. A navigation to a public route or expiry of the local token can stop new attempts, so “forever” means while protected route and a locally valid/revoked token persist.

**Synthetic fail-first.** In provider tests, open on a protected route with a synthetically unexpired JWT; simulate repeated unauthorized handshakes (`1008` and browser `1006`) while backend identity has been revoked. Assert retries stop or enter a bounded/observable auth-refresh strategy after a terminal verification, never silently loop every 3 seconds. Separately simulate transient `1006` (Redis/proxy flake) and verify bounded exponential backoff with jitter and recovery; switching to public route/unmount cancels all timers. Honor token refresh/logout authority and do not append JWT to URL.

### NOTIFYFANOUT-BE-001 — P2 conditional: a backpressured personal socket blocks healthy recipients and cross-worker Redis publication

**Source:** [`NotificationWebSocketManager._send_json_local` lines 120–132](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/backend/app/services/notification_websocket.py#L120-L132) loops **serially** over a same-user socket list and awaits each local `connection.send_json(data)` with **no send timeout**. The public [`send_json` method, lines 175–184](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/backend/app/services/notification_websocket.py#L175-L184), awaits that entire local fan-out **before** calling `_pubsub.publish_ephemeral(user:<id>, data)`. A connected but nonreading/browser-stalled socket that suspends on an ASGI send can prevent subsequent healthy same-user local sockets **and the cross-process Redis relay** from receiving that notification. Sending from a foreign thread schedules onto the connection home loop and returns without awaiting it, so this specific ordering hazard is most direct for a publisher on the **same application loop**. Do not claim it necessarily occurs in all production networks; ASGI/proxy send timeouts and worker loop topology need verification.

**Non-duplication:** unlike `QUEUEWSFANOUT-BE-001` (round 38, **canonical queue room** manager), this is the **personal-notification user-channel manager**, with different delivery call sites and a dedicated outbox/Redis relay. Not the already-known `NOTIFYDELIVERY-BE-001` (failed send does not prune a dead socket): **a slow unresolved await** is different from a send that raises.

**Synthetic fail-first:** two locally connected fake sockets for the same synthetic user (first `send_json` awaits an unset Event, second records data) and a fake Pub/Sub publisher recorder. Invoke `manager.send_json`, place a bounded `asyncio.wait_for` around **healthy-recipient and publish** completion, assert they both finish despite the nonreader and that the stuck socket is handled by a bounded backpressure policy. Include foreign-loop scheduling, last-disconnect and duplicate relay suppression; ensure no PHI in logs. A concurrent, bounded send strategy or per-socket outbound queue with explicit delivery policy is required. This is a static source hypothesis, no measured Redis outage.

### NOTIFYFRAME-BE-001 — P2 conditional: authenticated malformed JSON values crash the personal WS command loop instead of receiving a bounded validation response

**Source:** [`websocket_notifications` lines 60–72](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/backend/app/api/v1/endpoints/notification_websocket.py#L60-L72) catches only `json.JSONDecodeError`; valid JSON **array, string, integer, boolean or `null`** survives parsing and is immediately dereferenced using `payload.get("type")`. For `[]` or `null` that raises `AttributeError`, handled by the **outer endpoint exception**, which logs and closes the entire socket with WS 1011 rather than rejecting just the malformed command. Additionally [`notification_sync` line 185](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/backend/app/api/v1/endpoints/notification_websocket.py#L170-L192) casts `limit=int(payload.get("limit") or 50)` **without a local `ValueError/TypeError` guard**, despite having one for cursor; e.g. `{"type":"notification_sync","limit":"nope"}` tears down a previously authenticated connection.

**Impact and overlap:** a valid staff/client session can be unexpectedly disconnected by a protocol-invalid application frame; repeated malformed client traffic can interact with the separately **already-reported** `NOTIFYSESSION-BE-001` cleanup deficiency. **Do not** count the missing outer `manager.disconnect` a second time here, and do not conflate non-numeric limit with the old `NOTIFYSYNC-BE-001` unbounded **numeric** limit; those have separate existing IDs. No claim of unauthenticated remote server crash, data corruption or confirmed DoS. Priority conditional P2 transport resilience.

**Synthetic fail-first:** with a real authenticated synthetic WebSocket TestClient session, send `[]`, `null`, `"hello"`, `{"type":"notification_sync","limit":"nope"}`, then a valid `notification_sync`; assert malformed commands yield explicit bounded rejection/error without tearing down a valid session, no unbounded query or stack trace; verify manager removes socket on genuinely terminal close. Preserve existing authorization scope and max-limit policy, which is a separately tracked issue.

### NOTIFYACK-FE-001 — P2 latent: total unread is updated after WS ACK but role counters remain stale

**Source:** [`notification_websocket.py:83–163`](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/backend/app/api/v1/endpoints/notification_websocket.py#L83-L164) sends `notification_seen_ack`, `notification_read_ack`, `notification_archive_ack` and `notification_mark_all_read_ack` containing `unread_count` **without** `by_role`, `by_channel` or `by_severity`. The [frontend WebSocket handler lines 234–242](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/frontend/src/contexts/NotificationWebSocketContext.tsx#L234-L242) invokes `applyUnreadSnapshot(data)` on ACK, which passes `{total,by_role:null,by_channel:null,by_severity:null}` via `updateUnreadSnapshot(...,{replace:false})`. In [`NotificationCenterContext.applyUnreadSnapshot` lines 569–590](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/frontend/src/contexts/NotificationCenterContext.tsx#L569-L590), merge mode replaces `total` but on missing per-role backend breakdown the constructed keys are **null, not undefined**, so `by_role` becomes **null**. In `getUnreadCount(role)` [lines 934–946](https://github.com/drsapaev/final/blob/0621df8e97213ec52f1051c70548c595c8d11204/frontend/src/contexts/NotificationCenterContext.tsx#L934-L946), the role count then falls back to the count of local inbox entries rather than authoritative unread snapshot; **ACK handling does not change those inbox rows to seen/read/archived**, and does not refresh them. Thus a successful `notification_mark_all_read_ack` with `unread_count:0` can coexist with an inbox full of locally still-unread notifications and a nonzero role-specific badge even though total is zero.

**Correction to initial hypothesis:** this is **not** merely “the old by_role counters are retained”; the actual wrapper constructs null keys, causing the shared snapshot merger to clear role breakdowns. The observed issue is **mismatched total vs local per-role fallback** after ACK, until a fresh inbox sync updates row state. This distinction is required for test correctness.

**Reachability caveat:** code search found no first-party component currently calling exported `useNotificationWebSocket()` to send WS commands; the app's `NotificationCenterContext` usually uses HTTP mutation APIs. The ACK path nevertheless exists in mounted backend and active context, so this is **latent/conditional on using WS mutation commands**, not a claim of broken current HTTP mark-read functionality. It is independent of round-40 duplicate toasts and of previous `NOTIFYREPLAY-FE-001` on reconnect.

**Synthetic fail-first:** seed one synthetic role `doctor` notification with `isRead=false` and per-role count 1, emit `notification_mark_all_read_ack` with `unread_count:0`; assert both `getUnreadCount(null)` and `getUnreadCount("doctor")` resolve to zero, inbox item updated/authoritatively re-synced and no unintended extra toast. Repeat for read/seen/archive ACK, and a negative ACK/nonexistent delivery. A fix should apply ACK state by delivery ID and/or rehydrate bounded inbox+role snapshot; avoid inventing per-role truth from an incomplete total-only ACK.

### NOTIFYSEQ-BE-001 — P1 conditional: concurrent deliveries can reuse a non-unique sequence and cursor pagination silently skips one

**Evidence.** [`NotificationPlatformRepository.get_next_sequence_id`](https://github.com/drsapaev/final/blob/ce8c23f61077b6b4c72469ea7dbcf2a88f3be932/backend/app/repositories/notification_platform_repository.py#L70-L81) calculates `MAX(sequence_id) WHERE recipient_id=:id` then returns `max+1` with **no recipient lock/atomic allocator**. [`_create_or_get_delivery`](https://github.com/drsapaev/final/blob/ce8c23f61077b6b4c72469ea7dbcf2a88f3be932/backend/app/services/notification_platform/_policy.py#L579-L635) uses that number for the insert. [`NotificationDelivery`](https://github.com/drsapaev/final/blob/ce8c23f61077b6b4c72469ea7dbcf2a88f3be932/backend/app/models/notification.py#L74-L121) has a **non-unique** `(recipient_id,sequence_id)` index, while its separate unique dedup constraint only covers recipient+channel+dedup_key. Two PostgreSQL transactions for *distinct* notifications of the same recipient can both read `max=N` and insert `N+1`. The [inbox query](https://github.com/drsapaev/final/blob/ce8c23f61077b6b4c72469ea7dbcf2a88f3be932/backend/app/repositories/notification_platform_repository.py#L83-L154) orders by `sequence_id DESC,id DESC`, but follows cursor with **strictly `sequence_id < cursor`**. Thus if two rows share the boundary `sequence_id`, the next page skips the second row entirely. The total-count result may still claim two items, masking the gap.

**Synthetic interleaving:** start disposable PostgreSQL with per-recipient last sequence N, start two separate transactions, barrier both immediately after `get_next_sequence_id(R)`, insert two events with different dedup keys, commit. Assert **unique, monotonic per-recipient sequences** and that `limit=1` page traversal returns **both** delivery IDs once without skipping any. Repeat under load. This cannot be settled reliably by an isolated SQLite test and was **not run**. Fix needs gated DB ownership: transaction-safe allocator/row or per-user counter lock, DB uniqueness plus migration, collision retry, and cursor tie-break integrity. Do not classify as confirmed real-world missed clinical notification without concurrency proof. Separate from previously filed WS sync `limit` issue and from group 41 identity mixing.

### NOTIFYROLLBACK-FE-001 — P2: failed optimistic read/archive mutation remains sticky after authoritative inbox reload

**Evidence.** Active [`NotificationCenterContext.markAsSeen/markAsRead/archiveNotification` methods](https://github.com/drsapaev/final/blob/ce8c23f61077b6b4c72469ea7dbcf2a88f3be932/frontend/src/contexts/NotificationCenterContext.tsx#L810-L885) optimistically set `isSeen=true`, `isRead=true` or `isArchived=true`, then on HTTP error call `syncNotifications()`. Existing optimistic **true** therefore always survives the successful recovery fetch. A transient 500, 403 or network timeout on a mutation may leave a notification marked read or archived in the UI when the server did **not** accept that mutation. It is **not** round-41 `NOTIFYACK-FE-001` about latent WebSocket ACK totals: this error occurs in the actual HTTP mutation+resync path.
