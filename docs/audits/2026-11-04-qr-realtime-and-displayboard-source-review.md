### QR-FE-008 — Queue-scoped WS refresh destroys multi-queue board read-model (P1)

**Code.** Backend [`display_websocket.py` L248–264](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/services/display_websocket.py#L248-L264) forms a `queue_entries` list for **one** `daily_queue.id`, broadcasts to **all connected boards** [L315–349](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/services/display_websocket.py#L315-L349). For every `event_type !== 'queue.created'`, [L598–607](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/services/display_websocket.py#L598-L607) sends this subset via `broadcast_daily_queue_state`. Frontend [`DisplayBoardUnified.tsx` L387–423](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DisplayBoardUnified.tsx#L387-L423) calls `setQueueData(subset.map(...))` for such updates, thus **replacing the entire board**. On connection, however, [backend `display_websocket.py` L404–480](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/services/display_websocket.py#L404-L480) builds `initial_state` by iterating **all active queues** for the board. A multi-queue board showing A+B loses B after a `queue.updated` event for A, until a full snapshot arrives by reconnect/reload. Neither component nor event carries an explicit replace-global/replace-queue mode.

**Risk.** TV may incorrectly hide waiting patients in untouched departments and show only the most recently changed queue; canonical ticket/ordering database records remain unmodified. This is presentation read-model data loss, **not** queue fairness mutation. The current test [`DisplayBoardUnified.contract.test.tsx` L149–168](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/__tests__/DisplayBoardUnified.contract.test.tsx#L149-L168) sends only **one queue**; the same file's two-owner test uses initial_state only [L170–198](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/__tests__/DisplayBoardUnified.contract.test.tsx#L170-L198). Neither pins A+B → update A → B survives.

**Fail-first:** Render a board from `initial_state` with A#7 and B#7 (distinct IDs, owners, queue IDs). Push a real-format `queue_update` with `event_type='queue.updated'`, `data.queue_entries` only for A; assert B still visible, A updated, stable keys, no false cross-queue replacement. Check creation, cancellation, no-show and reconciliation across departments. Fix must define **backend-owned snapshot scope** (board-wide read or queue-scoped identity) before frontend merges; do not guess queue ownership by number or specialty label.

### QR-FE-009 — Advertised REST polling fallback never refreshes patient rows (P1 candidate)

**Code.** Frontend [`DisplayBoardUnified.tsx` L258–287](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DisplayBoardUnified.tsx#L258-L287) explicitly calls `/board/state` for **stats/board settings**, not live entries, and [L543–593](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DisplayBoardUnified.tsx#L543-L593) schedules it every 15–30+ seconds even in kiosk view as purported WS fallback. The other timer invokes `loadWindows()`, but [L327–335](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DisplayBoardUnified.tsx#L327-L335) this simply empties a removed legacy Windows route; it does **not** update queue rows. `queueData` is actually populated by WebSocket `initial_state` / `queue_update` [L363–423](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DisplayBoardUnified.tsx#L363-L423). The WS helper [`api/ws.ts` L68–70, L124–141](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/api/ws.ts#L68-L141) exhausts a finite five reconnect attempts. After prolonged WS failure, UI can keep refreshing its counts but display stale/missing patients; the "polling restores rows" comment is not supported by code.

**Risk.** False assurance of live patient row availability under network degradation. When the WS reconnects successfully, the server initial snapshot can heal the board; this finding is specifically the **sustained-disconnect** state, not all operation.

**Fail-first:** Mount board with synthetic initial_state A/B, mutate mocked backend queue, disconnect WS and exhaust five reconnects while REST /board/state responds with new stats. Advance fake timers >60s; assert actual row listing and count both reflect backend state, or present a prominent stale/unavailable indicator instead of silently claiming live. Backend must provide a **canonical safe display snapshot** or clear invalid state; don't repurpose stats or invent queue rows in React.

### QR-FE-010 — Queue WebSocket heartbeat ping is ignored (P2)

**Code.** [`useQueueWebSocket.ts` L106–120](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/hooks/useQueueWebSocket.ts#L106-L120) explicitly drops incoming application-level `{type:'ping'}` (same for `pong`) with no reply. The canonical backend [`ws/queue_ws.py` L381–405](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/ws/queue_ws.py#L381-L405) sends `{type:'ping'}` every 30s and waits for client text; only receiving **JSON `{type:'pong'}`** updates `last_pong` [L407–416](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/ws/queue_ws.py#L407-L416). A quiet subscription therefore reaches the 120s receive timeout and can be closed after `last_pong` age check [L424–435](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/ws/queue_ws.py#L424-L435). A browser WebSocket's native **control-frame pong** is not a substitute for this explicitly application JSON-based protocol.

**Risk.** Preventable periodic WS disconnections, missed instant update window during reconnect; polling in `ModernQueueManager` remains at 60s, so total outage is bounded but operationally visible. No claim that backend auth or WS routing is broken; JWT-in-WebSocket-subprotocol and origin validation are present.

**Fail-first:** Simulate a real authenticated queue WS (backend test socket or paired client/server mock), receive server ping at t=30s and assert client emits exactly `{"type":"pong"}`, has no credential in URL/log, remains subscribed after t>120s idle, and still triggers snapshot refresh on `queue_update`. Assert reconnect cleanup stops timers and stale connections.

### QR-FE-011 — Doctor queue adapter silently selects another specialist (P2)

**Code.** [`QueueIntegration.tsx` L86–111](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/components/QueueIntegration.tsx#L86-L111) first tries supplied/authenticated doctor id, then first doctor with matching specialty, then unconditionally **`availableSpecialists[0]`**. Real [dentist panel L444–450](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DentistPanelUnified.tsx#L444-L450) passes a doctor id + dentistry; real [dermatologist panel L1379–1382](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DermatologistPanelUnified.tsx#L1379-L1382) passes only `specialty='dermatology'`. `fetchAvailableSpecialists` is a **public QR-eligible catalog**, not the currently authorized doctor scope: [backend `_specialists.py` L9–46, L151–195](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/api/v1/endpoints/qr_queue/_specialists.py#L9-L195) collects all bookable doctors, sorts cardiology before dermatology and dentistry, and defaults to first. When the authenticated specialist isn't listed (e.g. schedule/eligibility) and requested specialty also has no match, UI silently binds to some unrelated specialist. [`QueueIntegration` L129–135](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/components/QueueIntegration.tsx#L129-L135) passes that ID to the doctor-mode `ModernQueueManager`, which offers calling the next patient.

**Boundary:** The canonical [backend call-next route L41–72](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/api/v1/endpoints/qr_queue/_queue_ops.py#L41-L72) calls `_ensure_doctor_can_mutate_specialist_queue`; **do not claim authorization bypass** or that a wrong patient has actually been called. The confirmed bug is incorrect *view/selection identity* and the possibility of a confusing command attempt.

**Fail-first:** Synthetic list `[{id:1,specialty:'cardiology'}]` with authenticated doctor 22 / specialty dermatology; assert no cardiologist is selected and actionable doctor call-next is disabled/unavailable with a truthful no-match state. Repeat two dentists and a specific `specialistId` absent; require exact doctor identity, no fallback to same specialty if caller explicitly gave a different doctor ID. Prefer an authoritative doctor-workspace owner resolver, not arbitrary public QR catalog position.

### QR-FE-012 — `queue.created` events appended without deduplication (P2 candidate)

**Code.** Backend [`display_websocket.py` L598–641](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/backend/app/services/display_websocket.py#L598-L641) broadcasts `queue.created` as `queue_update` with `data.queue_entry_id,queue_id,number,...`. Frontend [`DisplayBoardUnified.tsx` L387–407](https://github.com/drsapaev/final/blob/106597d67ece48ee9380ded5725ba421aed8cbc0/frontend/src/pages/DisplayBoardUnified.tsx#L387-L407) constructs the new entry, then **always appends** it to `queueData`; it does not check an existing `id`/queue key. If an initial snapshot already includes the same row by the time this event arrives, or an event is delivered twice, the displayed queue contains duplicate cards. On a multi-queue board with same numbers, the new event also omits queue owner/cabinet display fields although backend event includes specialist/queue metadata, causing temporarily less distinguishable rows.

**Fail-first:** Render initial snapshot with synthetic entry id 101 / queue A, push identical `queue.created` for id 101 and assert exactly one visible card. Independently deliver the same `queue.created` event twice to an initially empty board; assert one card and stable owner identity. Then deliver an event for a **distinct** id 102 with same number on queue B and assert **both** remain; never deduplicate on number alone.
