[WelcomeView.tsx:765–781](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/views/WelcomeView.tsx#L765-L781) passes `onRowClick={(row)=> logger.info(...)}` with only the placeholder comment «Здесь можно открыть модальное окно». [EnhancedAppointmentsTable.tsx:219–222](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/components/tables/EnhancedAppointmentsTable.tsx#L219-L222) passes the provided truthy callback to `DataTable`, which enables clickable/keyboard-activated rows. Thus pressing Enter/Space/clicking the row appears actionable but never opens a record. This is already [historical `REG-FE-001`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/docs/audits/2026-10-29-registrar-frontend-review-ledger.md#L27-L34). Acceptance: wire `onRowClick={openRecordPreview}` (with agreed group identity) or remove the callback and associated fake row activation; test click AND keyboard.

### `REG-FE-004` — P2: quick status controls do not match the canonical queue/payment contract

[WelcomeView.tsx:217–232, 508–526](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/views/WelcomeView.tsx#L217-L232) sets URL `status=queued` for «Активная очередь» and `status=paid_pending` for «Ожидают оплаты», but [`computeRegistrarWorklistRows`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/registrarWorklistRows.ts#L174-L246) filters exact `entry.status === statusFilter`. Queue entry statuses include `waiting`/`called` etc, while a pending payment is independently represented by `entry.payment_status='pending'`; [same worklist module department stats](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/registrarWorklistRows.ts#L93-L117) already checks *both* `status==='paid_pending'` OR `payment_status==='pending'` for pending payments. So Quick «Ожидают оплаты» can hide real unpaid entries; «Активная очередь» can hide actual waiting rows. **Existing historical `REG-FE-004`**, no new ID. Acceptance: semantic filter predicate against canonical status+payment facets (not a single fictitious equality) shared by URL-persisted filters and worklist; synthetic waiting + payment_status pending tests in both all-department and filtered-tab modes. Preserve unrelated URL scope (prior `REG-FE-030` fix).

### `REG-FE-044` — P2: Welcome revenue not reconciled with payments SSOT

[WelcomeView.tsx:396–411](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/views/WelcomeView.tsx#L396-L411) renders `ModernStatistics(appointments, selectedDate)`. ## Two genuinely NEW findings (independent of the historical `REG-FE` IDs)

### NEW `REGWELCOME-FE-001` — P2: “Утренний статус приёма” does not show whether a doctor/queue is open

[WelcomeView.tsx:277–395](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/views/WelcomeView.tsx#L277-L395) says this is a morning doctor-readiness checklist and renders a card with **only `doc.name` plus `Пациентов` or `Записей`**. It computes `ownerGroups` exclusively by iterating `appointments` (flattened existing queue *entries*) and returns no card when `doctorsList.length===0`; it never consumes `DailyQueue.active`, doctor session/queue open state, opening timestamp, working hours or an active schedule. [`useRegistrarWorklistData.ts:315–337`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/useRegistrarWorklistData.ts#L315-L337) flattens only the `queue.entries` arrays into `appointments`, thus a configured, active doctor or department queue with **zero patients is absent from the checklist**. Even a queue with N registered patients is not proof that the specialist has opened the day's service — the rendered card gives no open/closed indicator.

This is **not** the already fixed `REG-FE-027`: that changed grouping by canonical owner, distinct patient count and verified today gating, and its tests check exactly those. **New business defect** is absence of actual open/closed status and zero-entry owners in a control explicitly presented as a morning readiness view. The code and comments alone prove that status is never fetched/displayed; how the business defines “opened” (queue active vs doctor check-in) needs owner SSOT clarification before implementation.

**Acceptance:** define authoritative doctor/resource readiness from backend (Queue active/open or configured session check-in, not inferred from presence of patients), list known scheduled/active owners **including zero-entry queues**, show “Открыт/Закрыт/Неизвестно” or equivalent localized states with source timestamp when available; test zero-entry open queue, queue with entries but not opened, historical-day suppression and data-load failure honesty. Do not invent a “closed” status when backend omits the readiness fact. No bypass of permissions/PHI.

### NEW `REGWELCOME-FE-002` — P2 conditional: “Экспорт CSV” exports unfiltered patients and incorrect day in filename while scoped view is active

[WelcomeView.tsx:433–454](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/views/WelcomeView.tsx#L433-L454) executes:
```ts
const csvContent = generateCSV(appointments);
const filename = `appointments_${getLocalDateString()}.csv`;
downloadCSV(csvContent, filename);
notify.success(`Экспортировано ${appointments.length} записей`);
```
But the actual visible table is [`data={filteredAppointments}` at WelcomeView:752–770](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/views/WelcomeView.tsx#L752-L770), with department/doctor/status/search filtering computed in [`RegistrarPanel.tsx:263–272`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/RegistrarPanel.tsx#L263-L272) and [`registrarWorklistRows.ts:174–267`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/registrarWorklistRows.ts#L174-L267). So when URL scope includes `?dept=lab&status=...` or a search, the user sees a subset but this unqualified button **downloads every source row for the loaded date**, including patient names/phone fragments outside the visible selection; count in success toast refers to all source rows. [`registrarCsv.ts:37–101`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/registrarCsv.ts#L37-L101) serializes exactly whichever array is passed, with phone masking but with FIO and service information. This is **not evidence of crossing a server authorization boundary**: Registrar can already access all returned rows; it is a potential unintended disclosure/scope surprise in an exported file when user thinks they exported a filtered view.

Separately, `getLocalDateString()` in the filename is clinic **today**, whereas [`useRegistrarWorklistData.ts:285–288`](https://github.com/drsapaev/final/blob/1583e1ed778d838168c6a6c519022589432c06f1/frontend/src/pages/registrar/useRegistrarWorklistData.ts#L285-L288) can load an arbitrary `target_date` chosen from the calendar or `?date`; it never passes that verified loaded date to Welcome CSV. A Nov 16 export of an Oct 25 historical sample is named `appointments_2026-11-16.csv`, misleading for downstream records.

**Acceptance:** first agree product semantics: export **filtered visible records only** by default (or clearly distinguish a second “Export all day” action with explicit scope and confirmation). Use the SSOT **loadedDate** for file date (not transient calendar selection if newer load pending) and include real filter/scope in filename or file metadata. Test 3 rows two departments + status/search only 1 visible → only 1 exported; historical sample loaded yesterday while today is now → correct historical filename; synthetic patient names only and restored phone masking. Existing historical `REG-FE-045/046` concern CSV content/CSV formula protection, not scope or correct filename, so no duplicate ID. If owner explicitly requires all-day export as default, amend the UI to **label that scope unambiguously**, retaining regression coverage.
