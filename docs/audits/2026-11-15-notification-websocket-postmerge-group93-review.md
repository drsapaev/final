2. [`_assign_queue_numbers_on_confirmation:936–948`](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/app/services/visit_confirmation_service.py#L930-L950) appends `{"queue_tag", "number", "queue_id"}`; only the separate `print_tickets` objects include `queue_name`.

[`test_telegram_confirm_callback.py`](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/tests/unit/test_telegram_confirm_callback.py) tests correctly configured API origin/request but not response rendering from `queue_numbers`; so merged #4082 green tests do not cover this branch.

Assert no KeyError, message states success with correct human-readable queue, exactly one original confirm operation and no second mutation, callback answered reliably even if best-effort `edit_text` fails. Scope only safe callback response handling, not confirmation transaction. Mandatory Telegram/clinical gate before source edits.

"❌ Визит отменен")`. It does not call any cancellation API or `VisitLifecycleService`, change `Visit.status`, consume the token or clear a pending reminder.
- No patient-facing public cancellation endpoint is present in the examined [`visit_confirmation.py`](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/app/api/v1/endpoints/visit_confirmation.py). This is **not** the separate `confirm_<appointment_id>`/ `cancel_<appointment_id>` callback problem `NOTIFYTGREMINDCB-BE-001` in still-unmerged #4076.
- #4084 test `test_keyboard_has_no_unsupported_tel_url` proves button existence/format and `test_invitation_dispatches_to_linked_chat` proves fake-bot dispatch, **not cancellation persistence**. Therefore #4084's claim that the cancel button remains actionable must be read as *rendered*, not *functional*.

**Fix acceptance:** define and approve patient cancellation policy/allowed statuses; add a legitimate token-addressed cancel command with actor/link authorization, replay protection, expired-token handling, queue state link and reminder lease reconciliation. Until a safe contract is authorized, do **not** tell the user “Визит отменен”; replace with truthful “запрос на отмену” / contact clinic messaging. Require mandatory clinical lifecycle/Telegram/DB gate and tests.

## P2 existing unchecked `TGCONFIRM-BE-004`: callback drops actor identity; unverified identity may be written as authoritative provenance

**Main source:**
- `_handle_visit_confirmation` passes trusted Telegram `callback.from_user.id` to `_confirm_visit_via_api(token, telegram_user_id)`, but [`bot.py:547–579`](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/app/services/telegram/bot.py#L547-L579) posts only `json={"token":token,"channel":"telegram"}`. The argument `telegram_user_id` is **unused**, so real callback audit attribution becomes `telegram_unknown`.
- The public [`TelegramConfirmRequest`](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/app/api/v1/endpoints/visit_confirmation.py#L17-L29) declares optional `telegram_user_id`, forwarded into [`confirm_by_telegram`](https://github.com/drsapaev/final/blob/c9b3d72719a9f4edb84740b890cfd8063e86239d/backend/app/services/visit_confirmation_service.py#L314-L397) and encoded in `confirmed_by="telegram_<claimed value>"` and the queue claim's `confirmation_telegram_id` without a bot-authenticated/linked source in that HTTP route.
- Important boundary: a valid bearer confirmation token remains required; this is **provenance/queue-claim attribution**, not a claim that tokenless strangers can confirm a visit.

**Fix acceptance:** document whether confirmation token alone is the permitted capability. Bot-origin verified actor must be attested via server-side authenticated pathway, not merely by forwarding arbitrary client JSON `telegram_user_id`; direct bearer requests either omit strong Telegram identity attribution or mark caller-supplied identity unverified, and must not merge queue identities from an untrusted claimed ID. Synthetic real-bot callback + direct-public route negative spoof-ID tests; mandatory policy approval where identity ownership semantics change.
