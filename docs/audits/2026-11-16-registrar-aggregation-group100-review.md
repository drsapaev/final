## NEW `REGAGG-FE-001` — P2 / OPEN: missing patient identity can merge unrelated patient records

**Root evidence:** [`registrarAggregation.ts:223–246`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/registrarAggregation.ts#L223-L246) creates a grouping key of `patient:{patient_id{"}"}` when a backend patient ID exists, but **otherwise** groups by `identity:{normalizedFio{"}"}|{phoneDigits{"}"}|{birth{"}"}`; only when all name/phone/birth inputs are absent does it use a per-record key. [`registrarAggregation.ts:258–312`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/registrarAggregation.ts#L258-L312) then merges all matching keys into **one** `patientGroups[patientKey]`. [`registrarAggregation.ts:465–500`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/registrarAggregation.ts#L465-L500) collects both record references, available actions, payment and services under that same presentation group.

**Why real DTO shapes permit collision:** [`_today_queues.py:485–494`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/backend/app/api/v1/endpoints/registrar_integration/_today_queues.py#L485-L494) initializes `patient_id=None`, `patient_name='Неизвестный пациент'`, `phone='Не указан'`, `patient_birth_year=None` before per-record helper resolution and sends those fields through [`_serialize_queue_entry(...)` around L667–700](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/backend/app/api/v1/endpoints/registrar_integration/_today_queues.py#L667-L700). A resolved patient normally replaces these defaults; the finding is conditional on two distinct actual entries having no resolved patient ID and an identical fallback/unverified identity.

**Concrete synthetic example:** entry A `{id:101, record_kind:'online_queue', patient_id:null, patient_fio:'Неизвестный пациент', patient_phone:'Не указан', patient_birth_year:null, queue_entry_id:101}` and entry B with same identity but `id=202`, `queue_entry_id=202`. Both produce identical `identity:неизвестный пациент||`; the aggregate presents **one patient card containing two unrelated record refs**. A real, different patient with the same unverified name/contact/birth also collides. Backend SSOT may reject individual clinical actions, but grouping itself misrepresents who is in the queue and can expose a combined edit/selection affordance. This is a **frontend presentation / workflow integrity issue**; no proof of wrong backend mutation or privacy incident.

**Tests already present / gap:** [`registrarAggregation.test.ts:575–608`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/__tests__/registrarAggregation.test.ts#L575-L608) tests same name with **different valid patient IDs**, so both groups stay distinct; it does **not** test missing/null IDs. Existing [`REG-FE-063`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/docs/audits/2026-10-29-registrar-frontend-review-ledger.md) resolved **ticket dedup within a known group**, not whether two distinct unknown patients should be grouped at all. Do not reopen or duplicate it.

**Fail-first acceptance:** for two synthetic independent queue entries with `patient_id=null`, identical unknown-name/phone/no-birth (and another case same real-looking FIO/shared phone), expect **two separate patient cards** with one corresponding `grouped_record_refs` each; an independently verified same `patient_id` across services must still aggregate into one card. No grouping based on unproven demographic identity for command scope. Prefer canonical backend identity or a unique per-record fallback when `patient_id` absent; do not silently infer a patient link. Confirm whether a separate authoritative `person/identity` or group ID exists in DTO before choosing any fallback.

**Status:** `CONFIRMED_SOURCE / RED_TEST_PENDING / NOT_FIXED`. Severity **P2** for an actionable cross-record presentation error; not a demonstrated security bypass.

## NEW `REGAGG-FE-002` — P2 / OPEN: aggregate status retains only first record's status

**Root evidence:** [`registrarAggregation.ts:299–341`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/registrarAggregation.ts#L299-L341) initializes a grouped patient card with `status: appointment.status` from **the first member**. Subsequent entries in [`registrarAggregation.ts:375–566`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/registrarAggregation.ts#L375-L566) merge visit/appointment/ticket IDs, times, payment statuses, services, etc., **but never reconcile `group.status` and never store an overall status summary**. [`registrarAggregation.ts:581–643`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/utils/registrarAggregation.ts#L581-L643) explicitly computes `payment_status='mixed'` where necessary, yet leaves the top-level queue status as that first member.

**Visible propagation:** [`registrarWorklistRows.ts:240–297`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/pages/registrar/registrarWorklistRows.ts#L240-L297) sorts the raw entries then aggregates into **one row per patient** in «Все отделения». [`appointmentsTableColumns.tsx:1260–1272`](https://github.com/drsapaev/final/blob/a8531540cfcd1039710a1362c979573820ba56b1/frontend/src/components/tables/appointmentsTableColumns.tsx#L1260-L1272) renders `renderStatus(String(row.status ?? ''))` as that row's visible primary status. Individual `queue_numbers[]` carry per-ticket status and may be inspected elsewhere, **but do not correct the primary status badge**.

**Concrete synthetic example:** same known patient_id=77, `record_kind='visit'`, first queue_time=08:00, status `done`; separate second queue entry of same patient at 09:00 with `waiting`. The combined card retains `status='done'`, while a real service is still waiting. Reverse order yields `waiting` even if another visit is already complete. There is **no canonical single status** representing both members. Backend queue state is not changed; user may wrongly think all services completed or all are waiting.

**Distinctness from older IDs:** `REG-FE-052` fixed **unknown canonical status values mapped to an invented scheduled badge** in the renderer; this finding concerns **which backend member's valid status is selected for a mixed-status patient group**. `REG-FE-063` fixed queue ticket dedup, not mixed-status summarization. `REG-FE-004` is the separate queue/payment filter namespace defect. All stay separate.

**Fail-first acceptance:** run pure aggregation on same verified patient_id with two real record refs and statuses `done` and `waiting` in both input orders. The group should visibly identify **mixed per-record statuses** or provide per-ticket/per-record status breakdown, not single misleading "done"/"waiting" as the entire patient status. Preserve canonical per-record status for action authorization; choose an explicit UI representation with product owner rather than inventing a composite clinical state. Also test same-status group, `no_show`/cancelled + waiting, and render the result in `EnhancedAppointmentsTable`. No extra API or backend mutation authorized by this review.

**Status:** `CONFIRMED_SOURCE / RED_TEST_PENDING / NOT_FIXED`. Severity **P2** for clinical workflow truthfulness.
