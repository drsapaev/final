### NOTIFYPAGEFLAG-BE-001 — P2 conditional: incorrect cursor `has_more` on the last full page

**Source.** [`RestMixin.get_inbox`, lines 134–190](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/notification_platform/_rest.py#L134-L190) reads `deliveries = list_deliveries(... cursor=cursor, limit=limit)`, then independently reads `total = count_deliveries(...)` **without a cursor** and sets `has_more = total > len(items)` when `len(items) == limit`. [`NotificationPlatformRepository.list_deliveries`, lines 140–152](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/repositories/notification_platform_repository.py#L140-L152) applies `sequence_id < cursor` only to the page query; `count_deliveries` has no cursor parameter.

**Consequence.** With 100 eligible deliveries and `limit=50`, the first page correctly says `has_more=true`; the second page returns the final 50 but still calculates `100 > 50` and advertises a third page, which returns empty. This occurs for non-first **full** final pages; partial final pages are handled differently. The public response contract for `GET /notifications/inbox`, `/history`, `/sync` and the WS sync response inherits this flag. It is **not** `NOTIFYSEQ-BE-001` (group 42 concurrent sequence collisions) nor `NOTIFYHISTORYPAGE-FE-001` (group 44 UI never requesting further pages).

**Synthetic RED test to implement.** Insert 50, 100 and 101 synthetic deliveries for one authorized user with unique ordered sequence IDs, then paginate `limit=50` through both REST and WS surfaces. For 100 assert page 2: 50 items, `has_more=false`, `next_cursor=null`; for 101 assert page 3: 1 item and terminal; for 50 assert page 1 terminal. Ensure filtered searches and role scopes do not introduce gaps/duplicates. Use cursor-aware lookahead (e.g. limit+1) or count of remaining rows, not the unfiltered global total.

### NOTIFYREDISJOINRACE-BE-001 — concurrent different handlers can leave an unregistered Redis channel

**Source:** [RedisPubSubBridge.subscribe, lines 117–164](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/ws_redis_pubsub.py#L117-L164). The bridge adds each handler to the mutable set before awaiting Redis SUBSCRIBE. Only the call with was_added=true and len(handlers)==1 actually subscribes. An overlapping registration of *a distinct handler* for the same logical channel sees len==2 and returns true without awaiting a Redis subscription. If the first in-flight redis-py SUBSCRIBE then raises, its failure handler removes only that first handler. The second handler remains registered locally, and its caller has already received true although no server-side SUBSCRIBE succeeded.

**Minimal interleaving:** A adds handler_A, starts and awaits SUBSCRIBE; B adds distinct handler_B on the same logical channel, observes set length 2, returns true; A's pending SUBSCRIBE raises, removes A; the bridge retains B without an active Redis subscription. The previously repaired DISPLAYRELAY-BE-003 scenario was **single-handler first-attempt failure followed by retry**; this is a **separate join-while-in-flight failure race** not resolved by the current was_added rollback. No specific active production caller registering two distinct handlers for a notification-user channel was confirmed: the personal manager caches one handler per user, so mark this **conditional/latent for multi-handler shared-bridge users**, not an observed notification outage. This is also distinct from group-48 NOTIFYREDISHOL-BE-001 (the shared listener blocked on an already-delivered handler).

**Synthetic RED test, not executed:** instantiate the real bridge with two distinct handler closures and a fake redis-py PubSub whose first subscribe blocks on an asyncio.Event then raises. Start A, start B while A is pending, release the failure, assert the bridge does **not** report success for B without real Redis subscription; either retry safely or roll back B. Then publish one synthetic remote frame and assert B receives it. Cover one-handler normal SUBSCRIBE, concurrent same-handler idempotency, unsubscribing A while B remains, and no leaked listener tasks.

### NOTIFYUNREADSCOPE-BE-001 — mixed scope in the server-owned unread-count snapshot

**Source:** [RestMixin.get_unread_counts, lines 200–226](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/notification_platform/_rest.py#L200-L226) resolves a panel role and department filter and applies both **only to total**. The same dictionary obtains by_role, by_channel, and by_severity through repository methods with **recipient_id only**, omitting the role/department filters. The public [GET /notifications/unread-count](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/api/v1/endpoints/notifications.py#L654-L675) explicitly accepts role and department_key. Even with no role argument, total defaults to the user's panel role while all three group maps span every role attached to the user.

**Example:** one authorized synthetic user has cardiology 2 unread and dermatology 3 unread, all stored in the same account. A request with role=doctor and department_key=cardiology can report total=2 but by_role.doctor=5 (and possibly by_channel.in_app_inbox=5).
