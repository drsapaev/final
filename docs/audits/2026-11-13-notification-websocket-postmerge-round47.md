### NOTIFYPAGEFLAG-BE-001 — P2 conditional: incorrect cursor `has_more` on the last full page

**Source.** [`RestMixin.get_inbox`, lines 134–190](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/notification_platform/_rest.py#L134-L190) reads `deliveries = list_deliveries(... cursor=cursor, limit=limit)`, then independently reads `total = count_deliveries(...)` **without a cursor** and sets `has_more = total > len(items)` when `len(items) == limit`. [`NotificationPlatformRepository.list_deliveries`, lines 140–152](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/repositories/notification_platform_repository.py#L140-L152) applies `sequence_id < cursor` only to the page query; `count_deliveries` has no cursor parameter.

**Consequence.** With 100 eligible deliveries and `limit=50`, the first page correctly says `has_more=true`; the second page returns the final 50 but still calculates `100 > 50` and advertises a third page, which returns empty. This occurs for non-first **full** final pages; partial final pages are handled differently. The public response contract for `GET /notifications/inbox`, `/history`, `/sync` and the WS sync response inherits this flag. It is **not** `NOTIFYSEQ-BE-001` (group 42 concurrent sequence collisions) nor `NOTIFYHISTORYPAGE-FE-001` (group 44 UI never requesting further pages).

**Synthetic RED test to implement.** Insert 50, 100 and 101 synthetic deliveries for one authorized user with unique ordered sequence IDs, then paginate `limit=50` through both REST and WS surfaces. For 100 assert page 2: 50 items, `has_more=false`, `next_cursor=null`; for 101 assert page 3: 1 item and terminal; for 50 assert page 1 terminal. Ensure filtered searches and role scopes do not introduce gaps/duplicates. Use cursor-aware lookahead (e.g. limit+1) or count of remaining rows, not the unfiltered global total.

### NOTIFYMARKSCOPE-FE-001 — P2 conditional: optimistic bulk read updates unrelated departments

**Source.** [`NotificationCenterContext.markAllAsRead`, lines 879–917](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationCenterContext.tsx#L879-L917) accepts `role` and `departmentKey`. The optimistic `setInbox` maps all items and skips only when `role && item.role && item.role !== normalizeRole(role)`. It **never checks `item.departmentKey`** and lets `item.role === null` through. The REST request immediately below sends **both** `role` and `department_key`. The backend [`NotificationPlatformRepository.mark_all_read`, lines 311–344](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/repositories/notification_platform_repository.py#L311-L344) filters recipient, role **and department**. A success only triggers `refreshUnreadCounts` on the frontend, not an immediate per-item inbox reconciliation.

**Consequence.** If a caller invokes `markAllAsRead("doctor", "cardiology")`, a `dermatology` delivery with `role=doctor` is locally rendered read even when the backend correctly leaves it unread. Role-unset items are also treated as within scope. The current [NotificationInbox action](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/components/notifications/NotificationInbox.tsx#L239-L251) sends only the role (no department), so the department-specific failure is **conditional on a scoped consumer**; avoid claiming an observed user incident. This is different from group 42 `NOTIFYROLLBACK-FE-001` (unsuccessful optimistic mutation); here the request **succeeds for a subset**.

**Synthetic RED test to implement.** Mount the provider with two doctor inbox rows from distinct department keys, plus a role-null row. Mock a successful backend mark-all for cardiology only. Verify exactly the matching row becomes read in local state, all other rows remain unchanged and server counts remain authoritative. Cover no-department, different-role, archived, and same-account cases.

### NOTIFYSYNCBADGE-FE-001 — P2 conditional: WS replay drops existing authoritative role counts

**Source.** [`RestMixin.get_inbox`, return keys near lines 175–191](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/notification_platform/_rest.py#L175-L191) supplies `items`, `total`, `unread_count`, `next_cursor`, `has_more`, `cursor`, `role` and `status`, **not** `by_role`/`by_channel`/`by_severity`. [`notification_websocket.py`, sync response](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/api/v1/endpoints/notification_websocket.py#L189-L218) forwards that payload. [`NotificationWebSocketContext`, lines 226–245](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationWebSocketContext.tsx#L226-L245) nevertheless builds a snapshot with `by_role: data.by_role || {}` (similarly for channel/severity) and calls `replaceNotifications`. [`NotificationCenterContext.replaceNotifications`, lines 612–622](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationCenterContext.tsx#L612-L622) applies this incomplete snapshot with `applyUnreadSnapshot(..., true)`, **overwriting** previous REST group breakdown with empty maps. [`getUnreadCount(role)`, lines 932–949](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationCenterContext.tsx#L932-L949) falls back to counting locally cached inbox rows when that role key is missing; [`HeaderNew` bell](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/components/layout/HeaderNew.tsx#L1-L1) uses role-specific counts.

**Consequence.** Example: server has 75 unread doctor deliveries and an accurate REST snapshot `{total:75,by_role:{doctor:75}}`; a reconnect replay returns the first 50 rows, `unread_count:75` but no `by_role`. The client replaces role counts with `{}`; the doctor badge can show only the 50 cached records even though server total is 75. This is an **incomplete replay payload + destructive merge** issue, separate from `NOTIFYACK-FE-001` (group 41 mutation ACKs and stale item state) and from `NOTIFYHISTORYPAGE-FE-001` (group 44 older rows unavailable via UI).

**Synthetic RED test to implement.** Seed 75 synthetic same-role unread server rows, a previous authoritative REST role map, and a WS replay with first 50 rows and no `by_role`. Assert that the role badge remains 75 and total remains 75; guard against account switches and older in-flight replies. Require an authoritative grouped snapshot or a safe follow-up refresh rather than manufacturing `{}` as a server-provided zero count.

### NOTIFYREADBUTTON-FE-001 — P2: "Прочитать" also opens the destination page

**Source.** [`NotificationInbox.handleOpen`, lines 217–239](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/components/notifications/NotificationInbox.tsx#L217-L239) first invokes `markAsSeen`/`markAsRead` and then resolves and navigates to the target using `navigateToNotificationTarget`. The separately rendered button **labelled `Прочитать`** [lines 488–512](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/components/notifications/NotificationInbox.tsx#L488-L512) calls `void handleOpen(item)` too. The notification body button explicitly invokes this Open handler, but the "read" action has different user-facing semantics from "open".

**Consequence.** A user trying simply to mark a notification read is taken to its `deepLink` (or inferred route) and leaves the inbox if a target exists. This is not group 44 `NOTIFYOPENBLOCK-FE-001`: that issue covers an **intended Open** navigation blocked by a failed read mutation; this one covers **unwanted navigation on a read-only control**. The existing guarded navigation helper is still essential for actual Open actions and must not be bypassed.

**Synthetic RED test to implement.** Render one synthetic notification with a safe app-relative target. Click the "Прочитать" button: expect exactly one read mutation, **zero navigation attempts**, and the inbox remaining open. Click the notification body: expect the existing guarded Open flow (including lab dirty-leave behavior). Also test mutation error and absent link. Preserve accessibility and control labels.

### NOTIFYWSCURSOR-BE-001 — invalid WS cursor silently treated as first page

**Exact source:** [notification_websocket.py lines 168–181](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/api/v1/endpoints/notification_websocket.py#L168-L181) coerces the supplied sync cursor with Python int and **catches TypeError/ValueError by assigning None**, then [passes that value to get_inbox](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/api/v1/endpoints/notification_websocket.py#L201-L218). Thus an authenticated command with a malformed cursor such as "not-an-int" returns a fresh first page without validation error; Boolean true also converts to 1. The corresponding [REST sync API accepts a typed integer cursor](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/api/v1/endpoints/notifications.py#L573-L654), with FastAPI validation for invalid strings.

**Scope and distinction:** This is a client-protocol corruption issue during pagination, not a recipient authorization bypass. Different from group-41 NOTIFYFRAME-BE-001 (non-object top-level frames / sync limit), group-42 NOTIFYSEQ-BE-001 (sequence collision) and the cursor end-of-pages report duplicated with #4054.

**Synthetic RED test, NOT executed:** authenticate a synthetic user; send a sync command with malformed string cursor and then Boolean cursor; expect a bounded error identifying the cursor and *no* unintended first-page query, while the socket remains usable. Follow with a valid integer cursor to prove recovery. Establish valid lower bound and whether null is allowed before implementation.

### NOTIFYREDISHOL-BE-001 — one slow user blocks the entire notification Redis subscriber loop

**Exact source:** [RedisPubSubBridge._listen_loop lines 208–246](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/ws_redis_pubsub.py#L208-L246) processes Redis messages in one async-for loop and **awaits each handler inline** before reading the next event. The [personal manager's per-user receiver](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/notification_websocket.py#L69-L87) awaits _send_json_local, which [awaits WebSocket.send_json without deadline](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/notification_websocket.py#L150-L167). A backpressured recipient A can therefore stall dispatch to **different recipient B** on the same worker's notification bridge, notwithstanding separate user channel names.

**Scope and distinction:** The impact is conditional on a blocked send, not proven under real load. Group-41 NOTIFYFANOUT-BE-001 concerns sequential *same-user* fanout and publisher ordering; this concerns the shared Redis listener for *different users*. Persistence is outbox-owned and is not claimed lost.

**Synthetic RED test, NOT executed:** fake Redis receives events for synthetic users A and B. Hold A's send unresolved; assert B's event is dispatched within a bounded time independently, without releasing A first. Verify same-recipient message ordering, safe timeout/cancellation, no unbounded detached task accumulation, and last-socket cleanup.

### NOTIFYREDISENVELOPE-BE-001 — valid non-object Redis JSON kills the listener

**Exact source:** [RedisPubSubBridge._listen_loop lines 221–245](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/ws_redis_pubsub.py#L221-L245) catches invalid json.loads syntax, then immediately calls envelope.get("source") and envelope.get("payload") **without checking that the parsed value is a dictionary**. A valid JSON array, null, number or string from a noncanonical producer raises an AttributeError and falls into the [outer crash/recovery block](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/ws_redis_pubsub.py#L244-L270), rather than dropping one bad frame.

**Scope and distinction:** Owned bridge publishers [create dictionary envelopes](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/backend/app/services/ws_redis_pubsub.py#L53-L67); malformed input depends on a faulty/trusted external publisher or transport corruption, **not established attacker access**. The older NOTIFYFRAME-BE-001 concerns WebSocket *client* payloads in another owner.

**Synthetic RED test, NOT executed:** fake pubsub first yields a matching-channel JSON array, then a valid canonical envelope. Assert the malformed event is ignored, the listener stays alive (no recovery/reset), and the valid event reaches its handler. Repeat null and string; verify no notification payload enters error logs.

### NOTIFYROUTECHURN-FE-001 — protected page transitions unnecessarily disconnect notification WebSocket

**Exact source:** [NotificationWebSocketProvider route effect lines 396–437](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationWebSocketContext.tsx#L396-L437) depends on location.pathname, even though its policy is based on whether a route is public. Cleanup calls disconnectRef.current and closeSocketSafely on every pathname change, including a move **between two protected staff pages with unchanged user/token**. [closeSocketSafely actively closes an OPEN socket](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationWebSocketContext.tsx#L145-L163); the next effect [schedules a new connection](https://github.com/drsapaev/final/blob/eaab3b9365c0a1056b90f1afdc74c5e18924cfc2/frontend/src/contexts/NotificationWebSocketContext.tsx#L304-L328). This repeats authentication, unread-count DB reads and a fresh 50-item replay after ordinary navigation.

**Impact / distinction:** Extra websocket handshakes and a transient disconnect window, conditional on typical multi-page navigation; no real dropped notifications were measured. Distinct from group-40 permanent-denial retry and group-41 cross-principal isolation. Before changing, verify whether per-route rotation is deliberate and preserve logout/public-route/identity changes.

**Synthetic RED test, NOT executed:** with MemoryRouter and fake WebSocket, establish a socket on a synthetic protected doctor page, navigate to a different protected doctor page, assert no close, no second socket, no duplicate replay. Move to login and assert clean close; change account/token and assert mandatory security replacement. Include CONNECTING and stale onclose races.
