## NOTIFYOCCURRENCE-BE-001 — P1 conditional: identical, independent critical alerts reuse an already-read delivery forever

**Owner / source chain.** The mounted [`POST /notifications/send-system-alert`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/api/v1/endpoints/notifications.py#L412-L438) accepts an admin-triggered alert type/message/details and invokes [`notifications_pkg/_system.py::send_system_alert`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notifications_pkg/_system.py#L20-L66). Its persisted `record_delivery_for_users` event uses stable `title`, `message`, `payload_snapshot={alert_type,message,details}`, type `system_alert`, source `system`, and severity/priority. The timestamp added to the separately formatted Telegram message **is not present** in the persisted canonical event.

The backend [`_build_event_dedup_key`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_policy.py#L439-L467) hashes only event type, source, scope, title, message, severity, priority, correlation (default `None`), entity, and snapshot — **no occurrence/trigger instance or time**. [`_create_or_get_event` lines 505–545](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_policy.py#L505-L545) returns the original row on a matching hash, and [`_create_or_get_delivery` lines 579–610](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_policy.py#L579-L610) returns the already existing delivery with the same recipient/channel/dedup key. There is no TTL or time-based dedup window in those paths; both event and delivery keys have [DB uniqueness constraints](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/models/notification.py#L24-L88).

**Conditional failure:** admin sends synthetic `alert_type=critical, message="Queue server unavailable", details={...}`, a recipient reads it, then **a genuinely independent repeat** of the identical alert occurs hours/days later. Second call reuses the old persisted event and old **read** delivery; no new unread inbox item or sequence. It may re-broadcast the old delivery as a realtime frame (subject to policy) but does not create a distinct durable unread incident; backend stats/history undercount independent occurrences, and original actor attribution/time remain. This is **not** a claim that legitimate *retries of the same event* should duplicate — the existing idempotency intention must be retained. P1 is conditional on independently repeated identical critical events.

**Synthetic fail-first:** disposable DB with one admin and one notification recipient, mock WS manager. Send identical critical system alert once; mark delivery read; advance fake clock, send a **second independent incident** with identical text/details but different occurrence identity (or absence of provider-provided identity); assert two separately persisted events/deliveries (second unread, latest cursor, correct occurrence actor/time). Repeat the first request with **same stable idempotency key** and assert only one delivery. Test concurrent duplicate requests and exact same-event replay; use canonical server event occurrence ID or bounded dedup semantics, not random dedup everywhere. Mandatory gate for DB/notification policy fix.

## NOTIFYBULKFANOUT-BE-001 — P2 conditional: bulk mark-read commits but never informs the same user's other sockets

**Owner / source chain.** The [`POST /notifications/mark-all-read` handler](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/api/v1/endpoints/notifications.py#L750-L778) calls [`RestMixin.mark_all_read`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_rest.py#L482-L503). This bulk method calls [`NotificationPlatformRepository.mark_all_read`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/repositories/notification_platform_repository.py#L342-L369), commits the many `read_at` updates, logs count and returns. **It neither broadcasts changed deliveries nor emits a scoped unread-count/inbox-resync event**. The WebSocket `notification_mark_all_read` command in [`notification_websocket.py`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/api/v1/endpoints/notification_websocket.py#L154-L172) sends its ACK **only to the requesting socket**, not to other personal sockets. By contrast single [`mark_read` in `_rest.py`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_rest.py#L456-L470) explicitly calls `_broadcast_delivery(current_user.id,...)` after commit.

**Conditional failure:** one principal has connected browser tabs A and B. A successfully sends mark-all-read. B receives no event to invalidate its local inbox/unread cache, so it can keep showing unread rows and a stale badge until a separate refresh. This remains a correctness gap **even if** previously reviewed frontend zero-count fallback (`NOTIFYZERO-FE-001`) and the latent WS ACK row synchronization (`NOTIFYACK-FE-001`) were fixed: B receives no relevant ACK/event at all. Does not alter DB read state, which was committed correctly.

**Synthetic fail-first:** two synthetic sockets for one recipient in a fake cross-worker Redis/local manager plus a negative socket for another user. Perform REST mark-all-read, then WS command on socket A. Assert B receives an **authorized, versioned/role-scoped resync or unread snapshot event** without leaking IDs to unrelated users; A may receive its ACK but should not double-count. Test role/department subset (other unrelated roles must not be accidentally zeroed), Redis unavailable fallback and idempotent repeat. Prefer a bounded resync signal over broadcasting thousands of row payloads. Requires source gate and cross-tab/worker regression.

## NOTIFYWSRATE-BE-001 — P2 conditional: one authenticated WS client can continuously trigger bounded-but-unthrottled DB inbox queries

**Owner / source chain.** [`websocket_notifications` `while True` frame dispatcher](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/api/v1/endpoints/notification_websocket.py#L64-L82) reads and processes every client message with no per-user or per-socket command-rate check, token-bucket, concurrency gate or cooloff. For each `notification_sync`, [lines 174–220](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/api/v1/endpoints/notification_websocket.py#L174-L220) now **correctly validates each `limit` to 1..200** (prior `NOTIFYSYNC-BE-001` fixed), but **does not limit the number of 200-row queries per second**. Every valid frame calls [`RestMixin.get_inbox`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_rest.py#L119-L191): database list query, total count and unread count, then sends a response on the same persistent session. The same socket also supports read/seen/archive and mark-all mutations in the same unthrottled loop. No WS-specific rate limiter appears in the active endpoint (the canonical queue socket has separate rate-check protections, but they are not invoked here).

**Conditional failure:** a buggy or malicious **already authorized** client sends many `notification_sync` frames repeatedly. Page-size clamping does not bound **aggregate DB load per unit time**. A single session can monopolize worker responsiveness/DB resources; impact depends on sender rate, DB rows, network and server resources. This is **not** a claim that anonymous WebSocket users can connect, nor a refile of the old unbounded numeric `limit` bug.

**Synthetic fail-first:** TestClient/fake-WebSocket send e.g. 1000 valid `notification_sync` frames at a deterministic fake-clock rate with `limit=200`; instrument mock `get_inbox` calls and confirm a fixed per-principal rate/burst limit with a bounded response/error or documented policy close. Simultaneously test a second valid user gets timely responses; malformed-limit safe error path remains usable, heartbeats are unaffected, and no tokens/patient data enter logs. Fix using server-side per-user quota/backpressure aligned with existing WebSocket policy and work queue, mandatory security/DB gate.

## NOTIFYREPLAYPAGE-FE-001 — P2 conditional: newly fixed reconnect replay stops after one 50-row page even if disconnected backlog is larger

**Owner / source chain.** The **recently merged** [`NotificationWebSocketContext.tsx` handshake catch-up](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/frontend/src/contexts/NotificationWebSocketContext.tsx#L212-L245) correctly fixes an older missing-replay issue by sending **exactly once per socket** `{"type":"notification_sync","limit":50}` after `connection_established`. The [`notification_sync_response` handler](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/frontend/src/contexts/NotificationWebSocketContext.tsx#L248-L267) consumes `items` and unread counts but does **not** read `has_more` or `next_cursor` and never requests another page. The backend [`RestMixin.get_inbox`](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/backend/app/services/notification_platform/_rest.py#L119-L191) already returns those continuation fields. The [new frontend test](https://github.com/drsapaev/final/blob/355d1a94b79d5793c42d98b6ea4802fa864ceea4/frontend/src/contexts/__tests__/NotificationWebSocketContext.test.tsx#L349-L381) asserts **one** 50-row `notification_sync` only, not >50 missed-events completeness.

**Conditional failure:** the tab is disconnected while >50 personal delivery rows are persisted, reconnects and receives latest 50; earlier missed critical/operational notifications **do not enter the live context via replay** even though the backend can paginate them. This does **not** undo the merged fix (replay now exists and works for <=50). It is distinct from prior `NOTIFYHISTORYPAGE-FE-001` (group 44: manual drawer history/search never requests older pages **in ordinary browsing**): this is a **reconnection-loss catch-up contract** of the WebSocket transport, added in the recent merge, with a separate boundary and test. It can combine with the old manual history limitation, but this review does not retally that older root cause.

**Synthetic fail-first:** mock one principal offline during 65 distinct persisted synthetic deliveries, with backend responses latest 50 and remaining 15 using `next_cursor`; reconnect and handshake, then assert the client walks continuation until caught up or a bounded quota reached, merges each delivery once, and never re-toasts old persisted deliveries. Cover server cursor collision repair prerequisite (`NOTIFYSEQ-BE-001` prior round), concurrent live events, stale socket close and auth-principal swap, pending request limits, 429/WS degradation and incomplete replay user feedback. Preserve per-connection single start of reconciliation but support multiple **pages**, not unbounded bursts. Any frontend/back-end realtime contract fix needs the repo's mandatory gate.
