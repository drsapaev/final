# PR A — Registrar: doctor-specific services, shared doctor queue, per-doctor recovery guidance (Workstream A)

## Summary

- **Exact service-to-doctor assignment (Tasks 1/3/4):** a service pinned to a concrete doctor (`Service.doctor_id`) is now offered ONLY on that doctor's wizard card and is bookable ONLY with that doctor — the canonical guard `assert_doctor_eligible_for_service` rejects a conflicting selection with 409 on every write surface (registrar cart save, edit-delta quote/apply, QR full-update). Specialty eligibility stays in force for the pinned doctor (fail-closed, no cross-specialty exception).
- **One doctor queue (Task 4):** services of the same doctor in one booking share the doctor's SINGLE queue of the day — one queue entry, one number — even when their queue_tags/categories differ (D01 «dermatology» + D_PROC «procedures»); each service's own code/name/price stays in the entry payload. `get_or_create_daily_queue` converges tag spellings for one (day, doctor) (PR-26 documented intent), the wizard seam assigns ONE entry per doctor-owned visit, and the edit-delta strict lookup resolves the merged entry by its read-model identity without the queue-tag filter.
- **Admin recovery guidance (Tasks 2/5):** the seed now maps D01/S01/S10 `department_key`; `/admin/setup-directions` gains a service-assignment readiness section (doctor_missing / specialty_mismatch / missing_specialty_mapping) with per-row fix links (`/admin/doctors`, catalog); the wizard renders an instruction block for unofferable pinned services. All new text localized in RU / EN / uz-Latn / uz-Cyrl / KK.
- Registrar per-doctor tabs (queue_owner_kind='doctor' + owner id, full names, empty-queue tabs) were already landed by PR #3438 and are pinned by the existing suites — not redone here.
